**Implementation note:** The most significant finding from testing against real hardware rather than a fixture only (the exact scenario `STORY-P0-04-01`'s acceptance criterion 3 exists to catch): QEMU's PVH direct-kernel-boot loader leaves `hvm_start_info.rsdp_paddr` zeroed, even though the Xen PVH spec documents that field as the RSDP's physical address. Diagnosed by bisecting with single-shot `isa-debug-exit` writes carrying diagnostic codes (the exit device terminates the VM on every write, so it can't be used as a sequential debug console — each hypothesis required its own rebuild-and-boot cycle) — first confirming `kernel_main` was reached with a non-zero `start_info_paddr`, then that the `hvm_start_info` magic matched, then finding `rsdp_paddr` itself was zero. `discover_topology` now falls back to the classical BIOS-era EBDA/ROM signature scan (`find_rsdp_via_bios_scan`, ACPI spec 5.2.5.1) whenever the PVH-provided address is zero, since QEMU places its generated ACPI tables at those legacy addresses regardless of which boot protocol loaded the kernel. This is documented in `acpi.rs`'s module doc comment and `find_rsdp_via_bios_scan`'s own doc comment, not left as a silent implementation detail a future reader would have to rediscover.

A second judgment call: `boot.rs` now moves `EBX` (the PVH `hvm_start_info` pointer, per the protocol) into `EDI` immediately before `call kernel_main`, changing `kernel_main`'s signature from `extern "C" fn() -> !` to `extern "C" fn(u64) -> !`. `EBX` is verified untouched by every instruction between `_start` and that point (the page-table/GDT setup only ever uses `EAX`/`ECX`/`EDX`), so no new register-save logic was needed — documented inline in `boot.rs`'s module doc comment so a future reader modifying the 32-bit setup code knows not to clobber `EBX` without updating that comment.

## The defect, and that it was real

`crate::lock::PriorityInheritingLock` and `crate::wcet::apply` both wrote `Tcb::priority`. The lock captured the holder's pre-boost priority at boost time and replayed it on unlock; the WCET path wrote a declared floor on overrun. Whichever wrote last won, silently:

| Order | What was silently discarded | Consequence |
|---|---|---|
| Degrade, then unlock | **The degrade** — `unlock` replayed the pre-boost value | A task demoted for exceeding its declared budget walked away at its original priority. An enforcement decision undone by an unrelated lock release |
| Boost, then degrade | **The boost** — `wcet` overwrote it while a waiter was blocked | The priority inversion the boost exists to prevent, re-created by the enforcement path. A high-priority waiter starvable because a *different* task overran |

The second is the more serious and is a `G-RT-1` defect: unbounded waiter latency caused by an unrelated task's overrun.

## The fix

```text
effective(task) = max(base_priority, inherited_priority)
```

evaluated on demand, never stored. `base_priority` is the task's own — the only field `wcet`'s degrade lowers. `inherited_priority` is the highest priority currently inherited from a waiter — written only by `lock`. **Neither subsystem writes the quantity the scheduler reads**, so there is no stored decision left for a second writer to invalidate.

The writers are separated by name (`set_base_priority` versus `inherit_priority`/`release_inheritance`), so a caller cannot reach the other's field by accident — which is what both of these did.

`max` also makes *"inheritance raises and never lowers"* structural rather than a guard at each call site that someone can forget.

**The tempting alternative was refused**, and the code comment had already refused it: a conditional restore stores the same decision and merely narrows the window in which it is stale. The bug was the storage.

## Clause 5 — the falsification, which is the part that matters

Reverting the composition — making `set_base_priority` also clear the inherited priority, which is exactly the old single-field collision — produces:

```text
---- lock::tests::a_degrade_taken_while_boosted_survives_the_unlock stdout ----
assertion `left == right` failed: the waiter still needs the holder to finish
  left: Some(Priority(2))
---- lock::tests::the_two_priority_writers_are_independent stdout ----
assertion `left == right` failed: degrade cannot cancel a boost
  left: Some(Priority(3))

test result: FAILED. 9 passed; 4 failed
```

**Four of the six new tests go red, with diagnostics naming the defect rather than a generic mismatch.**

**And all seven pre-existing `lock.rs` tests stayed green under that same falsification.** That is not a footnote — it is the demonstration of *why this shipped*. The old suite asserted priority values in scenarios where only one subsystem was involved, so it could not see a collision that requires both. A test suite that cannot fail on a defect is not evidence that the defect is absent.

The overrun in every composition test is driven through **`wcet::account_tick`** — the entry point the timer ISR actually calls, and the only one that both detects an overrun *and* applies the declared policy. `record_tick` alone only detects; testing against it would have exercised half the path and proved nothing about the composition.

## Raw evidence

Six new host tests in `kernel::lock::tests`, all passing:

- `a_degrade_taken_while_boosted_survives_the_unlock` — the holder lands on floor 2, not on its pre-boost 5
- `an_overrun_never_lets_an_uninvolved_task_outrank_the_boosted_holder` — medium (15) never outranks the boosted holder across the degrade, and does once the waiter is released
- `the_two_priority_writers_are_independent` — both directions, with no lock or overrun machinery
- `inheritance_never_lowers_an_already_higher_inherited_priority`
- `an_inherited_priority_below_the_base_changes_nothing`
- `the_release_spoor_records_the_priority_the_task_actually_lands_on`

Two pre-existing `preempt.rs` tests that simulated a boost via the old single-field writer now call `inherit_priority`, which is what they always meant. No test's *meaning* changed.

`kernel::sched::highest_priority_ready` was reading the raw field and now reads `priority()` — selection is exactly the place a boosted holder must outrank an uninvolved medium task, so it is the one reader where the distinction is load-bearing.

Both `KNOWN DEFECT (LE-22)` comment blocks are gone, replaced by a statement of the composition rule pointing at the other side.

## What is not claimed

- **No Tier 0 fixture (`LE-50`).** The composed scenario has not run under genuine timer-driven preemption. `kernel::fixture_priority_inversion` proves the *inheritance* half that way; the composed case needs its own fixture, feature flag, `xtask` table entry and CI step, and extending the existing one would alter evidence a Verified Story rests on. Nothing blocks it. **Inventing a weaker Tier 0 claim to close the clause on schedule is what `ADR 0005`'s trap section forbids**, so the Story is `Host` and the debt is registered.
- **Two contended locks are still wrong (`LE-49`).** `release_inheritance` clears the task's inheritance outright, so unlocking one contended lock drops a boost the other's waiter needs. **Not a regression** — the old code wrote back a stale *absolute* value in the same scenario, which could raise a task above any priority it was entitled to — but a real remaining hole, found while fixing this one. The correct fix needs per-lock inheritance records, which needs blocking waiters, which this kernel does not have.
- **`LE-45` is not explained.** The soak anomaly was a `priority-inversion` fixture returning a non-zero exit with **no serial capture** (`LE-46`), in exactly this subsystem, and it is tempting to connect the two. **It is not connectable.** An unreproduced failure with no diagnostic cannot be attributed to a defect after the fact — that is the over-claiming [`40A`](../../session/hand-2026-07-28/40A-soak-anomaly-decision.md) refused, and `LE-45` stays open on its own terms. What can honestly be said is narrower and still worth saying: **a real defect did exist in that subsystem, so "environmental artifact" was never the only live hypothesis.**
- **Inheritance is still not transitive**, and no Story's assurance state moved.

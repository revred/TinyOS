This kernel now performs genuinely preemptive dispatch: the local-APIC timer, armed since `STORY-P0-04-02` and consumed by nothing since, takes a task off the CPU whether or not that task cooperates.

## The finding: the obvious place to save extended state is the wrong place

`LE-14` has been open since it was raised: `kernel::context::switch` saves callee-saved integer registers and flags and nothing else, which is sound only because every switch was *cooperative* — the SysV ABI makes XMM registers caller-saved, so a task that reaches `switch` by calling it has already spilled anything live. The next-session mandate named this as the trap to walk into, and required it be scoped rather than implied. It was scoped: an acceptance criterion of this Story, not a follow-up.

The implementation did the obvious thing — save the task's x87/SSE state when a tick decides to preempt, restore it when the task is resumed — and the fixture's very first run failed:

```text
fixture-preempt: xmm0 pattern=0x123456789abcdef clobber=0xfedcba9876543210 corrupted=true first_foreign_value=0x124df8
```

`0x124df8` is the diagnosis. It is neither the victim's pattern nor the preemptor's clobber value; it looks like a code address, because that is what it is. **An interrupt handler is itself ordinary compiled code running on the interrupted task's stack, and it can touch SSE registers whether or not it goes on to preempt anything.** Guarding only the preempting ticks left every *other* tick — the overwhelming majority — free to corrupt the task it interrupted.

The save/restore moved into the timer ISR **stub**, wrapping the entire handler call, with the 512-byte area carved out of the interrupted stack:

```asm
        mov rbx, rsp
        sub rsp, {extended_state_bytes}
        and rsp, -16
        fxsave [rsp]
        call timer_interrupt_handler
        fxrstor [rsp]
        mov rsp, rbx
```

That is correct by *construction* rather than by an argument about what the handler happens to compile to: nothing Rust can emit runs before the `fxsave` or after the `fxrstor`. It also composes with a context switch taken inside the handler for free — the area is on the task's own stack, so it travels with the suspended task and is restored when that task is resumed, however much later.

Worth stating plainly: the correct fix is *broader* than the Story's own criterion asked for. Every binary in this workspace that arms the timer now has its SSE state protected from its own tick handler, cooperative scheduling or not. That was a latent defect before this Story, not one this Story introduced.

**And it was then deliberately falsified.** With the `fxsave`/`fxrstor` pair removed from the stub and nothing else changed:

```text
fixture-preempt: xmm0 ... corrupted=true first_foreign_value=0x124c18 at_iteration=495535
TINYOS-RESULT/1 fixture=preempt ok=false
```

Corruption at iteration 495,535 — mid-run, at a tick, not at iteration 1 — which is precisely what separates "an interrupt destroyed the register" from "the task's own compiled code did". A save/restore nobody has watched fail is a save/restore nobody has evidence for.

## Design decisions worth carrying forward

**Interrupts are enabled only while a task runs.** The dispatcher holds `&mut Scheduler`; the tick hook reads the same scheduler. Those cannot both be true at once, and the mechanism that guarantees it is not a convention or a software flag — it is `RFLAGS`. The dispatcher body runs with `IF` clear, and a task's own saved flags (`0x202` from `Context::new`, or whatever the ISR's `pushfq` captured) re-enable interrupts across the switch *into* it and clear them again across the switch *back*. Nothing has to remember to do anything; the flag travels with the context. `kernel::preempt` therefore takes `*mut Scheduler` rather than `&mut Scheduler` and only ever forms a short-lived shared reference from it. Task code that touches the scheduler itself uses `without_interrupts`, which is the same property bought explicitly.

**The tick hook is a registered pointer, not a linker symbol.** The fault path uses `tinyos_fault_entry`: the HAL declares it, the binary defines it. That works because *every* binary needs a fault handler. Most binaries in this workspace legitimately have no tick consumer, so preemption is opt-in via `set_tick_hook`, and a build that registers nothing ticks exactly as it did before this Story. That is what keeps every pre-existing fixture bit-for-bit unaffected.

**The end-of-interrupt must precede the hook.** A preempting hook does not return until the interrupted task is next resumed, and until the local APIC is told the interrupt is complete it delivers no further ticks. Signalling afterwards would mean the *first* preemption silently stopped the clock and nothing could ever be preempted again. This is a one-line ordering with a system-wide consequence, so it is documented at the call site rather than left to be rediscovered.

**Equal priority does not preempt, and its absence is pinned by a test.** The comparison is strictly greater. Tick-driven rotation between equal-priority Ready tasks is a scheduling *policy* this Story has no requirement for, and adding one silently would change dispatch behaviour nothing asked for. A later Story that wants round-robin has to change a test rather than discover the behaviour.

**The decision is taken about the task the dispatcher would actually choose.** `on_timer_tick` reads the candidate through `Scheduler::highest_priority_ready` itself, never a parallel iteration that could drift from it — and that is asserted against a real `Scheduler`, because a drift between two selections is invisible to a pure-function test over invented inputs.

**The inversion test asserts three things, not one.** The dispatch order (`low → high → low → high`), medium's frozen counter across the window, *and* that medium was `Ready` throughout that window and does run afterwards. The third is the one it would have been easy to omit — a frozen counter for a task that was never runnable proves nothing at all, and the test would have passed for entirely the wrong reason.

## What this closes

- **`LE-14` — extended-state save/restore.** Closed, and more broadly than scoped: in the ISR stub, so it covers every tick rather than only preempting ones.
- **`LE-01` — priority inheritance's behavioural proof.** Closed. `STORY-P0-02-03`'s own doc comment has said since `EPIC-P0` that the behavioural half needed a dispatcher this kernel did not have. It has one now, and the three-task scenario runs for real: `dispatch order=[0, 2, 0, 2, 1]`, `counter_at_block=0 counter_at_resume=0 counter_final=1000`.
- **`STORY-P0-04-02`'s dangling primitive.** The armed timer has a consumer.

## What remains open

1. **`LE-02` is not closed and this Story did not touch it.** `kernel::wcet::record_tick` is still not driven by the real timer, and no overrun trips a declared fault policy. That is `STORY-P1-04-02`, and `FEAT-P1-04` does not exit until it lands.
2. **The shipping image does not preempt.** `os` installs no tick hook yet; the path is proven in its own fixtures first, exactly as `run_once_in_space` was before `STORY-P1-03-03` moved it onto the real boot path. Moving it is small and is the natural companion to `-04-02`.
3. **Tier 0 only.** `LE-09` unchanged. The clause 4 bound is counted in *ticks*, not cycles or microseconds, deliberately: QEMU's APIC-timer-to-wall-clock relationship is not a number to build a `D03` budget on, and calling a tick count a latency figure is exactly the mistake `STORY-P1-03-03`'s `D04` result argued against.
4. **`FXSAVE`, not `XSAVE`.** x87/MMX/XMM0–15 are covered; AVX and wider state are not. `CR4.OSXSAVE` is not set and nothing in this kernel generates AVX today, but a build that enabled it would need a wider area and would be silently wrong until it got one. Named rather than assumed away.
5. **Equal-priority tasks do not rotate.** Deliberate (see above), and a real gap for any workload wanting fair sharing at one priority level.
6. **One preemption per fixture, not sustained multitasking.** Each scenario is scripted and demonstrates a single preemption. Nothing here is evidence about preemptive behaviour under sustained load, and no claim to that effect should be read into it.
7. **Single CPU.** The interrupt-free critical section is a uniprocessor argument throughout.
8. **The cost of the ISR-stub save is unmeasured.** Every timer tick now carries an `FXSAVE`/`FXRSTOR` pair and a 512-byte stack reservation. `check-timing-regression` passed across all twelve gated statistics, but that is **not** evidence about this change: `fixture_measure` installs a fault-only IDT and arms no timer, so none of the gated paths take a tick at all. Interrupt latency is `D03`'s to measure and `D03` has no baseline yet. The pair is two instructions and is certainly cheaper than the corruption it prevents, but "cheap" here is an argument, not a number, and it should not be quoted as one.

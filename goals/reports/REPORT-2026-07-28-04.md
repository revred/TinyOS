## The finding: a green first run reassured nobody, and shouldn't have

All three fixtures passed on their first run. Two of them were not evidence.

Every enforcement mutation was then removed from `wcet::apply` — the decision still taken, the spoor still stamped, nothing done to the task — and everything re-run. At the host level this behaved: five of five enforcement tests failed, and the decision-table and attribution tests correctly stayed green. At Tier 0 it found two defects.

**`wcet-restart` passed with enforcement entirely removed.** The fixture was proving its *own* context rewind. The tick hook rebuilds the offender's `Context` — that half legitimately belongs to the caller, since `wcet` owns neither stacks nor contexts — and `dispatch::run_once`'s ordinary `Running → Ready` transition put the task back in the queue. Between them they reproduce every *visible* effect of a restart: the entry counter advances, the accumulator is zero, the task runs again.

What they cannot reproduce is the **spacing**. A task whose budget window is never reset is over budget on every subsequent tick, so enforcements pile up one per tick instead of one per window:

| | attributed ticks | enforcements |
|---|---|---|
| enforcement working | 15 | 3 |
| enforcement removed | 7 | 3 |

The fixture now asserts every enforcement is a full `budget + 1` attributed ticks after the previous one — the only externally visible consequence of the kernel having reset the window, and the thing the fixture's own machinery cannot fake.

**`wcet-trip` reported `ok=true` with enforcement removed.** It checked the disposition it was handed and never checked the kernel had actually marked the task `Finished`. That matters more here than anywhere else in this workspace, because **this fixture's pass condition is a failure exit code**. `broken-boot` and `idt-apic-unrouted` set that precedent, and the precedent has a hole: a fixture that breaks for any other reason exits 1 exactly as a correct run does. The falsification demonstrated it — enforcement removed, `wcet-trip` still exited 1.

Two things changed. The fixture reads the task's state back out of the scheduler and reports `task_finished=`, and the CI step greps the serial capture for `task_finished=true` and `ok=true` rather than trusting the exit code alone. That is a strictly stronger pass condition than the two fixtures whose precedent it follows, and the difference is deliberate rather than incidental.

**Worth stating plainly:** neither defect was in the kernel. Both were in the evidence, and both would have shipped as a green Tier 0 fixture that proved nothing. The Story's own acceptance criterion 4 — "each proving the arm actually happened rather than that a function was called" — was written to prevent exactly this, and it took a falsification rather than a careful reading to find that the fixtures had not met it.

## Design decisions worth carrying forward

**An overrun is not a fault, and `Disposition::of` is untouched.** This was decided in the Story before the Test document and did not shift under implementation. `Disposition::of` reads exactly one field because every other quantity available at fault time comes from possibly attacker-steered execution (`BND-04`). `disposition_for` holds the same discipline for the same reason over a different input: it reads *only* the policy the task declared in advance — never how far over budget it went, never how many times it has overrun. A task cannot influence its own consequence by misbehaving harder. A host test asserts `Disposition::of` still answers exactly as it did before this Story, so a later change that routed overruns through it would have to edit that test.

**The policy is a parameter of `create_task`, and that cost 78 call sites.** Acceptance criterion 2 refused a default. The alternative — a defaulted field with a setter — would have made a task's overrun behaviour the property of whoever wrote the enforcement path. Every task in this workspace now states its consequence out loud at the point its budget is declared, and the ones that are not being tested state `TripToSafeState`, which is the fail-closed choice. There is no setter, so the declaration is immutable for a task's whole life.

**A degrade floor above the task's own priority is rejected, not clamped.** `Degrade(floor)` where `floor > priority` is `TaskCreateError::DegradeFloorAbovePriority`, checked before a pool slot is claimed. An overrun that *raised* a task's priority would turn a missed deadline into a route to a criticality level nobody granted — a privilege escalation reachable by exceeding a budget. `Priority::try_new` already refuses to clamp for the same reason; this is that rule applied one level up.

**`OverrunPolicy` is defined in `sched`, not `wcet`.** The Test document names it `kernel::wcet::OverrunPolicy` and it is reachable by that path, via a re-export. Defining it in `wcet` would have made `sched` depend on `wcet` while `wcet` already depends on `sched` — legal within a crate, and a cycle this codebase has been explicit about avoiding (`sched`'s own "no dependency on `context`" note). The declaration belongs to a task; the consequence belongs to `wcet`.

**The restart arm's context rewind is the caller's, by necessity and by design.** `wcet` owns neither stacks nor entry points, so `OverrunDisposition::RestartTask` resets the budget window and re-queues the task, and *obliges the caller* to rebuild the context. That seam is documented on the variant itself. It is also exactly the seam that let the fixture fake a restart, which is why the spacing assertion above exists.

**Re-initializing a `Context` over a stack holding a live ISR frame.** The disposition runs in interrupt context on the offending task's own stack. For `Restart` the hook builds a fresh `Context` over that stack while a suspended interrupt frame and the hook's own frames are still on it. This is sound only because nothing ever resumes that frame — the hook switches into `ABANDONED_CTX` and the task is next entered through the fresh context, whose `RSP` is the top of the same stack. Same argument `hal_x86_64::fault`'s stubs rely on, same `ABANDONED_CTX` pattern `fixture_fault` established. Stated in the fixture's module doc rather than left implied.

**One fixture file, three feature-gated arms.** Three files would let the arms drift — one growing a workaround the others never got — when the claim being made is precisely that the *same* enforcement path produces three different correct outcomes because the *declaration* differed. `MODE` is a `const` selected by `cfg!`, so exactly one arm can be live in any build.

**Clause 6's evidence is an equality, not an absence.** "Enforcement did not punish the innocent" proven by the absence of a failure would be worth very little. The tick hook keeps its own per-slot count of every tick it attributed, independent of the scheduler's books, and the fixture asserts the two agree task for task. A tick charged to the wrong task, charged twice, or charged to whoever ran last breaks that equality in one direction or the other.

## What this closes

- **`LE-02` — WCET has no timer or watchdog.** Closed. Both halves now exist and both are exercised on the real timer.
- **`kernel::wcet`'s two-Epic scope note.** The module doc has said since `STORY-P0-02-04` that it had "neither a periodic timer-tick source that calls `record_tick` on its own … nor the documented watchdog/failsafe system to hand a detected overrun off to". Both prerequisites are now met.
- **`FEAT-P1-04` exits.** `STORY-P1-04-01` and `-02` are both `baseline-debt`.

## What remains open

1. **`LE-20` — the shipping image still does not enforce, or preempt.** `os` installs no tick hook, so both this Story and `STORY-P1-04-01` are proven in fixtures and nowhere else. Two Stories have now been shipped whose mechanism does not run on the real boot path, and that should not become three.
2. **`LE-22` (new) — degrade and priority inheritance have not been reconciled.** `PriorityInheritingLock` records a holder's pre-boost priority and restores it on unlock. A boosted holder degraded mid-hold therefore has its degrade silently *undone* by the subsequent unlock; and degrading a boosted task discards a boost a high-priority waiter is depending on, reintroducing the inversion `STORY-P0-02-03` exists to prevent. No fixture combines the two, no test pins the behaviour, and neither module's doc mentions the other. This is a genuine interaction between two shipped features, found by reading rather than by a failure.
3. **`D03` still has no measured baseline.** Enforcement being *correct* and enforcement latency being *bounded in real time* are different claims and only the first is made here. The detection bound is counted in ticks, not microseconds, for the reason `TEST-P1-04-01-A` clause 4 gave.
4. **Tier 0 only.** `LE-09` unchanged.
5. **The `Nobody` attribution arm never fires at Tier 0.** `unattributed=0` in every run, structurally: the dispatcher runs with `IF` clear, so a tick is only delivered once a task has been switched into. The arm is covered by host tests. The fixture reports the count and deliberately does not gate on it — whether a tick lands in the dispatcher is a property of QEMU's interrupt delivery, and gating on it would be gating on the emulator.
6. **No escalation on repeated overrun.** A degraded task that keeps overrunning is degraded again to no further effect and keeps running at its floor. Pinned by a host test so it is a recorded non-decision rather than an accident, but a real gap for anything wanting a "three strikes" policy.
7. **No periodic budget windows.** A budget is per-activation and resets only where a policy arm resets it. This scheduler has no notion of a task period, and inventing one was out of scope.
8. **Deadline monitoring is still not done.** `FEAT-P1-04`'s title names a deadline monitor *and* a WCET watchdog. A declared deadline is a different quantity from a declared execution budget, only the latter is enforced, and the Feature exits with that stated rather than blurred.
9. **The enforcement path's own cost is unmeasured.** Every tick now walks the task pool twice more than it did (`overrun_policy_of`, then `record_tick`'s own lookups). `check-timing-regression` is not evidence about this: `fixture_measure` arms no timer, so none of the gated paths take a tick at all. That is `D03`'s to measure, and `D03` has no baseline.

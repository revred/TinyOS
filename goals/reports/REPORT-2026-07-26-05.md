**Implementation note:** `Priority` uses a `0..=31` range (five bits) rather than a wider `u8` range or a small closed set of named levels. Rationale: wide enough to give every currently-anticipated criticality class (boot/idle tasks through interrupt-adjacent RT tasks) its own distinct level with headroom for tasks not yet designed, while staying small enough that a future priority-bitmap ready-queue (one bit per priority level, a standard fixed-priority scheduler technique) fits in a single `u32` register — a performance-relevant detail worth deciding now even though `STORY-P0-02-02` (context switch/ready-queue) hasn't landed yet, so the type doesn't need to change shape later. `TaskId` wraps `mem::PoolHandle` directly (rather than re-deriving its own index) so the scheduler doesn't duplicate `Pool`'s already-verified handle-validity invariants. `TaskCreateError` has one variant today (`Exhausted`); `PoolError::InvalidHandle` is mapped defensively into it via `From<PoolError>` for exhaustiveness even though `create_task` only ever calls `Pool::alloc`, which cannot produce that variant — documented inline as unreachable-in-practice rather than silently assumed. Neither `main.rs`, `boot.rs`, `qemu_exit.rs`, nor `Cargo.toml`'s `[[bin]]`/`[features]` sections were touched by this Story's implementation, avoiding a conflict with the concurrent `STORY-P0-04-01` workstream, which did touch those files.

**Deliberately not done:**

- **No integration with `Scheduler`/`Tcb` beyond sharing `TaskEntry`'s type.** `Context::new` takes `extern "C" fn() -> !` — the exact type `sched::TaskEntry` already is — but this Story's fixture builds its two `Context`s directly from local `extern "C" fn` entries rather than routing through `Scheduler::create_task`. `Scheduler` has no dispatch loop or "current task" concept yet (out of scope per `sched.rs`'s own module doc comment, and not part of this Story's acceptance criteria, which only require switching "between two tasks", not through the `Scheduler` API specifically); wiring the two together is naturally part of whichever future Story adds a real scheduler run loop.
- **No priority inheritance, WCET enforcement, or preemption (timer-interrupt-driven switching).** This Story is explicitly scoped to the register-save/restore primitive only — `STORY-P0-02-03` and `STORY-P0-02-04` are separate Stories, and nothing here assumes or requires a timer/interrupt path to exist.
- **`rflags`' initial value for a freshly-initialized task is a fixed constant (`0x202`), not derived from the boot context's actual flags.** `0x202` sets the reserved bit 1 and the interrupt-enable flag — a reasonable default for a task that hasn't run yet — but if a future Story needs a task to start with interrupts masked (or any other flag state), this constant will need to become a parameter, not silently reused as-is.

**Implementation note:** `Context` is a single `u64` (the saved stack pointer) — the callee-saved registers (`rbp`, `rbx`, `r12`-`r15`) and flags live on the suspended task's own stack, pushed/popped by `context_switch_asm`, the same technique every production x86_64 kernel (Linux's `switch_to`/`__switch_to_asm` included) uses; nothing here invents a new scheme. `context_switch_asm` is a `global_asm!`-defined free function (not inline `asm!` inside a normal Rust function body — inline asm mid-function is unsound for this pattern, since the compiler doesn't know `rsp` changed underneath its own prologue/epilogue) declared `extern "sysv64"` explicitly, which is what makes `context.rs`'s host unit test possible at all: `extern "C"` would silently follow the host OS's default convention (Windows x64 on this dev machine, System V on the kernel's real `x86_64-unknown-none` target), breaking the asm's fixed `rdi`/`rsi` argument-register assumptions the moment `cargo test` runs on Windows. `Context::new`'s stack-alignment arithmetic (`frame_base % 16 == 8`) reconstructs the System V AMD64 rule that `rsp % 16 == 8` at a callee's entry point immediately after `ret` pops the return address — verified correct by both the host test and the QEMU fixture actually reaching and running inside `task_a`/`task_b`'s function bodies without faulting.

# REPORT-2026-07-27-08

**Test(s) covered:** `TEST-P1-03-01-A` (`STORY-P1-03-01` — per-task `CR3` switching mechanism), performance domains `D04`/`D08`, mapped `SEC-03`/`SEC-19`, containment classes `C0`/`C1`/`C3`.

**Result: Pass — two genuinely distinct `exec::AddressSpace` trees are built, each identity-mapping a low kernel-replica region so a real `CR3` load into either does not immediately fault; switching into task A is a real, hardware-verified `CR3` reload; task A's deliberate read of task B's wholly-unmapped private address raises a real `#PF`, captured and contained (task A terminated, exactly as `fixture_fault`'s victims are); task B then runs to completion under its own distinct `CR3`. `STORY-P1-03-01`'s assurance state moves `specified` → `baseline-debt`. `FEAT-P1-03` is now In Progress; it does not exit on this Story alone — `STORY-P1-03-02` (W^X, teardown) is unstarted.**

## The Tier 0 evidence, verbatim

```
address-space-switch: space A built, cr3=0x127000
address-space-switch: space B built, cr3=0x128000
address-space-switch: distinct cr3 confirmed, creating tasks
address-space-switch: tasks created
address-space-switch: about to switch into task A, cr3_a=0x127000
address-space-switch terminated task 0
address-space-switch: back from task A
address-space-switch cr3_a=0x127000 cr3_b=0x128000 fault_captured=true task_a_finished=true task_b_runs=3 observed_cr3_after_a=0x127000 observed_cr3_after_b=0x128000
TINYOS-RESULT/1 fixture=address-space-switch ok=true
```

`observed_cr3_after_a`/`observed_cr3_after_b` are read directly off the `CR3` register (`hal_x86_64::paging::read_cr3()`) after each switch, not assumed from the values passed in — the two real reloads this Story claims, confirmed by the hardware itself. `task_a_finished=true` with `fault_captured=true` is the adversarial claim: task A's own page tables had no entry at all for task B's private address, the read faulted for real, and `kernel::fault`'s existing disposition/audit path (unmodified, the same functions `fixture_fault` calls) terminated exactly that task. `task_b_runs=3` is the scheduler still dispatching real work under a second, distinct `CR3` afterward.

## The finding: `AddressSpace::drop` silently erases both trees before their `CR3` is ever loaded

The fixture's first several attempts triple-faulted with no fixture-level diagnostic — QEMU reset, exit code 0, none of the success/failure `isa-debug-exit` codes. A `qemu -d int,cpu_reset` capture showed a `#PF`/`#DF`/triple-fault escalation with `CR3` already holding one of the two spaces' addresses, meaning the crash happened *after* a switch had already occurred, not during setup.

Adding progress checkpoints (`writeln!` after each construction step) isolated it precisely: the crash happened between "space B built" printing and the very next line — i.e., at the closing brace of the `unsafe` block that built both spaces and captured their `cr3()` values. `space_a`/`space_b` go out of scope there, and `AddressSpace`'s `Drop` impl (written for `STORY-P0-05-02`'s own teardown contract) unconditionally resets `*self.pml4 = PageTable::new()` and `*self.frame_pool = Pool::new()`. Both trees were being wiped to empty — every `PRESENT` bit cleared — the instant they were built, before either `CR3` value was ever loaded. The subsequent switch loaded a `CR3` pointing at a PML4 with nothing mapped in it at all: an immediate, unrecoverable fault on the very first instruction the new address space needed to fetch.

The fix is `core::mem::forget(space_a)`/`forget(space_b)` immediately after capturing their `cr3()` values — a deliberate leak, recorded as exactly that in both the fixture's own comment and `TEST-P1-03-01-A`'s scope-exclusion clause, not a workaround presented as a fix. Generation-safe teardown that could instead be *used* here (revoke, wipe, advance generation, only then permit reuse) does not exist yet; building it is `STORY-P1-03-02`'s charge, and reaching for `AddressSpace::drop`'s existing non-generation-safe teardown here would have reproduced the exact bug this Report just described.

## Design decisions worth stating

**The acceptance criteria were narrowed from their original draft, and the narrowing is recorded, not hidden.** The draft's criterion 1 implied production dispatch-loop wiring ("two tasks... run and switch"); what this Story actually proves is the mechanism, isolated in its own fixture, because wiring `switch_address_space` into `kernel::dispatch::run_once` for every real task needs W^X-correct kernel mappings *shared* across every space first (this fixture's own low-memory replica is a Tier 0 bootstrap that duplicates rather than shares, and is all-RWX — explicitly not that). Criterion 2's measured D04 same-space-vs-cross-space delta is also not produced, for the same reason: there is nothing in production yet to measure. Both narrowings are named in `STORY-P1-03-01.md`'s finalized acceptance criteria and in `TEST-P1-03-01-A`'s own scope-exclusion clause, rather than the Story quietly claiming less evidence than its draft implied.

**Two genuinely disjoint trees, not two sections in one tree.** `fixture_shared_memory_main.rs` already exercises two `AddressSpace` values sharing a *granted* mapping — deliberately not what this Story needed to prove. Task A's and task B's PML4/frame-pool statics are entirely separate; neither tree has any entry at all for the other's private address, so the probe's fault is a structural absence, not a permission check that happened to fire.

**Why `#UD`-style determinism informed the probe's shape, but the probe itself is a page fault.** Unlike `fixture_fault`'s `#UD`/`#GP` victims (chosen to avoid GDT/page-table-shape coupling), this fixture's adversarial read *is* a page-table-shape question by construction — that is what a cross-address-space isolation claim has to be about. The architecturally-guaranteed determinism this project's other fixtures reach for (real `ud2`, not a synthesized frame) is preserved here differently: the fault is guaranteed by the *absence* of a mapping this fixture itself controls completely, not by an emulator's fidelity to an architectural guarantee.

**Kernel context, not a real `TaskId`, for the fault report.** `tinyos_fault_entry`'s `FaultingContext` comes from the same `CURRENT_TASK`-slot convention `fixture_fault` established; task A's own slot correctly attributes the fault to a real `TaskId`. Nothing new here — recorded because it is the one place this fixture's fault-handling code is a near-verbatim copy of `fixture_fault`'s own, deliberately, rather than a from-scratch reimplementation of an already-proven pattern.

## What this Report does not establish

- **No hardware tier.** Tier 0 QEMU only; `LE-09` stays open.
- **No production integration.** No real task the boot path schedules has a dedicated address space; every existing Story's tasks are unaffected (`Tcb::address_space` defaults to `None`).
- **No W^X enforcement.** The fixture's kernel-replica mappings are all-RWX.
- **No teardown.** Both fixture address spaces are deliberately leaked, not torn down.
- **No measured `D04` switch-cost delta.** Nothing in production pays this cost yet to measure.

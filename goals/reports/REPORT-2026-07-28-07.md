## The finding: nine fixtures, never run

`TEST-P0-01-04-A` clause 5 was written to check the direction the existing drift guard did not: table → CI, rather than CI → table. Its first run:

```text
these fixtures exist but no CI step runs them, so they are unverified while
looking verified: ["context-switch", "idt-apic-timer", "idt-apic-unrouted",
"pci-enumeration", "address-space", "win32-shim", "blue-sharc",
"blue-sharc-broken", "shared-memory"]
```

Nine of twenty-three. Every one is named by an owning Test document that claims Tier 0 evidence for it; that evidence was last produced on a development machine at an unknown commit. All nine pass when run, so this is a gap in *evidence*, not in behaviour — but "it passed once locally" is exactly the standard `LE-07` was raised about.

The count took two corrections to get right, and both are worth recording because each would have overstated the problem:

1. The first version reported **eleven**, including `measure`, which CI runs as the bare `measure --runs=1` subcommand rather than by `--fixture=` name.
2. It also reported `dispatch-measure`, which is the *same binary* CI runs as `--fixture=dispatch` — `--fixture=` is overloaded across two namespaces with different spellings for one fixture. Coverage is now credited by **build target** `(package, binary, feature)`, which removes the special case rather than hard-coding it.

A third, mundane one: the workflow is checked out with CRLF, so an anchor on `"…qemu-x86_64\n"` matched nothing and reported every default-invoked fixture as unrun. The scan is line-based now.

## The finding that explains three deferrals

The exit-code hole was recorded across three mandates as "the CI step should grep the serial capture, per `wcet-trip`" — which reads like a CI edit. Running the two fixtures showed why nobody finished it:

```text
$ xtask qemu-x86_64 --fixture=broken-boot --serial-capture=bb.log   # exit 1
$ cat bb.log
                    <-- empty
$ xtask qemu-x86_64 --fixture=idt-apic-unrouted --serial-capture=idt.log   # exit 1
$ cat idt.log
                    <-- empty
```

**There was nothing to grep.** `broken-boot` panics, and the panic handler was `exit_qemu(QemuExitCode::Failure)` with no output. `idt-apic-unrouted` reaches `unhandled_interrupt_handler`, likewise a bare `exit_qemu`.

So the harness gap was hiding a system defect: **a TinyOS kernel that panicked died in complete silence.** On Tier 0 that costs an assertion. On a board — where there is no `isa-debug-exit` code at all (`LE-09`) — the serial line is the *only* diagnostic there would be.

## Green

All eleven `#[panic_handler]`s in the workspace were byte-identical bare `exit_qemu` calls. Rather than copy a sentinel eleven times, they route through one shared `hal_x86_64::qemu_exit::panic_report`:

```text
$ xtask qemu-x86_64 --fixture=broken-boot --serial-capture=bb3.log   # exit 1
TINYOS-PANIC/1 message=fixture-broken-boot: deliberate panic for TEST-P0-01-03-A file=src\kernel\src\main.rs line=141

$ xtask qemu-x86_64 --fixture=idt-apic-unrouted --serial-capture=idt2.log   # exit 1
TINYOS-UNROUTED/1 fail_closed=true
```

The message is emitted **before** the location deliberately: a CI step keyed on a line number breaks the next time anything above it moves, so `broken-boot`'s assertion greps its own deliberate panic message instead.

Ordering is fail-closed. The sentinel is written before the exit port is touched, because the exit port stops the machine; and every write is `let _ =`, so a UART that will not accept bytes cannot turn a panic into a hang.

## Falsification

Both new assertions were confirmed to be load-bearing by observing the Red state directly rather than by argument: **before** this Story, both captures were empty, so both greps fail on the pre-change binaries. That is the same discipline `TEST-P1-04-02-A` established when it found a broken `wcet-trip` still exiting 1 and still looking green.

## What is retrospective, and labelled as such

`TEST-P0-01-04-A` clause 6 documents the properties the `2da1ccd` tooling enforces — the loose-ends register, the status grammar, the fixture registry. **This is back-filling, not TDD**, and clause 7 says so. That tooling already had 25 unit tests covering every violation case (register gaps, closure without evidence, out-of-vocabulary states, `Complete` not matching `Completely`, `Functionally Verified` not truncating to `Verified`). What it lacked was the assurance artifact, which is what made it a bypass of rules 3 and 8 rather than a testing gap. Clauses 1–5 are genuinely Red-first; the distinction is stated rather than blurred, because blurring it is how the discipline erodes.

## What this does not establish

- **No hardware tier.** Tier 0 only; `LE-09` untouched.
- **The unrouted sentinel does not name its vector** (`LE-25`). One shared stub serves every unrouted vector and receives no vector argument. The line proves containment was reached, not which vector reached it.
- **The new guard catches a fixture nobody runs, not a fixture whose result nobody reads.** `LE-07` is reinforced, not closed.
- **No claim the panic path is safe under all conditions.** It writes to a UART from a context that may hold arbitrary broken state. It is best-effort by construction, and failure to emit cannot prevent termination.

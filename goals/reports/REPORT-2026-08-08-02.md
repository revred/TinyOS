# REPORT-2026-08-08-02 — A Human Typed at TinyOS on Silicon

**Test(s) covered:** [`TEST-P1-09-18-A`](../tests/TEST-P1-09-18-A.md) clause 7 — the

[`STORY-P1-09-18`](../stories/STORY-P1-09-18.md) criterion 6, and with it `21A` §3's

**Date:** evidence 2026-08-08 (two boots of the same image, power-cycled by software

**Platform, exactly (`ADR 0005` Q1 discipline):** Raspberry Pi 5 Model B, BCM2712,
4× Cortex-A76, `pi5-bcm2712`, **netbooted** — no writable filesystem mounted, so the
mains cut is safe by construction. Direct peer-to-peer Ethernet, link-local, no switch

**Toolchain/commit:** `nightly-2026-07-26`; `kernel8.img` 525,728 octets, sha256
`d23652c66ed2d5345e656fa6b4db19a80331755df3113a1a80085ab3b0e100dc`, fixture `measure`,
served by `tos64-netboot` and **confirmed transferred whole** — 1027 blocks, digest

**Session:** [`22A`](../../session/hand-2026-08-08/22A-the-usable-os-is-on-the-board.md)

**What this Report records:** `TINYCMD` — the verb core, the labelled volume and
the DOS front-end — executed a command line typed by a human on a laptop,
carried over a direct Ethernet cable to a Raspberry Pi 5, and answered with its
own output. This is the first time TinyOS has been *used* rather than *proven*.

## 1. The session

Sent with `ti64dink --console`, one `TOS64-CMD/1` frame per line typed, on a
board that had completed its boot campaign and settled.

```text
tos64>     sent   : verb=PING id=1 seq=1
    ANSWER : verb=PING seq=1
tos64>     sent   : verb=STATUS id=2 seq=2
    ANSWER : verb=STATUS seq=2 status=TOS64-RESULT/1 fixture=measure ok=true
tos64>     sent   : verb=SHELL id=3 seq=3 line="VER"
    ANSWER : verb=SHELL seq=3
    |
    | TinyOS Version 0.2.0 (Tier 0, x86_64)
    |
    |
tos64>     sent   : verb=SHELL id=3 seq=4 line="VOL"
    ANSWER : verb=SHELL seq=4
    |
    |  Volume in drive A is TINYOS
    |  Volume Serial Number is 5049-3501
    |
tos64>     sent   : verb=SHELL id=3 seq=5 line="FIND /N "cable" README.TXT"
    ANSWER : verb=SHELL seq=5
    | ---------- README.TXT
    | [2]This session runs over the Ethernet cable.
    |
tos64>     sent   : verb=SHELL id=3 seq=6 line="DEL README.TXT"
    ANSWER : verb=SHELL seq=6
    | Access denied: verb Delete is not granted to session WIRE [audited]
    |
tos64>     sent   : verb=SHELL id=3 seq=7 line="SET FLAVOR=DOS"
    ANSWER : verb=SHELL seq=7
    | Access denied: verb Env is not granted to session WIRE [audited]
    |
tos64>     sent   : verb=SHELL id=3 seq=8 line="ECHO %FLAVOR%"
    ANSWER : verb=SHELL seq=8
    | ECHO is on
    |
tos64>     sent   : verb=WOBBLE id=0 seq=9
    REFUSED: unknown-verb seq=9

console: 0 exchange(s) went unanswered
```

Every claim `STORY-P1-09-18` makes is visible in those nine exchanges:

- **The verb core answered.** `VOL` reported the volume label and serial the
  image seeded; `FIND /N` returned a numbered match out of a file on the
  board's own RAM volume. That is `TINYCMD`'s own rendering, not a re-wording.
- **Deny-by-default, audited, on the wire.** `DEL` and `SET` were each refused
  by name, naming the verb and the `WIRE` session, and the refusal came back
  *as text the operator can read* rather than as silence.
- **Statelessness.** `SET FLAVOR=DOS` was denied, and `ECHO %FLAVOR%` then
  answered `ECHO is on` — the variable does not exist, in a session where it
  was just set. A second run (§2) makes the stronger form of this observable.
- **The verb table still denies.** `WOBBLE` was refused `unknown-verb` by the
  table, not by a width check.

## 2. Statelessness, as a before/after on the board

From the run immediately preceding §1, on the same boot: a `DIR`, then two
mutating commands, then the same `DIR`.

```text
tos64>  line="DIR"              →  README.TXT 112 / VERBS.TXT 49 / 2 File(s)
tos64>  line="DEL README.TXT"   →  Access denied: verb Delete is not granted …
tos64>  line="MD SCRATCH"       →  Access denied: verb MakeDir is not granted …
tos64>  line="DIR"              →  README.TXT 112 / VERBS.TXT 49 / 2 File(s)
```

The two listings are byte-identical. The `World` is rebuilt from a `const` seed
for every admitted command, so nothing a frame does is visible to the next one.

## 3. The board's own counters, independently

Read off the wire from the board's canvas row after the sessions above:

```text
TOS64-CMD/1 last=SHELL answered=17 refused=2 lastlen=144
TOS64-RX/1  state=listening accepted=19 refused=23 dropped=42
```

Three things this row settles that the console alone could not:

- **`lastlen=144` is exactly `COMMAND_PAYLOAD_BYTES`.** The widened envelope
  arrives at precisely the width the board declares, so `LE-122`'s MAC-side FCS
  strip still holds at the new width — the defect that made every command
  `oversize` has not returned with the widening.
- **`answered=17` accounts for every frame sent.** 8 answers in §1, 6 in §2's
  run, and **the 3 exchanges that the console reported as `TIMEOUT`** — which
  the board therefore *did* answer. See §4.
- **`refused=2`** is the two `WOBBLE` frames, one per session. Nothing else was
  refused, so no command was lost to a width, a magic or a rate bound.

## 4. The finding: answers during the boot campaign arrive after the console's window

A first session was driven immediately after the board came up. Its first three
exchanges — `PING`, `STATUS`, `SHELL VER` — reported:

```text
    TIMEOUT: nothing answered seq=1 within 4s
             (the board not heard from — NOT a refusal)
```

and every exchange from the fourth onward answered normally. §3's `answered=17`
proves those three were **answered, late**, not lost: the board was still
running its boot measurement campaign, and the answer for each arrived after the
console's 4-second default had passed.

**Nothing here is a defect, and one thing here is a success.** The bound is a
stated UX default, not a measured one, and `ConsoleMode.DefaultTimeoutSeconds`
documents it as such. What matters is that the console reported the condition as
a **timeout** and explicitly *not* as a refusal — rule 1 of its design, which
exists so an operator does not go looking for a bug in the verb table when the
board is merely busy. It behaved correctly under the first real condition that
exercised it.

The operational consequence, recorded for the next bench session: **wait for
`TOS64-MEAS/2 END` before typing**, or pass a longer `--timeout`.

## 5. `LE-124`, confirmed on silicon rather than predicted

```text
tos64>  line="VER"  →  TinyOS Version 0.2.0 (Tier 0, x86_64)
```

On an AArch64 Raspberry Pi 5. The row was raised earlier the same day from a
host transcript; this is the board saying it. The string is a literal in
`shell/src/verbs.rs` and is pinned byte-exact by `TEST-P2-07-01-A`'s golden
transcript, so the gate that exists to catch shell-output drift is currently the
thing requiring the false line.

**No claim in this Report rests on that line**, and no future Report may quote
it as a platform fact until `LE-124` is closed.

## 6. What this Report does not claim

- **No timing.** The measurement campaign's own numbers ride the same wire and
  are not this Report's subject. Nothing here quotes a latency, and §4's
  four-second bound is a UX default, not a measurement.
- **No assurance-state change.** `STORY-P1-09-18`'s mapped performance domains,
  security controls and containment classes are unmoved; this closes a
  **functional** criterion. `D20` remains stated open debt.
- **No claim about a rate.** `answered=17` counts answers that left the board,
  not answers per unit time.
- **The 8 MB image ceiling** is measured in the Story, not here.

**Deliberately not done:**

- **No live `CR3` load / no real `#PF` induction.** `STORY-P0-05-02.md`'s acceptance criterion 1 records this: permission correctness is verified by reading back the constructed page-table entries (`hal_x86_64::paging::translate`), not by making the tree the CPU's live address space and catching a fault when code under test writes to a read-only page. Doing the latter needs an IDT/exception-handling subsystem this kernel doesn't have yet — a prerequisite for a future Story, not something silently faked here.
- **No demand-zero / `.bss`-style backing.** `AddressSpace::create` maps file-backed pages only; a section whose `virtual_size` exceeds `file_size` is out of this Story's scope (real loaders zero-fill the gap — not implemented).
- **No frame allocator beyond a fixed-capacity `Pool<PageTable, N>` the caller owns.** Physical backing for a section's content is `image_bytes` itself (no copy), which must begin on a page boundary — validated, not silently truncated/misaligned.
- **A structural prerequisite this Story needed and made, not "not done": relocating `boot.rs`/`qemu_exit.rs` from `kernel` into `hal-x86_64`.** `exec` needs `kernel::mem::Pool`, which rules out `kernel`'s own binary depending back on `exec` for a Tier 0 fixture (a cyclic crate dependency) — so `exec` got its own `exec-fixture` `[[bin]]`, and the shared PVH boot-entry glue moved to `hal-x86_64` so both binaries (and any future one) can reuse it. See `hal_x86_64::boot`'s doc comment for the full rationale; `STORY-P0-01-01`'s own acceptance criteria are unaffected (identical assembly, just relocated).
- **Boot stack increased from 64KiB to 1MiB** (`hal_x86_64::boot`), discovered necessary mid-session: the QEMU fixture triple-faulted (stack pointer wrapped to 0, `#PF` on push) under the original 64KiB budget, because this Story's unoptimized dev-profile build routinely passes 4096-byte `PageTable` values by value through several call layers without reusing stack slots the way an optimized build would. Verified via QEMU's `-d int` trace (register dump showed `RSP=0`, `CR2=0xfff...f8`) before the fix, and a clean boot after. Flagged in case a future Story's own stack usage grows further and needs another bump.

**Implementation note:** `hal_x86_64::paging` builds a 4-level (PML4/PDPT/PD/PT), 4KiB-granularity page-table tree using a caller-supplied `FrameAllocator` trait (Dependency Inversion — the module has no dependency on `kernel::mem::Pool` or any other specific allocator). `exec::address_space::AddressSpace` supplies a `Pool<PageTable, N>`-backed allocator and holds `&mut PageTable`/`&mut Pool<PageTable, N>` borrows from caller-owned storage rather than owning them directly — an `AddressSpace` must never move once its page-table cross-links are populated (the intermediate frames are referenced from `pml4` by raw address), so callers place both in a `static` or a stack local that's never itself moved after being borrowed, mirroring `context.rs`'s/`context_switch_fixture.rs`'s own `static`-based task/stack storage for the same reason. `AddressSpace`'s `Drop` impl resets `*pml4` and replaces `*frame_pool` with a fresh `Pool` — the assignment drops the old `Pool` in place first, running its own `Drop` and freeing every occupied slot — giving symmetric teardown for free from `Pool`'s existing discipline rather than needing per-handle bookkeeping in `AddressSpace` itself.

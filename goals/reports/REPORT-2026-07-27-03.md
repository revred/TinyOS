## The seam held — stated as a diff, not as a claim

The load-bearing result is what is *absent* from this Story's diff. `os/src/hal/` and `os/src/kernel/` are untouched entirely — zero lines. `os/src/xtask/src/timing.rs` gains 21 lines, all of them one `#[cfg(test)]` case. Everything else in the diff is the new crate, the assurance spine (contract row, Story, Test, this Report, the three rebased counts in `assurance.rs`, the traceability matrix and `FEAT-P1-01`), one workspace-member line in `os/Cargo.toml` with its `Cargo.lock` entry, and the crate-map row in `docs/mvp-delivery-strategy.md`. `STORY-P1-01-01` designed the seam a week before anything crossed it, and nothing had to be redesigned to cross it.

Two smaller design facts surfaced only by writing the second backend, neither of which required a change:

- The `Timebase` trait's `Option<u32>` return — added because QEMU/TCG has no honest timebase — turns out to carry the ARM case too: `CNTFRQ_EL0` left unprogrammed by firmware is a *different* reason for the same honest `None`.
- The `Environment { arch, cycle_source }` fields the envelope carries were speculative when written. They are now the fields that let one parser read both architectures with no version bump.

## The two `mrs` reads: what was and was not verified

Not executed. No AArch64 target spec, boot path or fixture exists in this repository — those are `LE-09` pieces 1, 2 and 5, sequenced after `FEAT-P1-02`. What *was* verified, beyond "it compiles":

```
$ rustup target add aarch64-unknown-none
$ cargo check -p hal-arm64 --target aarch64-unknown-none      # clean
```

and, via a throwaway out-of-tree `staticlib` that calls both reads (so LLVM cannot discard them as unreachable), the emitted assembly was inspected:

```
probe_cycles:
        isb
        mrs     x0, CNTVCT_EL0
        ret
probe_timebase:
        ...
        mrs     x8, CNTFRQ_EL0
```

So the inline assembly assembles, names the intended registers, and keeps the `isb` ordering barrier ahead of the count read (the architecture's own requirement — without it the `mrs` may be reordered against the instructions being timed, which for a *measurement* counter is the one error that silently corrupts every sample). That the registers then contain what the ARM ARM says they contain remains asserted, not verified, until a board runs.

## The finding: a 54 MHz ruler is a coarse ruler

`CNTVCT_EL0` is a fixed-frequency **system** counter, not a CPU cycle counter. On a Pi 5 it runs at 54 MHz — one tick is ~18.5 ns, against ~0.43 ns for a TSC tick at the 2,302–2,307 cycles/µs [`REPORT-2026-07-27-02`](REPORT-2026-07-27-02.md) measured. Consequences for `EPIC-P1`, recorded here because they change how hardware evidence must be read *before* the hardware arrives:

1. **A calibrated overhead of zero is an ordinary reading on this board**, not a failure. The harness already handled it (minimum-of-N with saturating correction), but nothing had forced the question until now; clause 6 pins the behavior so a later "overhead must be positive" assertion cannot be added innocently.
2. **The smallest metrics will be quantization-limited, not noise-limited.** A ~100 ns context switch is ~5 ticks. That is a different statistical problem from the 39–61% run-to-run p99 variation Tier 0 showed, and `STORY-P1-01-02`'s gate design must not assume the hardware tier is simply a quieter version of Tier 0 — the tiers are noisy for different reasons, and a tolerance derived from one does not transfer to the other.
3. **The higher-resolution alternative is not free.** `PMCCNTR_EL0` (the PMU cycle counter) is not architecturally guaranteed accessible, must be explicitly enabled at EL1, and is affected by frequency scaling in a way the generic timer is not. Recorded as new loose end **`LE-15`** — a considered follow-up when the board exists, deliberately not a substitution made on paper today.

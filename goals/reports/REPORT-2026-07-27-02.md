## Two real bugs found by measuring on target

### 1. `Scheduler::highest_priority_ready` could not execute on the real target binary (`#UD` → triple fault)

The D05 phase died on its first call. QEMU's `-d int,cpu_reset` trace gave `v=06` (`#UD`) at `0x10a140`, then `v=0d`, then `v=08`; `llvm-objdump` at that address showed `movups (%rax), %xmm0` inside the `filter`/`max_by_key` chain. LLVM uses SSE for ordinary 16-byte moves in float-free code, SSE raises `#UD` while `CR4.OSFXSR` is clear, and nothing in the boot path had ever set it. **A production scheduler function was therefore unable to run on target at all** — invisible until now because its verification was host-only and no `EPIC-P0` QEMU fixture ever called it.

Fixed by enabling SSE in `hal_x86_64::boot`'s long-mode entry (`CR0.EM` clear, `CR0.MP` set, `CR4.OSFXSR`+`OSXMMEXCPT` set), with the rejected soft-float alternative and the consequences recorded in [`docs/adr/0003-enable-sse-in-the-boot-path.md`](../../docs/adr/0003-enable-sse-in-the-boot-path.md). Newly-named debt from it: `context::switch` saves no SSE/x87 state (`LE-14`).

### 2. A fixture that switches into a task enables interrupts against an empty IDT

Before the SSE bug, the D04 phase died on its very first `context::switch`. `Context::new` seeds a task's initial `rflags` with `IF` set, so switching in enables interrupts — and a measurement fixture deliberately installs no IDT (calling `interrupts::init` would arm the APIC timer and inject ticks into the regions being measured). A legacy IRQ0 accumulated during the ~10 ms PIT calibration then fired against an empty IDT: triple fault. `EPIC-P0`'s `context-switch` fixture never hit this because it switches four times within the first millisecond of boot, before any legacy tick.

Fixed in the fixture by retiring the legacy PIC first (`hal_x86_64::interrupts::remap_and_mask_pic`, made `pub` for exactly this use — quiescing without arming). The underlying fail-open seam — `IF` set with no IDT installed — is named as `LE-11`, owned by `FEAT-P1-02`.

## Timebase: the microsecond conversion `REPORT-2026-07-27-01` needed

That Report's first "immediate next step" was to state a defensible TSC-frequency assumption so cycle-denominated evidence could be scored against microsecond-denominated guardrails. This Story supplies it as a **measurement, not an assumption**: `hal_x86_64::tsc::calibrate_cycles_per_us` times the timestamp counter against one 10 ms PIT channel-2 one-shot (1.193182 MHz by construction), inside the guest, with implausible results reported as no timebase rather than as a guess.

Observed across three consecutive runs: **2307, 2306, 2302 cycles/µs** (0.2% spread). Every microsecond figure below is derived with the run's own factor.

Honest limit: under QEMU/TCG both the TSC and the PIT are software models, so this factor describes the emulation. It makes Tier 0 numbers *comparable and checkable*; it does not make them silicon.

## Scored against `goals/performance/catalogue.tsv` — what closes, and what does not

Nothing closes. Scored explicitly rather than left implied, because `REPORT-2026-07-27-01`'s correction was precisely about tagging data with guardrail IDs and never doing this arithmetic:

- **`PERF-D07-G01`/`G02`/`G06`/`G07`** (p50 ≤ 0.05 µs / p99 ≤ 0.1 µs / p50 ≤ 100 cycles / p99 ≤ 250 cycles): alloc/free p50 is 1.57–2.04 µs and 3618–4696 cycles — **36×–47× over** the cycle budget, **31×–41× over** the µs budget. Does not close.
- **`PERF-D07-G20`** (denied work completes ≤ 0.125 µs, zero state change): the state-change half **holds** (every denial phase verified byte-for-byte no observable change, in both fixtures); the latency half is 5.7–28 µs at max. Does not close.
- **`PERF-D04-G01`/`G06`** (p50 ≤ 0.3 µs / ≤ 800 cycles): the context-switch round trip — **two** switches — has p50 620–728 cycles, i.e. 0.269/0.316/0.269 µs. Even charging the whole round trip to a single switch, two of three runs sit inside both budgets and the third misses the µs budget by 5%. This is the closest anything in this Report comes to a pass, and it still does not close: a budget met in two runs of three is not met.
- **`PERF-D04-G02`/`G03`/`G04`** (p99 ≤ 0.6 µs, p99.9 ≤ 0.9 µs, max ≤ 1.2 µs): runs 1–2 inside all three; run 3 outside all three (p99 2782 cycles = 1.21 µs). Does not close.
- **`PERF-D04-G05`/`D07-G05`/`D05-G05`** (run-to-run p99 CV ≤ 5%): 60.81% / 39.11% / 2.03%. The two small-operation metrics fail by an order of magnitude. Does not close — and see the next section, because this is the most important number in this Report.
- **`PERF-D05-G01`/`G06`** (p50 ≤ 0.2 µs / ≤ 500 cycles): ready-queue selection is 26530–28922 cycles, 11.5–12.5 µs — **53×–58× over**. Does not close.
- **`PERF-D05-G13`** (enqueue-to-service p99 ≤ 5 µs): the cooperative dispatch round is 49–51 µs at p99. Does not close.
- Every other guardrail in these three domains (`G08`–`G12`, `G14`–`G19`, `G21`–`G23`, and the Claim-stage `G24`/`G25`) was **not attempted** by this Story and is not claimed in any state.

**Why these overruns are not conclusions about the code.** Two properties of this measurement environment dominate every absolute number above, and both are stated here rather than buried:

1. **The measured binaries are dev-profile builds** (`cargo build` with no `--release`, which is what `xtask`'s fixture path has always used). Unoptimized iterator chains, no inlining, every `Pool` accessor a real call. `dispatch_select_highest_priority_ready` costing 55× a context switch is not a plausible property of the code — it is a property of an unoptimized `filter`/`max_by_key` chain under emulation.
2. **QEMU/TCG's emulated TSC does not advance in proportion to guest work** the way silicon does, and its noise floor is the host machine's scheduler.

So the Tier 0 numbers calibrate the *harness and the regression mechanism* — which is exactly what `FEAT-P1-01` says they are for — and they cannot fail or pass a code budget. Getting release-profile measurement onto the same harness is named debt (`LE-13`) and is the first thing `STORY-P1-01-02` needs.

## The finding that shapes `STORY-P1-01-02`

Three of five metrics have a run-to-run p99 coefficient of variation between 39% and 61% at Tier 0. **A timing-regression gate that thresholds p99 or max on a single Tier 0 run would be pure noise** — it would fail green code and pass real regressions, and once a gate does that, the honest response is to disable it, which is how gates die. Concretely, for `STORY-P1-01-02`:

- Gate on the statistics that are stable here: `min` and `p50` (D04's p50 spread is 620–728 cycles, ~8%), not `p99`/`max`.
- Require multiple runs per gate evaluation and compare medians of runs, not one run against one baseline.
- Set Tier 0 tolerances from *this measured noise*, not from the catalogue's hardware budgets — the catalogue's numbers are release-blocking targets for hardware evidence, not thresholds a TCG run can be judged against.
- Keep the tail percentiles reported (they are the evidence hardware measurement will eventually be judged on) while explicitly not gated at Tier 0, and say so in the gate's own output so nobody mistakes silence for a passing tail.

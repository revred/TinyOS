## 1. The result — `M2`

Three lines typed at `ti64dink --console` against a running board:

```text
tos64>     sent   : verb=PING id=1 seq=1
    ANSWER : verb=PING seq=1
tos64>     sent   : verb=STATUS id=2 seq=2
    ANSWER : verb=STATUS seq=2 status=TOS64-RESULT/1 fixture=measure ok=true
tos64>     sent   : verb=WOBBLE id=0 seq=3
    REFUSED: unknown-verb seq=3
console: 0 exchange(s) went unanswered
```

`19A` proved the round trip with three refusals. This is the other half and it is a different
claim: **`STATUS` carries a fact the board alone holds** — its own boot verdict, read out of the
running kernel because a human asked for it — and `WOBBLE` is now refused by the *verb table*
(`unknown-verb`) rather than by the size check, which is what makes the two accept arms above
evidence that the deny-by-default table was consulted at all.

The board's own row, one transcript rotation later:

```text
TOS64-RX/1  state=listening accepted=3 refused=27 dropped=30
TOS64-CMD/1 last=STATUS answered=2 refused=1 lastlen=46
```

**`lastlen=46`**, against `19A`'s `lastlen=50`. That is `LE-122`'s prediction met exactly: the
row the defect was measured on is the row that now reads correct, and the number moved by four.

## 2. `LE-122`, closed at the MAC as the row recommended

`19A` measured the disagreement rather than guessing it: the host builds `14 + 46 = 60` octets, the
board reported a 50-octet payload, and the delta was exactly the four-octet frame check sequence,
which the GEM descriptor's frame length includes.

The fix is one bit, **transcribed and not recalled** — `macb.h`
(`rpi-6.12.y`, `drivers/net/ethernet/cadence/macb.h`) gives
`#define MACB_DRFCS_OFFSET 17 /* FCS remove */` — set in `enable_receive`'s existing
read-modify-write of `NCFGR`, beside the promiscuous bit it already clears, and pinned by two host
tests: one that a device whose `NCFGR` reads back with the bit clear is written with it set, and one
that the bit is `1 << 17` and lands clear of every other field this path or the transmit path
writes.

**Why at the MAC and not by subtracting four in the glue**, which was the row's own reasoning and is
worth keeping: this is where every other bound on the receive path lives — the MAC enforces and
software does not compensate. A software subtraction encodes a hardware behaviour as arithmetic,
and on the day that bit is set by anything else the frame reads four octets *short* and every
command refuses as `Undersize` instead. Same defect, opposite name, and no test could tell.

`FRAME_CHECK_SEQUENCE_BYTES` is named in the module so the measured number has somewhere to be
stated. **Nothing subtracts it.**

## 3. `STORY-P1-09-16` criterion 4: five arms, ten frames each, one counter at a time

From a settled counter, `ti64dink --send <arm> --count 10`, reading the board's own row after each:

```text
settle        TOS64-RX/1 state=listening accepted=26 refused=67 dropped=93
ping x10      TOS64-RX/1 state=listening accepted=36 refused=67 dropped=103
unicast x10   TOS64-RX/1 state=listening accepted=46 refused=67 dropped=113
ethertype x10 TOS64-RX/1 state=listening accepted=46 refused=77 dropped=123
prefix x10    TOS64-RX/1 state=listening accepted=46 refused=87 dropped=133
notforus x10  TOS64-RX/1 state=listening accepted=46 refused=87 dropped=133
```

Every arm moved **exactly its own counter by exactly ten**, and the other one not at all:

- `ping` and `unicast` — `accepted +10`, `refused` unmoved. The hardware filter admits this board's
  own address and not only broadcast.
- `ethertype` (0x0800) and `prefix` (`TINYOS-`) — `refused +10`, `accepted` unmoved. The two
  software refusals are reachable, distinct, and counted.
- `notforus` (unicast to `02:aa:aa:aa:aa:aa`) — **nothing moved, including `dropped`.** The frame
  never entered the ring. That is the arm that matters most: it is the only one that tests the
  containment argument rather than the classifier, and a moved `refused` here would have meant the
  hardware address filter was not containing what `STORY-P1-09-16` says it contains.

An earlier pass, kept out of the record above, read `accepted +3` in the `ethertype` window. It was
straggling `unicast` admissions crossing a rotation boundary, not a misclassification — the arms
were re-run from a counter observed settled across two consecutive rotations, which is the run
quoted here. It is mentioned because the ambiguity was real and the resolution was to re-measure,
not to explain.

`dropped` tracks `accepted` almost one for one throughout, and that is the designed behaviour of a
one-descriptor ring polled once per beat against ten frames delivered at wire speed: nine of every
ten arrive with the descriptor still software-owned. `LE-118`'s fix is what makes that a number
instead of a dead ear.

## 4. What this closes, and what it does not

**Closes:** `LE-122`. `STORY-P1-09-16` criterion 4 in full — all five arms on silicon.
`STORY-P1-09-17` criterion 4's accept half, and with it `M2`.

**Does not close:** any `G04` gate, any bound, any timing claim. This Report measures mechanism, not
time — no figure in it is a latency and none may be quoted as one. `STORY-P1-09-16` and
`STORY-P1-09-17` remain assurance state `specified`: their functional criteria are met on hardware
and their mapped performance, security and containment evidence is untouched by this Report.

**Does not close `LE-117`.** The Pi OS card role is not implicated in this run — the board netbooted
and the bootloader EEPROM was not re-read — so the tripwire `19A` §6 item 3 owes is still owed, and
this Report's platform line deliberately does not restate `REPORT-2026-08-07-01`'s pin as though it
had been checked today.

**Does not close `LE-121`.** Untouched.

## 5. Method

One `xtask board-run --plug=… --dialect=shelly-gen2 --server=… --expect-digest=… --until=text=TOS64-CMD/1`:
digest verified, image served over DHCP+TFTP to one MAC from a named server address, mains cut under
software control, the wire watched for a named condition, and the board left ON. Roughly 90 s, no
hand on the bench. Every counter quoted above is the **board's own**, read off the wire — `LE-119`'s
close is what makes this Report possible at all, and it is four days old.

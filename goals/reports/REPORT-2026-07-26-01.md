# REPORT-2026-07-26-01

**Test(s) covered:** [`TEST-P0-01-01-A`](../tests/TEST-P0-01-01-A.md) (QEMU boot-to-halt integration test)

**Result:** **Pass.** `cargo run -p xtask -- qemu-x86_64` builds `os/src/kernel` against `os/targets/x86_64-tinyos.json` (`-Z build-std=core,compiler_builtins`), boots the resulting ELF64 image under QEMU x86_64 (`q35` machine type) via the Xen PVH direct-boot protocol, and reaches [`kernel_main`](../../os/src/kernel/src/main.rs), which halts cleanly by writing to QEMU's `isa-debug-exit` device. `xtask` observed QEMU exit code 33 (`(0x10 << 1) | 1`), mapped to `xtask`'s own exit code 0. No panic, no unexpected output (serial disabled entirely for this Test — the debug-exit device is the sole pass/fail signal). Boot completed well within the 15-second bounded startup budget `xtask` enforces.

**Environment/tier:** Tier 0 (QEMU x86_64, `qemu-system-x86_64` 11.0.50, `SoftwareFreedomConservancy.QEMU` winget package), per the [Target Hardware & Test Matrix](../../README.md#target-hardware--test-matrix).

**Toolchain/commit:** `nightly-2026-07-26` (`rustc 1.99.0-nightly (008fa22ce 2026-07-25)`), workspace commit base `167db4f4dc642c82d42336b6b4e621e53e57964c` (working tree, Phase 0 walking skeleton not yet committed at time of this Report).

**Notable implementation decisions made to pass this Test** (see linked ADRs for full rationale):

- Boot uses the **Xen PVH** direct-boot ELF note, not Multiboot — QEMU's built-in `-kernel` multiboot loader only accepts Multiboot **1** headers on **32-bit** ELF images, incompatible with an ELF64 `no_std` kernel. PVH is QEMU's supported direct-boot path for a raw 64-bit ELF.
- [ADR 0001](../../docs/adr/0001-nightly-toolchain-for-build-std.md): nightly toolchain, justified solely by `-Z build-std`'s lack of a stable equivalent.
- [ADR 0002](../../docs/adr/0002-no-msvc-dependency-on-windows.md): `xtask`'s host build avoids a Visual Studio/MSVC dependency on Windows, using `rust-lld` + the `cargo-xwin` import-library cache instead (a VS Build Tools install attempt failed with installer exit code 1602 on this machine; the project decision, per prior art in the sibling `Sharc.Blue` project, is not to depend on Microsoft's build tools at all).

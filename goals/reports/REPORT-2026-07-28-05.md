## The three findings worth carrying

### 1. Without the hook, a real workload hangs the shipping image outright

The falsification that removes `set_tick_hook` and changes nothing else does not merely make an assertion fail. Against the runaway workload it produces:

```text
xtask: kernel did not reach the isa-debug-exit port within the 15s boot time budget
```

That is what `LE-20` actually was, stated as a capture rather than as a paragraph. For two Features this project had a Verified preemptive scheduler and a Verified WCET watchdog, and its shipping image could be stopped indefinitely by twenty-four bits of machine code (`EB FE`) inside a workload the capability gate had already admitted. Nothing in the existing evidence would have shown that, because nothing in the existing evidence ran the shipping binary against a workload that declined to yield.

### 2. The `CR3` trap named in Handover 06 was real, and only the shipping image could have caught it

`os` dispatches through `run_once_in_space`; the `FEAT-P1-04` fixtures use `run_once`, which touches no `CR3` at all. Removing the supervisor-`CR3` reinstatement and running the shipping arm gives:

```text
tinyos: loaded image — 2 import(s), 2 granted, 0 trapped, cr3=0x147000
tinyos: scheduler hook_installed=true if_clear=true cr3_after_round=0x147000 ...
```

`cr3_after_round` is the *image's* `PML4`. The supervisor was running — and would have made its next scheduling decision — with the workload's address space live. This was survivable only because the image space attaches the shared kernel directories, so the supervisor's own code and stack stayed mapped; it is a containment defect rather than a crash, which is exactly the kind that survives a green test run. Handover 06 predicted it in the abstract; this Story is where it became observable, and the observation required the binary that ships.

### 3. Counting serviced ticks is not evidence that a hook is installed

Clause 1 was first written to assert `ticks_unattributed >= 1` — the boot stages run with interrupts on and no task on the CPU, so a live hook must count something. Two consecutive runs of identical binaries reported `ticks_attributed=[1,0,0,0] unattributed=1` and then `ticks_attributed=[0,0,0,0] unattributed=2`. The total held, but the split moved, and both numbers are a function of how long this boot took relative to a 16ms timer period. On a faster host the total could legitimately be zero, and a build that never installed a hook would then be indistinguishable from one that did.

`interrupts::tick_hook_installed()` reads the pointer back instead. The claim being made is about whether the hook is installed, and that is now what is asserted; the serviced-tick count is still reported, and is still asserted in the runaway arm where it is structurally guaranteed. **A gate whose verdict depends on host speed is the failure mode this project already carries as `LE-16`/`LE-18`**, and it very nearly acquired a second one.

## The declaration that changed, and why it was not a placeholder

The embedded workload declared `OverrunPolicy::TripToSafeState` with a 1,000-tick budget. The mandate called that "a placeholder rather than a decision". On inspection it is worse than unconsidered: it is the wrong answer.

`TripToSafeState` means a contained, capability-mediated application that does nothing worse than burn CPU may halt the whole system. That is a **strictly more severe** consequence than the same system gives the same task for a genuine CPU fault, where `kernel::fault::Disposition::of` answers `TerminateTask(task)` and reserves `HaltSystem` for the kernel's own context. It also hands that application precisely the denial of service that `PD-07`/`PD-08` temporal isolation and `BND-15` exist to deny it.

The workload now declares `Degrade(PRIORITY_MIN)` against an 8-tick budget: it keeps running — losing the CPU is a budget consequence, not a death sentence — but at the bottom of the priority space, where it can preempt nothing and starve nothing. `TripToSafeState` remains right for a task whose *failure* is a system-level event, and that distinction is the whole reason the policy is per-task.

## Evidence quality: what makes the runaway arm evidence about the shipping binary

The two Tier 0 arms differ in exactly one thing: which four pages `include_bytes!` embeds. The hook, the dispatch loop, the loop bound, the declared policy, the address-space handling and every assertion path are the same compiled code. A host test asserts the two images are byte-identical outside `.text`, so the loader path, the import surface and the capability decision cannot silently diverge between them either.

That is deliberately a stronger arrangement than a fixture. `TEST-P1-04-02-A`'s lesson was that a fixture which constructs part of the effect it is testing will pass without the part it is meant to test. Here the mechanism under test is not reconstructed anywhere: the runaway arm exercises the shipping hook, and the only thing it supplies is a workload that will not yield.

## What this does not establish

- **No hardware tier.** `LE-09` open. Every number here is a count of ticks, not a latency.
- **`D03` still has no measured baseline.** That the shipping image enforces *correctly* is this Story's claim; that it enforces within a bounded real time is not, and remains unmeasured.
- **The degrade is observed as a priority that dropped, not as a competitor that started winning.** The boot path carries one task. The second claim is `fixture_wcet_degrade`'s and is unaffected.
- **No teardown.** `ExitProcess` still routes into the capability trap.
- **`LE-22` untouched.** Degrade and priority inheritance are still unreconciled; this image takes no locks.
- **The dispatch loop's round bound is not a scheduling policy** and is not evidence about one. It is a property of a boot path with one workload and no idle task, and a boot path that gains either should revisit it.

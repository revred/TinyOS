**Deliberately not done:**

- **No live timer tick source.** Nothing in this kernel periodically calls `record_tick` on its own — the same missing ready-queue/priority-based dispatch loop `STORY-P0-02-03`'s own Report/handover already named as an open prerequisite. `record_tick` is a function any future timer-interrupt handler or dispatcher tick would call; none exists to call it yet.
- **No real watchdog/failsafe system.** `README.md` Non-Negotiable #5 commits to one at the design level, but no implementation exists anywhere in this codebase, independent of the dispatcher gap above. `OverrunHandler` is this Story's own standalone trait standing in for it (Dependency Inversion, mirroring `exec::win32_shim::CapabilityPolicy`'s stand-in for `aci`); wiring in a real watchdog implementation later is additive, not a rewrite, but it is a genuine, currently-unmet acceptance criterion (`STORY-P0-02-04.md`'s AC2, marked "partially met").
- **No admission control or budget scheduling** (e.g. rate-monotonic feasibility analysis at task-creation time) — this Story is purely reactive detection after ticks are attributed, not a preventive check that a task set's budgets are even schedulable together.
- **Budget windows reset only via explicit `reset_budget_window` calls**, not automatically on any periodic boundary (since there's no periodic tick source to drive that automatically either — same root cause as the timer-tick gap above).

# REPORT-2026-07-27-05

**Test(s) covered:** `TEST-P1-02-01-A` (`STORY-P1-02-01` — `#PF`/`#GP`/`#UD` capture, terminate-vs-halt disposition, spoor audit), performance domain `D02`, mapped `SEC-03`/`SEC-14`/`SEC-19`, mapped `BND-04`/`BND-17`/`BND-20`.

**Result: Pass — three real CPU exceptions, raised by real instructions from inside scheduled tasks under QEMU, are each captured, contained to the faulting task, audited, and survived: the scheduler ran a fourth task three times afterwards. A fault is no longer a silent, system-terminal event. `STORY-P1-02-01`'s assurance state moves `specified` → `baseline-debt`, not `verified`: Tier 0 only, no double-fault survival (`STORY-P1-02-02`), no fault-latency baseline yet, and no privilege boundary behind the word "task".**

The default handler is the quiet half of this Story. On the normal boot path there is no task to contain a fault to, so the policy returns `HaltSystem` and the system still stops — but it now **prints the vector, error code, `RIP`, `RFLAGS`, `RSP` and (for `#PF` only) the faulting address** before it does. That exact situation, a fault on a path with no task, is what cost `STORY-P1-01-01` two debugging cycles as a silent triple fault.

A small linking fact worth recording, because it caught this session: once `interrupts::init` references the fault stubs, `tinyos_fault_entry` becomes a **required symbol for any binary that installs the IDT**. The kernel binary failed to link until the default handler existed. `exec`'s fixture binaries still link fine — they never install an IDT, so `--gc-sections` drops the stubs and the requirement with them.

## The Tier 0 evidence, verbatim

```
fixture-fault switching into #UD victim (slot 0)
fixture-fault captured #UD vector=6 error_code=0x0 rip=0x103e11 cr2=0
fixture-fault terminated task 0
fixture-fault back in supervisor after #UD victim: finished=true current_cleared=true
fixture-fault switching into #GP victim (slot 1)
fixture-fault captured #GP vector=13 error_code=0x18 rip=0x103e45 cr2=0
fixture-fault terminated task 1
fixture-fault back in supervisor after #GP victim: finished=true current_cleared=true
fixture-fault switching into #PF victim (slot 2)
fixture-fault captured #PF vector=14 error_code=0x0 rip=0x10364f cr2=549755813888
fixture-fault terminated task 2
fixture-fault back in supervisor after #PF victim: finished=true current_cleared=true
fixture-fault survivor ran 3 times after three contained faults
fixture-fault captured=3 contained=3 fault_spoors=6
TINYOS-RESULT/1 fixture=fault ok=true
```

Every number there is load-bearing: `error_code=0x18` is the out-of-range selector the `#GP` victim loaded; `cr2=549755813888` is exactly 512 GiB, the canonical-but-unmapped address the `#PF` victim read; `cr2=0` on the other two is the type system refusing to report a stale `CR2` against a vector it means nothing for. The verdict travels on `STORY-P1-01-02`'s `TINYOS-RESULT/1` line — the mechanism a Pi 5 will depend on, getting its second user.

## The finding: "architecturally must fault" is not "faults under this emulator"

The `#GP` victim was first written as a `wrmsr` to reserved MSR `0xFFFF_FFFF` — architecturally a guaranteed `#GP`. **Under QEMU/TCG it did not fault at all.** The write was silently accepted, the task fell through to its own `unreachable!()`, and the run ended as a panic with no fault captured. The fixture reported failure, which is the system working; but the lesson is worth more than the fix:

> A Tier 0 fixture can only ever check what the *emulator* does. Where the architecture and the emulator disagree, Tier 0 sides with the emulator, silently.

That is the same class of gap `STORY-P1-01-01` hit from the other direction (code that passed every host test and could not execute on target). The replacement — loading a segment selector past the boot GDT's three-descriptor limit — is architecturally guaranteed *and* observed to fault here, and it produces a non-zero error code, which exercises the decoder rather than the zero path. Both facts are recorded in the fixture's own source so the next person does not repeat the experiment.

## Design decisions worth stating

**No `Resume` arm exists.** `STORY-P1-02-01`'s second criterion forbids speculative "maybe recoverable" paths, and this kernel has no recoverable fault case — no demand paging, no copy-on-write, no guard-page stack growth. So the disposition has exactly two arms, both reachable and both tested: terminate the faulting task, or halt when the kernel itself faulted. The entry stubs correspondingly save no registers and never execute `iretq`, because there is nothing to return to. When a genuine recoverable case exists it arrives with its own Story, its own enumeration, and the save/restore that path would then need — rather than that machinery sitting unused and unexercised in a fault path in the meantime.

**The frame is evidence, never authority** (`BND-04`). `Disposition::of` reads exactly one field — which context was running. It never sees the error code, the faulting address, or the faulting `RIP`; `FaultReport` does not even carry the frame, so a future policy arm cannot casually reach for it. A host test pins this: the same context yields the same disposition for vectors 0, 6, 8, 13, 14, 255 and `u64::MAX`.

**A terminated task is abandoned, not unwound.** With no IST (that is `STORY-P1-02-02`), a same-privilege fault runs the handler on the victim's own stack. The handler marks the task `Finished` and switches to the supervisor context, abandoning the victim's stack and its half-executed frame — sound precisely because that context is never resumed.

**The spoor carries no address and no error code.** `PD-12` scopes a fault record to class/actor/action/outcome; an audit atom is not a debugging channel. A host test pins the payload to exactly the task index and the vector.

## What this Report does not establish

- **No double-fault survival.** A fault inside the fault handler still triple-faults; no TSS/IST exists. `STORY-P1-02-02`.
- **No hardware tier.** Tier 0 QEMU only — and this Story produced fresh evidence for why that matters (the `wrmsr` finding). `LE-09` stays open.
- **No privilege boundary.** Everything runs at CPL 0 in one identity-mapped address space. "The fault happened in a task" means *which context the kernel had switched into*, not a hardware ring transition. `FEAT-P1-03`'s charge.
- **No fault-latency baseline**, which `FEAT-P1-02`'s exit criteria ask for. The handler is not on a measured path yet; wiring it into `fixture_measure` is named follow-on work rather than quietly dropped.
- **No `PERF-D02` guardrail closes.**

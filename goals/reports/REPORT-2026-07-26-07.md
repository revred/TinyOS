# REPORT-2026-07-26-07

**Test(s) covered:** `TEST-P0-05-01-A` (`STORY-P0-05-01` — PE64 image parsing into a validated, typed `LoadDescriptor`).

**Result:** **Pass.** `cargo test -p exec --lib` runs 14 tests, all passing, in the new `os/src/exec/` crate (`src/pe.rs`):

- `parses_a_well_formed_image` — a hand-crafted, well-formed PE32+ image (one `.text`, R+X section; one import descriptor for `MYDLL.DLL`'s `MySymbol`) parses into a `LoadDescriptor` whose entry point, image base, section permissions, and import list match what was encoded — acceptance criterion 1 (well-formed case) and criterion 3 (import list).
- `parsing_is_deterministic` — parsing the same bytes twice yields identical `entry_point_rva`/`image_base`/sections/imports — `TEST-P0-05-01-A`'s determinism bullet.
- `rejects_missing_dos_signature`, `rejects_missing_pe_signature`, `rejects_non_amd64_machine` — malformed signature/machine fields are rejected with typed `PeError` variants, never a panic.
- `rejects_truncated_header`, `rejects_truncated_section_table` — a file cut off mid-COFF-header or mid-section-entry is rejected (`PeError::Truncated`/`SectionTableOutOfBounds`), never read past its own end — acceptance criterion 1 (truncation) and `TEST-P0-05-01-A`'s truncation bullets.
- `rejects_section_data_past_end_of_file` — a section whose declared file offset + size exceeds the actual file length is rejected (`PeError::SectionDataOutOfBounds`) without touching the file's real length — `TEST-P0-05-01-A`'s out-of-bounds-section bullet.
- `rejects_write_and_execute_section` — a section characteristics field requesting both write and execute is rejected at parse time (`PeError::WriteExecuteSection`), even though every other field is well-formed — acceptance criterion 2 (W^X enforcement).
- `rejects_more_sections_than_capacity`, `rejects_more_imports_than_capacity` — a `LoadDescriptor<0, _>`/`LoadDescriptor<_, 0>` capacity of zero fails closed (`TooManySections`/`TooManyImports`) rather than growing storage, mirroring `hal::topology::Topology<N>`'s fixed-capacity contract.
- `read_c_string_rejects_name_exceeding_capacity`, `read_c_string_rejects_missing_terminator` — the internal NUL-terminated-string reader fails closed (`NameTooLong`/`NameOutOfBounds`) rather than truncating or reading past the file.
- `no_truncation_length_panics` — every one of the well-formed image's ~300 possible truncation lengths (0 through its full length minus one) is parsed and asserted to return `Err`, never a panic; only the full length parses successfully. A lightweight stand-in for `cargo-fuzz` (not yet set up anywhere in this repo — see "Deliberately not done" below) over the truncation dimension specifically, per `agent/CODING_STANDARDS.md`'s adversarial-input-parser requirement.

**Deliberately not done:**

- **No real `blue-sharc.exe` fixture bytes.** Per Handover 11's open decision (vendor vs. build-from-sibling-project), sourcing the real binary is still deferred to `STORY-P0-05-04`; this Story's acceptance criterion 4 ("ideally, real bytes from a `blue-sharc.exe` build") is satisfied only by the hand-crafted fixture in `parses_a_well_formed_image`, not a real-binary comparison against `objdump`/`llvm-readobj` output. `TEST-P0-05-01-A`'s own spec explicitly allows this ("Given... either a hand-crafted fixture, or real bytes").
- **No `cargo-fuzz` harness.** The repo has no existing fuzz-target precedent to mirror (confirmed absent workspace-wide before this Story), and setting one up is a standalone infrastructure decision, not scoped to this Story's acceptance criteria. `no_truncation_length_panics` covers the truncation dimension exhaustively (every prefix length of the one fixture) as an interim substitute; it does not exercise arbitrary byte-level mutations (flipped bits, arbitrary field corruption) the way a real fuzzer would. Recorded here as a gap for whoever next hardens this module, not silently left uncovered.
- **Ordinal-only imports are not recorded.** A thunk with `IMAGE_ORDINAL_FLAG64` set (import-by-ordinal rather than by name) is skipped rather than represented in `LoadDescriptor::imports()` — documented inline on `IMAGE_ORDINAL_FLAG64`'s doc comment. `blue-sharc.exe`'s own import table is expected to be name-based (its build target per `ADR 0002` is `rust-lld`/`cargo-xwin`, which emit by-name imports for CRT/Win32 calls), so this is not expected to hide any of that binary's real imports; it is a real scope limitation for a hypothetical ordinal-importing binary, worth revisiting if `STORY-P0-05-04` ever encounters one.

**Implementation note:** `LoadDescriptor<const SECTIONS: usize, const IMPORTS: usize>` and `FixedBytes<const N: usize>` (a fixed-capacity byte buffer standing in for a bounded `String` in `no_std`) both follow the same caller-chosen-capacity pattern `hal::topology::Topology<N>` and `kernel::mem::Pool<T, N>` already established — a file declaring more sections, imports, or a longer name than the caller's chosen bound fails closed with a typed error rather than growing unbounded storage, consistent with the RT/no-heap-allocation discipline in `agent/CODING_STANDARDS.md`. RVA-to-file-offset translation (`rva_to_file_offset`) uses `max(virtual_size, file_size)` as a section's mapped extent, matching real PE loaders' tolerance of headers where the two disagree (common in optimized/aligned builds). Only PE32+ (64-bit) images are supported; a 32-bit `PE32` image (different optional-header layout entirely) is rejected via `PeError::NotPe32Plus` rather than partially parsed, since every Goal this Feature targets (`G-PC-1`..`G-PC-4`) and the flagship validation case (`blue-sharc.exe`) are 64-bit-only.

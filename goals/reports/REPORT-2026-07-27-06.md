## The Tier 0 evidence, verbatim

```
fixture-double-fault ist stack 0x11f090..0x123090 installed_top=0x123090
fixture-double-fault switching into the stack destroyer (slot 0)
fixture-double-fault captured #DF vector=8 error_code=0x0 rip=0x10349e faulting_rsp=0x8000000000
fixture-double-fault handler_rsp=0x122d58 ist_stack=0x11f090..0x123090 on_ist_stack=true
fixture-double-fault double_fault_spoors=2 attributed_to_task=true terminal=true
TINYOS-RESULT/1 fixture=double-fault ok=true
```

Two numbers carry the whole claim. `faulting_rsp=0x8000000000` is exactly 512 GiB — the unmapped address the victim installed as its stack pointer, so the fault demonstrably originated from the destroyed stack and not from somewhere incidental. `handler_rsp=0x122d58` lies inside `0x11f090..0x123090`, the reserved `#DF` stack: the CPU loaded `RSP` from the TSS before it pushed anything. `installed_top` is read back out of the installed TSS rather than recomputed, so it says what the hardware was told, not what the code intended to tell it.

Everything else is corroboration: `error_code=0x0` is `#DF`'s architecturally fixed value, `double_fault_spoors=2` is the audit pair in the journal, and `attributed_to_task=true` is the escalation being credited to the task that started it. The verdict rides `STORY-P1-01-02`'s `TINYOS-RESULT/1` line — the Pi 5's future pass/fail channel getting its third user.

## The contrast, observed rather than assumed

"It passes now" is not evidence that the IST is what made it pass. So the same fixture was run with vector 8's gate changed from `set_handler_with_ist` to `set_handler` — one line, nothing else touched — under `qemu -d int,cpu_reset`:

```
     0: v=0e e=0002 i=0 cpl=0 IP=0008:000000000010349e SP=0010:0000008000000000 CR2=0000007ffffffff8
check_exception old: 0xe new 0xe
     1: v=08 e=0000 i=0 cpl=0 IP=0008:000000000010349e SP=0010:0000008000000000
check_exception old: 0x8 new 0xe
Triple fault
```

That is the entire escalation in five lines: `#PF` on the push (`CR2` is `0x7ffffffff8`, eight bytes below the destroyed `RSP` — the push target), `#PF` again while delivering it, so `#DF`; then `#PF` a third time while delivering *that*, and the CPU gives up. Serial output stops after `switching into the stack destroyer`. QEMU exits **0** — not the success debug-exit code 33, not the failure code 35, but a reset — so `xtask` reports a harness error rather than a kernel verdict.

This is what `LE-04` has meant since Handover 32, and it is why nothing softer than an IST could close it. `RIP` in both frames is `0x10349e`, the victim's `push` — the same instruction that produced a clean, reported `#DF` two paragraphs above.

## Design decisions worth stating

**The GDT is additive, and that is what makes it safe.** The new table repeats `boot.rs`'s null/code/data descriptors byte for byte and appends the TSS descriptor after them. Because entries 0–2 are unchanged, no segment register is reloaded: no far return through a hand-built stack frame to reload `CS`, no window in which the code segment is undefined. A host test asserts the three quadwords against `boot.rs`'s values, so the two copies drifting apart is a test failure rather than a mystery triple fault — they cannot be shared, since `boot.rs`'s copy has to be a compile-time constant inside 32-bit `global_asm!` that runs before any Rust does.

**There is no `DoubleFaultDisposition`, for the same reason there is no `Resume`.** `Disposition::of` is not called, not extended, and did not gain a vector-dependent branch — its load-bearing invariant is that it reads exactly one field, which context was running, and a `match` on the vector would have ended that for the one vector where the answer was never in doubt. A double fault means the primary path failed *while the CPU was delivering a fault*; there is no arm to choose between, because the machinery that would do the containing is what just broke. An enumeration with one variant is a decision that isn't one. `STORY-P1-02-01`'s existing test `the_vector_is_recorded_but_never_changes_the_decision` passes unmodified, and a new test asserts that vector 8 reaches the same disposition as vector 14 — precisely because nothing routes it there.

**The audit attributes but never claims containment.** `audit_double_fault` carries the faulting context so an auditor can see which task was running, and stamps `Outcome::Failed` on the disposition spoor in **both** contexts. A host test pins that: a double fault inside a task is not a contained fault and must never audit as one. Neither spoor carries an address, an error code or register content (`PD-12`), exactly as the primary path's do not.

**One IST slot, not seven.** `#MC` (vector 18) is the obvious second consumer and is deliberately unwired: there is no Tier 0 way to raise a machine check, so wiring it would put unexercised memory and an unexercised gate in a fault path — the same argument `STORY-P1-02-01` used to refuse an unreachable resume arm. A host test asserts `populated_interrupt_stacks() == 1`.

**The safety net is on the real boot path, not only in the fixture that tests it.** Both `init_faults_only` and `init` install the GDT and TSS before touching the IDT. A net wired only where it is measured is theater, and `LE-04` was never a fixture-only problem.

## The coupling this Story had to remove

`STORY-P1-02-01`'s `#GP` victim loaded selector `0x18` *because* `boot.rs`'s GDT held exactly three descriptors, and its own Handover flagged that growing the GDT would change that fixture. It would have — index 3 is exactly where the TSS descriptor now sits, so the victim would have silently become a TSS-selector load: still a `#GP`, but for a different reason, with a different error code, and nothing would have said so.

The victim now uses index 511 (`0xFF8`), far past any GDT this kernel will plausibly install, and the constant's own doc comment records why. A fixture that picks a value by counting the things that happen to exist today is a fixture that breaks the next time one is added; the fix is to stop counting.

One knock-on worth recording: `Gdt` is aligned to 8, not 16 like `Idt`. At 40 bytes, a 16-byte alignment would round `size_of` up to 48, and the limit derived from it would advertise eight bytes of tail padding as a sixth descriptor slot — turning an out-of-range selector into a zeroed one, which is a quieter failure than the `#GP` hardware should raise. Caught by the descriptor-placement host test, not by reasoning.

What this Story *does* have, which the last one did not, is a **recorded, deliberate Red at Tier 0**: the fixture was built and run with the IST removed and nothing else changed, the triple fault was captured under `-d int,cpu_reset`, and the transcript is above. ## A side effect: every fixture feature now passes target clippy

`LE-12` says CI's clippy never lints target-only fixture code. Verifying this Story meant building the kernel binary against the real `x86_64-tinyos` target, which made running clippy there nearly free — so it was run once per fixture feature, and the debt turned out to be concrete rather than theoretical: **`fixture-context-switch` (7 lints), `fixture-fault` (7) and this Story's own `fixture-double-fault` (3)** all failed `-D warnings`.

All of them were the same thing: `&mut *(&raw mut STATIC)`, this workspace's single-owner `static mut` pattern, which clippy wants simplified to `&mut STATIC` — precisely the `static_mut_refs` the raw-pointer form exists to avoid. `hal_x86_64::interrupts::init` has carried the matching allow since `STORY-P0-04-02`; the fixtures had simply never been linted, so nobody had added it. One genuine simplification was taken rather than allowed (a `match` on `faulting_address()` became `unwrap_or(0)`, keeping its comment).

Every fixture feature of `kernel`, plus `exec`'s fixture binaries, now passes `-D warnings` against the real target. `LE-12` is **not** closed by that: the CI job still does not run these passes, so the property is true today and unenforced tomorrow. What changed is that closing it is now a wiring job with a clean starting point rather than a cleanup of unknown size.

## The timing gate did not pass on this host, and this Story is not why

Stated plainly rather than omitted. `check-timing-regression` was run five times during this session's verification and failed every time — but on a **different set of metrics each time**, and with the count of regressed statistics climbing monotonically (2 → 4 → 6) as the session's own QEMU boots loaded the machine:

```
attempt 1   D07/pool_u64x64_alloc_free_round_trip   p50  baseline=70   observed=138  limit=112
attempt 2   + D04/context_switch_yield_roundtrip    p50  baseline=226  observed=402  limit=361
attempt 3   + D05/dispatch_select_highest_priority  p50  baseline=76   observed=148  limit=121
```

Three reasons this is host noise and not a regression this Story introduced:

1. **The measured binary never executes any code this Story touched.** `fixture_measure` installs **no IDT at all** — it calls `interrupts::remap_and_mask_pic` and nothing else from that module (its own source says so, and says why). The GDT, the TSS, the `ltr`, the IST-backed gate and the `#DF` stub are all unreachable from it; the IST stack static is not referenced, so `--gc-sections` drops it.
2. **The regressing metrics have nothing in common with the change.** `D07/pool_u64x64_alloc_free_round_trip` is pure `kernel::mem::Pool`, untouched by this Story, and it is the one that fails most often.
3. **The direction is not stable.** In the same session `D05/dispatch_run_once_cooperative_round` measured *below* its baseline (384 and 398 against 420/446) while other metrics measured 2× above theirs. A code regression does not make one metric faster and another slower on alternate runs.

A clean A/B against the pre-change tree was attempted and could not be completed: `check-timing-regression` and the `measure`/`write_result` harness it depends on are themselves uncommitted work from `STORY-P1-01-02`, so stashing this session's source changes also removes the gate.

The honest reading is that the committed baselines were recorded on a quieter machine than this one, and Tier 0 (QEMU/TCG) cycle counts on a loaded Windows host drift further than the gate's 60% tolerance allows. That is `LE-16` ("the gate can only detect regressions of ~1.6× or worse") seen from the other side: ambient noise on a busy host is now *larger* than the gate's own tolerance, so the gate is not merely blunt, it is host-condition-sensitive. Recorded as **`LE-18`** rather than fixed by loosening the tolerance or re-recording baselines from a noisy machine — either of those would make the gate quieter without making it better.

CI runs this gate on a GitHub runner against the same baselines, which is a separate question this session has no evidence about.

## What this Report does not establish

- **No hardware tier.** Tier 0 QEMU only, and `STORY-P1-02-01`'s finding applies here with full force: a Tier 0 fixture can only check what the *emulator* does. QEMU's escalation behavior matched the architecture this time; that is an observation, not a guarantee. `LE-09` stays open.
- **No `#MC` survival.** Vector 18 has no IST and keeps the shared fail-closed default, deliberately.
- **No triple-fault survival.** A fault inside the `#DF` handler itself is the end of the chain. "Terminal but reporting" is the whole claim.
- **No privilege boundary.** `RSP0` is zero and unused; everything is still CPL 0 in one identity-mapped address space.
- **No fault-latency baseline** (`LE-17`), which `FEAT-P1-02`'s exit criteria require. Both of the Feature's Stories are now functionally Verified and it still cannot exit.
- **No `PERF-D02` guardrail closes.**

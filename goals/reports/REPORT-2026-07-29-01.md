## The finding

`LE-40` named one `.expect` and was explicit that it was **not** the TOCTOU it had originally been reported as. That analysis is correct and is unchanged by this Story: `owner_space` is held under a shared borrow on a single core, so the re-read cannot diverge today.

Auditing the whole function for the same *defect class* found a second instance that the row had not described, and it is worse than the one it had:

```text
thread 'shared_memory::tests::a_grant_whose_sharee_range_overflows_the_address_space_is_rejected'
panicked at src\exec\src\shared_memory.rs:228:35:
attempt to add with overflow
```

`grant` computed every page address with unchecked `+` and `*` on **caller-chosen** values. The request that produces the line above is well-formed by every check that existed: two legitimately-mapped owner pages, and a `sharee_virt` of `0xFFFF_FFFF_FFFF_F000` — page-aligned, so the alignment check passes it, and far above `KERNEL_RESERVED_REGION_END`, so the kernel-collision check passes it. The second page's address then overflows.

Two things make this materially different from the `.expect`:

- **It is reachable today.** Single core, no shared page directory, no SMP. The `.expect` is not.
- **The release build is worse than the debug build.** `os/Cargo.toml` sets no `overflow-checks` for `[profile.release]`, so it takes Cargo's default of **off**: there is no panic, the address wraps silently to `0x0000_0000_0000_0000`, and the wrapped value is *never re-checked against `KERNEL_RESERVED_REGION_END`* because the function is already past that check by the time it computes the address. A safety defect in debug becomes a containment defect in release.

And the debug disposition is not mild either: both profiles set `panic = "abort"`. A panic here is not an unwind the caller could contain — it is a whole-system abort, on a path whose entire contract is to be transactional.

## What changed

**One grantability verdict.** *Is this owner page mapped?* and *does it carry the authority the sharee asked for?* are now answered by one function that both owner-facing loops call. The mapping loop previously re-read the translation, `.expect`ed its presence, and re-checked its permissions **not at all** — so under either condition `LE-40` names as invalidating the re-read, the presence half panicked while the permission half would have mapped the page anyway. The privilege-escalating half was the unguarded one; that asymmetry is the substantive part of the fix, not the panic removal.

**A range check before any page is inspected**, returning a new `SharedMemoryError::RangeOverflow`, covering `owner_virt`, `sharee_virt` and `pages`. Checked once up front rather than per iteration, so the loops keep plain arithmetic — against an invariant now stated in the comment that establishes it, which is exactly what `LE-40` faulted the old code for not doing.

**A generation counter that refuses to wrap or saturate.** It is the whole basis of `StaleGrant`: a wrapped counter lets a stale token match a later grant, and a saturated one gives every subsequent grant the same generation. An exhausted counter is `RegistryExhausted`, with the mapping rolled back.

**`revoke` inherits rather than re-derives.** `grant` is `SharedGrant`'s only constructor, so a token that exists describes a representable range. Recorded as a documented invariant on the type — a check that cannot fail is dead code, and dead code on a kernel path reads like a real guard.

## The falsification: the gate fires on the pre-fix source

Per `ADR 0005` and `STORY-P0-01-07` clause 2, an instrument never shown to detect anything cannot be believed when it reports a pass. All four new failure-mode tests were run against the pre-fix source first:

```text
---- this_modules_non_test_source_contains_no_panic_constructs ----
`.expect(` on this module's non-test path, line 262: `grant` is a kernel path and
`agent/CODING_STANDARDS.md` puts fail-safe above keep-trying (LE-40)

---- a_grant_whose_sharee_range_overflows_the_address_space_is_rejected ----
panicked at src\exec\src\shared_memory.rs:228:35: attempt to add with overflow

---- a_grant_whose_owner_range_overflows_the_address_space_is_rejected ----
  left: Some(RegionNotOwned)   right: Some(RangeOverflow)

---- a_grant_whose_page_count_overflows_the_address_space_is_rejected ----
  left: Some(RegionNotOwned)   right: Some(RangeOverflow)

test result: FAILED. 14 passed; 4 failed
```

The last two are worth reading as more than a mismatched enum: before this Story a nonsense `pages` count was rejected only *incidentally*, by whichever unmapped page the loop happened to reach first. Being rejected for the wrong reason is how a request that overflows on a fully-mapped region gets through.

## What this does not establish

- **That SMP is safe.** One precondition is removed, for one function. `LE-40`'s "before any SMP work" ordering constraint is satisfied here and nowhere else.
- **That the rest of the kernel fails closed.** The source gate covers one module. `LE-52` carries the generalisation, and names the reason it is not a one-liner: the explicit half is a mechanical clippy sweep, the implicit half (`overflow-checks` in release) is a per-subsystem judgement about whether a panic is genuinely safer than a wrap.
- **Absence of implicit panics in this module.** The gate catches explicit constructs only. The reachable defect above was an unchecked `+`, not an `.expect` — which is precisely why `LE-52` says a field-count-shaped gate is not sufficient here either.
- **Any timing claim.** Nothing was measured.

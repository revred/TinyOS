# REPORT-2026-07-28-06 — `STORY-P1-01-04`: the timing gate stops measuring the runner

**Test(s) covered:** `TEST-P1-01-04-A` (`STORY-P1-01-04` — a timing gate whose verdict is about the code), performance domains `D02`/`D04`/`D05`/`D07`, mapped `SEC-19`/`SEC-20`, containment classes `C0`/`C1`.

**Result: Pass, with one pre-committed acceptance bound recorded as failed.** The gate now compares each metric's same-run ratio to a fixed reference workload instead of an absolute cycle count. It is green on a runner measured **2.24x slower** than the one that recorded the baseline — the exact condition that has been failing `main` for five sessions — and still exits 1 naming the injected regression, on both a quiet and a loaded host. `TEST-P1-01-04-A` clause 4's ≥3x bound was **not** met (1.41x–2.28x measured); §Calibration records it and what the same data did support. `LE-16` and `LE-18` are addressed and restated rather than closed. `STORY-P1-01-04`'s assurance state is `baseline-debt`.

`main`'s `check-timing-regression` step had been red for five sessions. The evidence that settles what it was measuring, from CI runs `30274004446` and `30274317558` (Handover 10): the second commit changed **one markdown file and not one byte of code**, so the binaries were identical, and every gated metric moved together by 1.8–2.2x. `D05/dispatch_select_highest_priority_ready` went 90 → 182 against a limit of 121 and reported `REGRESSED`.

The gate was reporting how fast the runner was.

## The reference workload, and the draft that was falsified in one run

The gate needs a denominator no gated code path can move. `kernel::fixture_measure::phase_reference_loop` is a fixed integer recurrence touching no scheduler, pool, context switch, fault path or allocation, measured through the same `Stopwatch`/`Calibration`/`Samples`/`summarize` path as everything else.

The first draft placed `black_box` on the loop's input and result only. It measured **16 cycles** — smaller than most of the metrics it exists to normalise:

```text
REF  fixed_integer_loop  n=1000 dropped=0 p50=16 p99=20 p99.9=22 max=36 (cycles)
```

The release profile had unrolled 64 iterations and closed-formed the entire recurrence into a single multiply-add. With the barrier moved **inside** the loop, forcing a genuine dependent chain:

```text
REF  fixed_integer_loop  n=1000 dropped=0 p50=650 p99=660 p99.9=664 max=728 (cycles)
```

A reference that optimises to nothing divides every ratio by quantisation noise. This is recorded at the function's definition, alongside the instruction not to edit it.

## Calibration, against clause 4's pre-committed bound

Ten release-profile runs: five on a quiet host, five with 14 spinner processes on a 16-core box. Reference p50 across the ten runs spanned **538–1274 cycles (2.37x)**, so the intended condition was achieved.

**Clause 4's bound was: ratio spread must be ≥3x tighter than absolute spread. It failed.** Measured across six simulated `--runs=3` gate invocations (every consecutive 3-run window within each condition), using the median-across-runs statistic the gate actually compares:

| Metric | abs swing | ratio swing | tighter by |
|---|---|---|---|
| `D07/pool_u64x64_alloc_free_round_trip` | ∞ (median 0 cycles) | ∞ | — |
| `D07/pool_u64x4_alloc_denied_exhausted` | 4.18x | 1.83x | 2.28x |
| `D05/dispatch_select_highest_priority_ready` | 3.06x | 1.77x | 1.73x |
| `D02/fault_ud2_capture_terminate_kernel_context` | 2.49x | 1.24x | 2.00x |
| `D05/dispatch_run_once_cooperative_round` | 2.50x | 1.33x | 1.89x |
| `D04/context_switch_yield_roundtrip_2switches` | 1.72x | 1.22x | 1.41x |

**An analysis error worth recording.** The first pass at this table measured spread across *individual runs* and concluded the design should be narrowed to three metrics. The gate never compares an individual run — it compares the median across an invocation. Recomputed with the gate's own statistic, the same raw data supports gating five of six. Analysing a gate with a statistic the gate does not use produces a conclusion about nothing, which is the same error this Story exists to fix, one level up.

## The tolerance, and why it is a looser number than before

The excursion the gate must actually absorb is a **quiet-host baseline compared against a loaded-host observation**:

| Metric | worst excursion |
|---|---|
| `D05/dispatch_select_highest_priority_ready` | **+62%** |
| `D07/pool_u64x4_alloc_denied_exhausted` | +55% |
| `D05/dispatch_run_once_cooperative_round` | +26% |
| `D02/fault_ud2_capture_terminate_kernel_context` | +9% |
| `D04/context_switch_yield_roundtrip_2switches` | improves |

Committed: **100% relative, 20,000 ppm floor** — clearing the worst by 38 points. `REFERENCE_TOLERANCE` is **300%** (a 4x band) on the reference's absolute cycles, against the 2.2x worst swing recorded between identical binaries; it is a tripwire for the reference having stopped being the reference, not a regression check. Both bounds are `const _: () = assert!(...)` so the compiler holds them, not a test that might not run.

**100% is nominally looser than `STORY-P1-01-02`'s 60% and is a better gate.** That 60% was applied to absolutes measured swinging up to +318% on unchanged code, so it was not a 1.6x detector; it was a coin toss that had been red for five sessions. This one contains every excursion the calibration produced.

## One metric withheld

`D07/pool_u64x64_alloc_free_round_trip` medians to **0 cycles** — the operation costs less than the calibrated `rdtsc` overhead subtracted from it. It is listed in `gate::UNGATED_AT_TIER0` with that reason, printed on every run, still measured, still baselined, still subject to every fail-closed check. Only the verdict is withheld. The set is in source and pinned by test rather than being a column in the baseline TSV: moving a metric out of a gate should require editing code with a reason attached.

## Green — the four-quadrant demonstration

Baseline re-recorded over five quiet runs (`--update-baseline --date=2026-07-28`), reference at `min=454 p50=572`.

| Host | Code | Reference p50 | Result |
|---|---|---|---|
| quiet | unchanged | 532 | **exit 0** — no regression across 12 gated statistics (2 reported without a verdict) |
| loaded | unchanged | **1284** (2.24x) | **exit 0** |
| quiet | `--inject-regression` | 678 | **exit 1** — `D05/dispatch_select` min 197,761 → 2,223,255 ppm, limit 395,522 |
| loaded | `--inject-regression` | **1230** (2.15x) | **exit 1** — `D05/dispatch_select` min 197,761 → 2,205,314 ppm, limit 395,522 |

Row 2 is the failure `main` has carried since `91c95c1`. Rows 3 and 4 are the proof it was not achieved by blinding the gate: the regression's observed ratio under load is **within 1%** of its value measured quiet, while the absolute cycle count for the same statistic moved 936 → 1826.

### What these four rows do not establish

**They vary load on one machine. They say nothing about a second machine**, and the distinction is not pedantic — it is exactly `LE-23`.

Ratio invariance holds when the runner scales all work by a common factor, which host load largely does. **A different microarchitecture need not.** The reference is a dependent integer-multiply chain and is ALU-bound; `D05/dispatch_select_highest_priority_ready` walks a ready queue and is memory- and branch-bound. A host that scales ALU throughput and memory latency differently — a different CPU generation, a different TCG version, a different cache hierarchy — shifts that ratio with no regression present, and this gate would report it as one.

So the premise is **proven against load and unproven against hardware, with a named mechanism for it to fail.** A systematic cross-host ratio shift is the outcome to be ruled out, not the surprise case. The metrics most exposed are the ones whose work differs most in kind from the reference's; the metrics least exposed are `D05/dispatch_run_once` and `D04/context_switch`, which are the closest to it in both magnitude and composition.

### Addendum: the first cross-host run, and what it settled

CI run `30294647525` on `22c269f` — **green on every job**, and the first fully green run in five sessions. It is also the first datum against `LE-23`, and it confirms the concern rather than dismissing it.

Reference: **572 cycles (Windows baseline) → 441 (Linux CI)**. Per-metric p50, baseline → observed:

| Metric | ratio shift | absolute shift |
|---|---|---|
| `D05/dispatch_select_highest_priority_ready` | **+80%** (limit +100%) | 112 → 155 |
| `D07/pool_u64x4_alloc_denied_exhausted` | +25% | 26 → 25 |
| `D04/context_switch_yield_roundtrip_2switches` | −23% | 332 → 207 |
| `D05/dispatch_run_once_cooperative_round` | −40% | 438 → 259 |
| `D02/fault_ud2_capture_terminate_kernel_context` | −46% | 1174 → 467 |

A **second** run (`30294872213`, `0e0fd50`, reference p50 = 510) separates two effects that the first run alone conflated:

| Metric | run 1 | run 2 |
|---|---|---|
| `D05/dispatch_select_highest_priority_ready` | +80% | +4.4% |
| `D04/context_switch_yield_roundtrip_2switches` | −23% | −37% |
| `D05/dispatch_run_once_cooperative_round` | −40% | −53% |
| `D02/fault_ud2_capture_terminate_kernel_context` | −46% | −50% |

- **A real, consistently-signed cross-host offset.** `D04`, `D05/dispatch_run_once` and `D02` read **23–53% below** their Windows baseline in both runs, and two tripped `improved (is the baseline stale?)` in run 2 — the gate correctly reporting a baseline from the wrong machine. `LE-23` confirmed; the fix is to re-record from CI.
- **A separate run-to-run instability on `D05/dispatch_select`**, +80% → +4.4% on unchanged code. That is `LE-18` surviving *inside* the ratio at smaller amplitude, on this gate's perennially least-headroom metric. The **100% tolerance is what absorbed it**; at the 60% first drafted, run 1 would have gone red.

**A claim made from run 1 alone, corrected here because the error is the instructive part**: run 1 was read as showing ratios shift cross-host as much as absolutes do (3.36x vs 3.45x spread). Run 2 shows most of that spread was the second effect, not the first. **One run is not a measurement** — which is this Story's own thesis, very nearly missed one level up for the second time.

One unexpected improvement: `D07/pool_u64x64_alloc_free_round_trip` measured **25 cycles on CI**, not 0. `LE-24` is a property of the Windows host's overhead calibration, not of the metric — on the Linux runner it is gateable. That binds `LE-24` to `LE-23` as one piece of work.

## The residual sensitivity, stated sharply

At Tier 0 this gate catches ratio regressions of roughly **2x or worse**, down from `STORY-P1-01-02`'s nominal 1.6x. Put in the form that matters: **a real 50% regression on a gated path passes this gate.** That is the honest cost of a tolerance wide enough to contain the measured noise, it is not improvable by any Tier 0 work, and it is `LE-09`-gated. The previous 1.6x was not a better trade — it was noise with a number on it — but it should not be pretended that nothing was given up.

## What this does not establish

- **No hardware tier.** Every number is Tier 0 QEMU/TCG. `LE-09` stays open, and a ratio closes no `PERF-D*` microsecond guardrail.
- **No defence against a uniform slowdown of everything**, reference included. Deliberate, and the price of row 2. The reference is a fixed integer computation no kernel change can move, so the realistic hazard is a toolchain change, and the 4x structural band is what watches for it.
- **The ratios have never met a second machine.** They were recorded on a Windows dev host. Ratios should transfer where absolutes could not; that is this Story's central untested claim, the four rows above do **not** test it, and §"What these four rows do not establish" names the mechanism by which it can fail (`LE-23`).
- **`LE-16` is restated, not closed.** Roughly 2x-or-worse at Tier 0 — a real 50% regression passes.

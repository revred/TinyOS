# REPORT-2026-07-27-01

**Test(s) covered:** `TEST-P0-03-01-A` (`STORY-P0-03-01` - `Pool<T,N>` bounded-capacity allocator), `PERF-D07` release guardrails `G01`-`G23`, mapped `SEC-03`/`SEC-19`/`SEC-20`, mapped `BND-04`/`BND-15`/`BND-20`.

**Result: Partial - one guardrail genuinely closed, two correctly N/A-debt, the rest either not attempted or gathered-but-not-passing/unverifiable against `goals/performance/catalogue.tsv`'s numeric targets. `STORY-P0-03-01` stays `baseline-debt` (unchanged) - not `verified` - both because `G22` (72-hour soak) has not run and because the majority of the other 22 guardrails do not yet close either.**

This Report consolidates a four-part assurance-evidence effort run earlier this session (a measurement design plan, a Host-tier diagnostic harness added to `os/src/kernel/src/mem.rs`, a real Tier-0 QEMU fixture added at `os/src/kernel/src/fixture_pool_bench.rs` plus a new `os/src/hal-x86_64/src/serial.rs` COM1 driver, and a SEC/BND boundary-evidence mapping) and an independent adversarial verification pass over all of it. The adversarial pass found no fabricated numbers, but found that every one of the first three sub-reports tagged raw data with guardrail IDs without ever checking that data against `catalogue.tsv`'s actual numeric thresholds - creating a false impression of broad "coverage." This Report corrects that: every guardrail below is scored against its real numeric target, not just "was some cycle count printed with this ID next to it."

## What was actually run (real commands, this effort)

- `cargo test -p kernel --lib -- --nocapture` (Host) - 66/66 passing. Added 6 new `#[cfg(test)]` diagnostic functions to `mem.rs` (`perf_pool_u64x64_alloc_free_round_trip_host_diagnostic`, `perf_pool_u64x64_million_op_tail_host_diagnostic`, `perf_pool_u64x64_occupancy_pattern_host_diagnostic`, `perf_pool_u64x64_denial_paths_host_diagnostic`, `perf_pool_exhaustion_drain_cycles_drop_accounting`, `perf_pool_u64x64_size_of_host_diagnostic`) plus RDTSC/`Instant`-based helpers. No production code in `mem.rs` was touched.
- 5 independent host-process re-runs of the alloc/free round-trip test, for run-to-run jitter (`G05`).
- `grep -rn "global_allocator\|GlobalAlloc" os/src/kernel/src/` - zero matches (categorical no-heap-allocator evidence, `G11`).
- New Tier-0 fixture: `os/src/kernel/src/fixture_pool_bench.rs` (`fixture-pool-bench` Cargo feature, wired into `os/src/xtask/src/main.rs`'s `qemu_x86_64` match arm as `--fixture=pool-bench`), driving `kernel::mem::Pool` through the same operation shapes as the Host harness, each phase in its own `#[inline(never)]` function (a real stack-overflow/triple-fault was hit and fixed by this split), reporting cycle percentiles over a new polled COM1 UART driver (`os/src/hal-x86_64/src/serial.rs`, SAFETY-commented `inb`/`outb`), with a final pass/fail bit via `isa-debug-exit`.
- `cargo run -p xtask -- qemu-x86_64 --fixture=pool-bench` -> exit 0 (isa-debug-exit Success); direct QEMU invocation with `-serial file:` to capture the numeric serial log (`c:\tmp\pool_bench_serial.log`).
- Full 11-fixture QEMU regression sweep (default boot, `broken-boot`, `context-switch`, `address-space`, `win32-shim`, `blue-sharc`, `blue-sharc-broken`, `shared-memory`, `idt-apic-timer`, `idt-apic-unrouted`, `pool-bench`) - no regressions, every fixture's documented exit code unchanged.
- `cargo clippy -p kernel --lib -- -D warnings`, `cargo clippy --workspace --lib -- -D warnings`, `cargo fmt --check` - all clean.
- SAFETY-comment audit: all 6 `unsafe` sites in `mem.rs` (2 more added by the new host diagnostics: an `_rdtsc()` call and a byte-for-byte snapshot read) carry a `// SAFETY:` comment.
- An independent adversarial verification pass re-ran essentially all of the above from a clean invocation, reproduced the same order-of-magnitude numbers (host-process noise means exact digits differ run-to-run, consistent with the harness's own "diagnostic, noisy host" caveat), confirmed no fabrication, confirmed `story-contracts.tsv`'s `STORY-P0-03-01` row was never touched, and then did the threshold arithmetic none of the three prior sub-reports had done.

**Deliberately not done:**

- **No behavioral verification that priority inheritance actually prevents starvation under live scheduling.** This kernel has no ready-queue/priority-based dispatch loop yet (`kernel::context::switch` is a raw two-context primitive invoked explicitly by its caller, not an autonomous scheduler) — so there is no live "medium preempts low" scenario to run at all, on any tier. This Story verifies the bookkeeping half exhaustively (a contended lock boosts the holder; release restores it deterministically) but the behavioral half needs a real dispatcher, named as a concrete, still-open prerequisite in `STORY-P0-02-03.md`'s scope-resolution note and this session's handover, not silently assumed solved.
- **No blocking/parking of a contending waiter.** `PriorityInheritingLock::try_lock` reports contention via `Err(LockError::AlreadyLocked)` rather than blocking the caller until the lock frees — actually parking a task is, again, a dispatcher responsibility this kernel doesn't have.
- **No priority-ceiling protocol implemented as an alternative** — `STORY-P0-02-03`'s description named priority inheritance "or a documented priority-ceiling equivalent"; this session implemented inheritance only, since it's the more direct match for the acceptance criteria as drafted.
- **Boost bookkeeping supports exactly one lock's worth of contention state at a time** (a single `original_priority: Option<Priority>` per `PriorityInheritingLock`) — a task holding multiple `PriorityInheritingLock`s simultaneously, each separately contended, is not covered by this Story's tests; each lock instance's bookkeeping is independent and correct in isolation, but multi-lock interaction (e.g. the deadlock-avoidance ordering real priority-inheritance protocols also need) is out of scope.

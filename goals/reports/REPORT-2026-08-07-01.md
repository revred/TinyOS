## Result

substantive sentence.** ADR 0005 requires Q1–Q4 to exist *and* a campaign whose largest observed
excursion is inside the bound being claimed; Q3's campaign has not been run. What this record holds:

## Q1 — Platform identity

Board, SoC, firmware and configuration as in the header. `config.txt` is generated by the build and
pinned by test (`os_check=0`, `kernel=kernel8.img`, `pciex4_reset=0`, `hdmi_force_hotplug=1`).
GIC-400 (GICv2), 4 implemented priority bits, confirmed on silicon (`LE-69`).

**The entry exception level, previously the register read that "needs one boot" (`LE-103`'s audit),
is now captured on the wire on two boots:**

```
TOS64-QUAL/1 boot_entry current_el=EL2 raw=0x0000000000000008 now_at=EL1 firmware_cntvoff=0x0000000000000000
```

TinyOS is entered at **EL2**, non-secure, and its own stub performs the drop to EL1 — matching the
TF-A BL31 handoff Q2 predicts (`SPSR_64(MODE_EL2, …)` in `plat/rpi/common/rpi3_common.c`, AArch32
compiled out for rpi5). The raw register value is quoted beside the decode so a wrong decode is
diagnosable from the capture alone.

**The `start*.elf`/bootcode wording gap is resolved:** ADR 0005 Q1 names "the `start*.elf`/bootcode
firmware revision" because it was written against Pi-4-era boot flow. On the Pi 5 those components
do not exist as files: "All VPU blobs have been moved into EEPROM (former start4.elf & fixup4.dat)"
(TF-A rpi5 platform documentation). The EEPROM version above is therefore the correct and complete
satisfaction of that clause on this platform. Corroborated on this bench: the netboot serve log
(2026-08-07) shows the firmware requesting `armstub8-2712.bin` — the documented user-override hook
for the EL3 stub — before falling back to its EEPROM-embedded copy.

## Q2 — The secure-world configuration, and how it was determined

**On a stock Raspberry Pi 5 booting a bare-metal `kernel8.img`, EL3 is occupied at runtime by a
resident TF-A BL31 armstub that the closed EEPROM boot firmware loads before releasing the kernel at
non-secure EL2.** The stub's source is public (github.com/raspberrypi/arm-trusted-firmware,
upstreamed as `plat/rpi/rpi5`; BL31 v2.6-lineage per the `rpi-eeprom` firmware-2712 release notes).
It installs the standard TF-A EL3 runtime vector table and services **PSCI over SMC** — the stock
`bcm2712.dtsi` carries `psci { method = "smc" }`, so EL3 is live and re-enterable at runtime, which
is **materially different from the Pi 4**, whose stock `armstub8.S` left EL3 vectorless and dead.

**What is routed to EL3 asynchronously: nothing.** The rpi5 BL31 platform setup declares the GICv2
driver with base addresses only and **no `interrupt_props`** (`plat/rpi/common/rpi4_bl31_setup.c`,
shared by rpi5), so every interrupt is configured non-secure Group 1; no SPD is built, so no secure
FIQ path exists. Only synchronous SMCs from the kernel's own execution enter EL3. TF-A's own
documentation adds that this EL3 residency confers no security: "this port isn't secure. All of the
memory used is DRAM, which is available from both the Non-secure and Secure worlds" — BCM2712 has no
secure memory controller.

**The determinability boundary, stated as the ADR requires.** The VideoCore boot firmware is closed
source (Raspberry Pi engineers jamesh and jdb, forum t=391063) and lives entirely in SPI-EEPROM.
What the VPU does *before* the ARM reset vector, and the exact build configuration of the
EEPROM-embedded BL31 binary as opposed to its public source tree, **cannot be independently
determined**. Everything at and below the ARM reset vector is determinable from public source and is
as stated above. The EEPROM release notes pin the shipped stub to named commits of the public tree
(e.g. 2024-10-10: "armstubs: 2712: Rebuild with…", linking raspberrypi/arm-trusted-firmware), which
is provenance, not a build manifest — Q4 carries this limitation forward.

**Board-side corroboration from this session's boots:** entry at EL2 (a BL31 that hands over at EL2,
observed); `CNTVOFF_EL2 = 0` as firmware left it, read at EL2 in the one instruction window this
kernel has before zeroing it itself (`TOS64-QUAL/1 boot_entry … firmware_cntvoff=0x0`); and a
user-supplied stub override hook observed live (`armstub8-2712.bin` TFTP request). A platform
wanting a very strong Q2 can take EL3 from the reset vector with its own stub — the ADR's
"platform-specific route" — and this bench has now watched the firmware offer exactly that hook.

## Q3 — The residency campaign: instrument corrected and proven, campaign not run

`LE-103` recorded that the only Q3-shaped probe in the tree read `CNTVCT_EL0` — the one counter a
world above NS-EL1 can offset via `CNTVOFF_EL2` — and was therefore blind by construction to what Q3
measures. This session built the corrected instrument test-first
(`hal_arm64::timer::probe_residency_window`, windowed on the **physical** counter so the window's
length cannot be handed to whatever owns the offset; the blindness itself is pinned by a host test
that scripts a mid-window offset move and asserts it surfaces as the two counters' advances
disagreeing), and ran it on silicon inside the fixture's interrupt-masked region — Q3's stated loop
condition. Both boots:

```
TOS64-QUAL/1 counter_split cntpct=73644282 cntvct=73644284 virtual_offset=…(−2)   (boot 1)
TOS64-QUAL/1 residency window_ticks=540000 cntpct_ticks=540003 cntvct_ticks=540004 pmccntr_delta=24000170
TOS64-QUAL/1 counter_split cntpct=78031204 cntvct=78031205 virtual_offset=…(−1)   (boot 2)
TOS64-QUAL/1 residency window_ticks=540000 cntpct_ticks=540002 cntvct_ticks=540003 pmccntr_delta=24000125
```

Physical and virtual counters agree to 1–2 ticks (back-to-back read skew; the stub zeroed
`CNTVOFF_EL2` and the split confirms it stayed zero), and `PMCCNTR_EL0` advances at 2400.0 MHz
against the physical-counter window. Over these 10 ms windows there is no unexplained physical-time
advance.

**None of that is a campaign, and this record does not present it as one.** Q3 requires a stated
duration, sample count, largest excursion, distribution shape, environmental conditions — and the
ADR's own trap clause: **the instrument must first be shown to detect an injected perturbation**,
because a zero from an instrument never shown to produce a non-zero is an absence of measurement,
not a measurement of zero. The host test that detects a scripted offset move is the *logic's*
positive control; the *silicon* positive control (an injected stall or deliberate perturbation
observed by the same probe on the same board) has not been run and is the campaign's first step.

## Q4 — The refusal to over-claim, in this record's own words

An excursion not observed in two 10 ms windows is not an excursion that cannot occur. A secure
handler that fires on a thermal event, a USB event, or an SMC this kernel never issues was not
exercised by an idle bench. Nothing in this record licenses a worst-case bound, a WCET claim, or a
jitter envelope on this platform; `qualified-platforms.tsv` correctly still counts zero, every
`G04` gate remains closed to this platform, and the envelope's own `qualification=none` remains the
truthful self-description of every measurement taken to date. Where Q2 rests on public source, it
rests on the *published tree* the EEPROM release notes name, not on a reproducible build of the
shipped binary — a firmware update, or evidence that the shipped stub diverges from its published
source, voids the Q2 determination and with it this record.

## What this record changes

The owner decision `LE-94` records as pending — whether to run the Q1–Q4 campaign — is now two
parts smaller than the register believed on 2026-08-06: Q1 and Q2 are held (this record), Q4 was
already consistent practice and is now stated, and Q3 is one instrumented campaign with a stated
duration plus its silicon positive control. `LE-95`'s relay remains what automates the loop; this
session demonstrated the loop runs today with a human hand on the plug — two power cycles, two
boots, both captured, the second parsing to its own verdict.

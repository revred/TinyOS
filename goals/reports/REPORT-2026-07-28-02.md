## The finding: the previous Story's containment was accidental

`REPORT-2026-07-28-01` closed with a green capture: `blue-sharc.exe` faulted at `rip == cr2 == 0x7b9d9e` and was contained. Re-reading it rather than filing it produced this Story.

Nothing had patched the image's Import Address Table. Every thunk still held the RVA of its own `IMAGE_IMPORT_BY_NAME` record, so the CRT's first indirect call jumped to that RVA *taken as an absolute address*. It landed on non-executable memory and faulted — the right outcome, reached by arithmetic rather than by decision. An RVA is an attacker-visible number. An image laid out so that some thunk's RVA collided with a mapped executable page would have transferred control there, and nothing in the system would have objected.

The fix is that every IAT slot is now written exactly once at load time: a granted import gets a real, callable `extern "win64"` trampoline; every other import — not allowlisted, or allowlisted but policy-denied — gets `CAPABILITY_TRAP_VIRT` (`0xdead_0000`), an address deliberately unmapped in every address space. The same real artifact now faults at `cr2=0xdead0000`, which a reader can diagnose from the fault line alone.

**The lesson worth keeping:** a passing test told us containment held; only reading *how* it held revealed that it held for the wrong reason. Green evidence is not the same as understood evidence.

## The system image exists

`os` is a new top-level binary crate depending on both `kernel` and `exec` — the thing `kernel`'s own binary could never be, since `exec` depends on `kernel` and the reverse link is a cyclic crate dependency. That constraint is why every integration this project built lived in a fixture, and why the shipping binary had never created a task.

The real boot path now: discovers ACPI topology and PCI bus 0 (unchanged calls, unchanged gates) → enables `CR0.WP`/`EFER.NXE` and retires the all-RWX bring-up map for the W^X kernel tree → loads the embedded probe through the real PE64 pipeline into its own W^X, kernel-sharing address space → resolves its imports against the allowlist and a policy granting exactly the two it declares → seals → schedules it via `run_once_in_space` → contains and journals what happens.

```text
tinyos: 1 CPU(s), 6 PCI device(s)
tinyos: W^X memory protection active
tinyos: loaded image — 2 import(s), 2 granted, 0 trapped, cr3=0x13f000
tinyos: task 0 terminated — vector=14 rip=0xdead0000 cr2=0xdead0000 (refused capability)
tinyos: workload returned 0xffffffffffffffff (GetCurrentProcess ok=true), exited via trap 0xdead0000, task_finished=true, spoors=5
tinyos: boot complete, ok=true
```

`0xffffffffffffffff` is the sentence this project has been working toward: a real loaded image's own instruction stream, running under its own address space, called a Win32 API through a loader-patched IAT and got the correct answer back. Combined with the `first-task` fixture — where the same machinery *refuses* 198 of `blue-sharc.exe`'s 205 imports and contains the first reach beyond them — both directions of the capability contract are now demonstrated against real images.

`G-DX-8`'s image-size gate moved from `kernel` to `os`, which is where it belongs now that a binary exists containing the loader, the address spaces, the shim and the workload. The system image is **74,568 bytes** against the 8MiB ceiling.

The embedded workload is a 16KiB generated capability probe, not `blue-sharc.exe`: a system image is the operating system, not the applications it runs, and embedding an 8.3MiB third-party binary (plus its staging arena) to prove something the fixture already proves would have been the wrong trade. The probe is a genuine PE32+ — real headers, real section table, real split ILT/IAT, real hand-assembled code — generated by `xtask make-probe-pe` so it is reviewable source rather than an opaque committed blob, with host tests that re-derive every offset and displacement it claims.

## The D04 delta, and why it argues for hardware

`FEAT-P1-03`'s last exit criterion. Deferred twice for an honest reason — nothing in the dispatch path installed a per-task address space, so any number would have been fixture overhead misreported as a scheduling cost — and measurable for the first time now. Release profile, median of three runs:

| Metric | p50 (cycles) |
|---|---|
| `D04/dispatch_round_same_space` | 276 |
| `D04/dispatch_round_cross_space` | 7,452 |

**The ~7,200-cycle delta is an emulator artifact and must not be quoted as a hardware cost.** Under TCG a `mov cr3` forces QEMU to flush its own software TLB and re-resolve translations — vastly more expensive than the real instruction. What the measurement establishes is that the path works, the two arms are distinguishable, and the cost is bounded above. It is also the sharpest argument yet for `LE-09`: this is a case where Tier 0 cannot give even the right order of magnitude, so the hardware tier is not a refinement here, it is the only way to get a real number.

The metrics are reported and deliberately not gated — thresholding them would gate QEMU's TLB model rather than this kernel.

## What remains open

- **Tier 0 only.** `LE-09` unchanged, and sharpened by the D04 result above.
- **`ExitProcess` does not cleanly terminate a task.** It routes into the capability trap — contained, but a fault rather than a teardown. A task that finishes by *returning* needs scheduler support that does not exist. This is the clearest next Story in this area.
- **The trampolines are capability-mediated stubs, not subsystems.** `HeapAlloc` returns `NULL`, `WriteFile` returns `FALSE`; there is no heap, console driver or filesystem behind them. They fail the way real Windows fails rather than fabricating success, but a workload that needs those subsystems still cannot make progress.
- **The workload is embedded rather than loaded from storage.** A filesystem Story replaces `include_bytes!` with a real load path.
- **The probe is hand-assembled, not compiled.** It is evidence about the loader and the capability boundary, not about a real toolchain's code generation; `blue-sharc.exe` remains the evidence for that.
- **No preemption** (`FEAT-P1-04`), and the D04 metrics are ungated by choice.

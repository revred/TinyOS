# REPORT-2026-07-28-01

**Test(s) covered:** `TEST-P1-03-02-A` (`STORY-P1-03-02` — W^X/NX mappings, sealing, generation-safe teardown, and the first real scheduled task), performance domains `D04`/`D05`/`D08`, mapped `SEC-03`/`SEC-14`/`SEC-19`, containment classes `C0`/`C1`/`C3`.

**Result: Pass — both Tier 0 fixtures green.** The boot-time all-RWX identity map this system has run on since `STORY-P0-01-01` is retired at run time for a W^X kernel tree built from the linker's own section symbols, shared at page-directory granularity into every address space rather than duplicated. Both directions of W^X fault for real with the enforcement bits (`CR0.WP`, `EFER.NXE`) actually enabled, the loader's writable aliases are sealed, and teardown revokes/wipes/advances in `PD-13` order with a stale-mapping probe task confirming it. Then the first real task: the real `blue-sharc.exe`, loaded through the real PE64/TXE pipeline into its own W^X address space and dispatched through the production `CR3`-aware dispatcher, whose own CRT called an unallowlisted Win32 API through an unpatched IAT, faulted for real, and was contained — with spoor journaling it from a production call site. `STORY-P1-03-02`'s assurance state moves `specified` → `baseline-debt`.

## The headline finding

`blue-sharc.exe`'s real MSVC CRT startup called **`GetSystemTimeAsFileTime`** — not among the nine calls this shim allowlists — through its unpatched import address table. An unpatched thunk still holds the *RVA* of its `IMAGE_IMPORT_BY_NAME` record, so the indirect call took that RVA as an absolute address and fetched instructions from `0x7b_9d9e`, where the image's own bytes read `00 00 "GetSystemTimeAsFileTime"`: a hint word and an ASCII name. Under this Story's mappings that address is *present* (it lies inside the kernel's own mapped low memory) but **NX**, so the fetch raised `#PF` (`rip == cr2`), the task was terminated, and the system carried on.

Two consequences worth stating plainly:

- **The fault is not staged.** No `ud2`, no deliberately-unmapped probe address, no fixture-authored victim. A real, externally-authored program reached for a capability it did not hold, by the precise mechanism ungoverned code reaches for one, and the containment machinery caught it. That is a materially stronger claim than anything filed before this Story.
- **`EFER.NXE` and the W^X kernel map are load-bearing, not hygiene.** Without them that fetch would have *succeeded*, and this kernel would have begun executing an API name string as machine code. The bit that made the difference is one nothing in this codebase set until today — `map_4k` has been writing PTE bit 63 since `STORY-P0-05-02` with no hardware honoring it.

## The pre-implementation review, and why it mattered

The Story's acceptance criteria were reviewed against the actual code before any was written, and nine defects were found ([`session/hand-2026-07-28/03-story-p1-03-02-hardening-review.md`](../../session/hand-2026-07-28/03-story-p1-03-02-hardening-review.md)). Three would have been fatal:

- **D1.** "An out-of-allowlist Win32 call from inside the task raises a real fault" conflated three mechanisms and none of them faults: the shim is a Rust-level API with no IAT patching behind it, an out-of-allowlist import is refused at *load* time, and a policy-denied call returns `Err`. Code inside a loaded image had no path to the shim at all. The criterion was unimplementable as written; it became a two-layer claim (load-time refusal, journaled; runtime containment under an explicit override policy), and the runtime layer is what produced the `GetSystemTimeAsFileTime` finding above.
- **D3/D4.** "No mapping anywhere in the running system is W^X" would have been checked only over task trees while the kernel's own 1GiB RWX boot map — the largest violation, and the one the kernel actually executes from — went unexamined; and with neither `CR0.WP` nor `EFER.NXE` set anywhere in the codebase, the W^X tests would have passed *vacuously* (ring-0 writes ignore read-only pages) or failed *wrongly* (NX bits as reserved-bit faults).
- **D5.** A per-entry W^X audit would have passed while W^X was defeated: the loader copies image bytes through a writable staging alias in kernel memory, so every "immutable" executable page kept a live writable view. Sealing closes it, and the audit gained an alias clause that would catch its return.

The remaining six (D2 crate-cycle, D6 sharing granularity, D7 host-testability of the `CR3` arm, D8 teardown protocol, D9 what "production" means for spoor) each changed the design rather than only the wording.

## What remains open

- **No hardware tier.** Tier 0 QEMU only; `LE-09` unchanged.
- **The shipping `kernel` binary still discovers topology and halts.** `first-task-fixture` *reproduces* `kernel_main`'s discovery path rather than living inside it, because `exec` depends on `kernel` and the reverse link would be a cyclic crate dependency (the same constraint that created `exec-fixture` in `STORY-P0-05-02`). Unifying them behind a top-level `os` binary crate is the natural next structural step, and it is what would let the real boot path schedule a real task.
- **No IAT patching.** The image faults on its *first* reach through the IAT, so no allowlisted Win32 call has yet resolved and returned from inside a loaded image. That is the next thing standing between "a real workload is contained" and "a real workload runs."
- **No preemption** (`FEAT-P1-04`), and **no page-table frame reclamation** in teardown (deliberate: the torn tree must stay loadable for the stale probe).
- **No measured `D04` same-space-vs-cross-space delta**, deferred with `STORY-P1-03-01`'s deferral of it. It is now measurable for the first time, since a production dispatch path actually installs per-task address spaces.

**Root cause found and fixed during bring-up (recorded per this project's "surface the gap, don't silently claim it's solved" discipline):** the local APIC is architecturally relocatable via `IA32_APIC_BASE` (Intel SDM Vol 3A §11.4.1), and this Story's first working version relocated it into `boot.rs`'s existing first-1GiB identity map to avoid touching boot assembly. Under QEMU's own APIC device model, relocation is not honored — every local-APIC register (including the read-only, hardware-answered APIC ID register) read back all-zero after relocating, proving the access was landing on ordinary backing memory, not the APIC. Diagnosed via a temporary debug-serial hex dump of `IA32_APIC_BASE`/SVR/LVT/ID/current-count read back after `init` (removed before this Report was filed) confirming the MSR write itself was correct (enable bit set, address field as requested) while every subsequent MMIO read against that address returned zero. Fixed by targeting the local APIC's real, non-relocated default address (`0xFEE00000`) instead, requiring `boot.rs`'s identity map to be extended (`boot_pd_gib3`, a second `PDPT[3]`-rooted `PD` covering `0xC0000000-0xFFFFFFFF`) so that address is actually reachable — verified via the regression sweep above that this shared boot-path change does not affect any of the nine pre-existing QEMU fixtures.

A second, independent bug was found and fixed the same way: `fixture-idt-apic-unrouted`'s first version called `interrupts::init(1)` (timer reload count `1`, "irrelevant since this fixture never waits on a tick" per its own then-current comment) — but `init` unconditionally arms and enables the timer regardless of whether the caller ever reads a tick, and a reload count of `1` fires near-continuously, starving the CPU of forward progress before it ever reached the fixture's own deliberate `int 0x21` (observed as a 15-second QEMU boot-timeout hang, not a crash). Fixed by using `u32::MAX` as the reload count, guaranteeing the timer cannot fire before the fixture's own `int` diverges.

**Deliberately not done:**

- **No I/O APIC / device-IRQ routing** — this Story's own scope-correction note (`STORY-P0-04-02.md`) explains why: no device driver exists yet to request a routed line, and this Story's own acceptance criteria never actually needed it. Deferred to `STORY-P0-04-03` or a later driver Story.
- **No TSS/Interrupt Stack Table.** A `#DF`/`#MC` whose own stack is already invalid can still fault a second time while the CPU pushes that vector's frame — `idt::Idt`'s own doc comment states this as a real, general, unresolved limitation, not assumed solved by the fail-closed default handler (which only protects against a *reachable* handler being absent, not against a stack that's already unusable).
- **No production tick consumer.** `interrupts::init` is called from the real boot path (closing "no IDT/fault containment" as an actual boot-time capability, not just a fixture demonstration), but nothing reads `tick_count()` yet — no scheduler dispatch loop exists to consume it.
- **No raw performance/security evidence** for the assurance spine's `D02`/`D03`/`SEC-03`/`SEC-18`/`SEC-19`/`SEC-20` mapping — marked `baseline-debt`, not `verified`.

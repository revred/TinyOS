## Design decisions worth stating

**Why `#UD` and not `#GP`/`#PF`.** Same reasoning `fixture_fault::victim_invalid_opcode` already established: `ud2` is architecturally guaranteed to fault with no dependency on GDT shape or page-table layout, so it is the one vector this fixture can trigger deterministically, a thousand times in a row, with nothing to drift. `#GP`'s and `#PF`'s own fixtures both carry doc comments about constants that had to be chosen carefully to avoid coupling to table sizes that change — an unnecessary risk for a phase whose only job is timing, not vector coverage (that is `fixture_fault`'s, already Verified).

**Why `FaultingContext::Kernel` and no `Scheduler`.** `kernel::fault::audit` computes the same cost for `TerminateTask` and `HaltSystem` — it branches only on which `Outcome` to stamp, never on how much work to do. Standing up a `Scheduler`/`TaskId` per iteration (or reusing one across 1,100 iterations, which the disposition API's task-less `Kernel` arm makes unnecessary) would add container bookkeeping to what this phase is honestly measuring: the capture-decide-audit span. Task termination *behavior* — a task actually dying while its siblings keep running — is what `fixture_fault` already proves; this phase's only job is the timing, and it says so in its own doc comment so a future reader does not mistake `FaultingContext::Kernel` here for a claim that no task ever faults in production.

**Per-iteration context reinitialization, unlike every other phase.** `phase_context_switch`'s task loops forever, switching back and forth through the same `Context` for all 1,100 iterations. A fault handler never resumes the context it interrupted (`kernel::fault`'s own doc comment: there is no `Resume` arm), so `phase_fault_latency` cannot reuse a live task the way `phase_context_switch` does — each iteration calls `Context::new` fresh, exactly as `fixture_fault::run_victim` does once per victim. The difference here is doing it 1,100 times in a driver loop rather than three times by hand.

**Installing `init_faults_only` changes nothing about the first five phases.** It arms no APIC timer and never executes `sti` itself — the same non-properties the bare `remap_and_mask_pic` call it replaces already had. The one behavioral difference it adds is a real IDT with `#UD`/`#GP`/`#PF`/`#DF` gates, which only this sixth phase's deliberate fault ever reaches. `D07`/`D04`/`D05`'s numbers are unaffected because nothing in them touches an exception.

**Domain `D02`, matching the Story-contract selection already made.** `STORY-P1-02-01`/`STORY-P1-02-02` already select `D02` ("Interrupt entry and exit") as their performance domain in `goals/assurance/story-contracts.tsv`, despite being Tier 0 fixtures — `D02`'s catalogue rows name tier `T1+T2` as what would *close* its guardrails, not what is permitted to report evidence toward them, exactly the same relationship `D04`/`D05`/`D07` (tier `T0+T1+T2`) already have with Tier 0 numbers that carry `baseline-debt`, never `verified`.

## What this Report does not establish

- **No hardware tier.** Tier 0 QEMU only; the number calibrates the harness and mechanism, not real silicon. `LE-09` stays open, and this baseline is exactly the kind of Tier 0 evidence that will need a Raspberry Pi 5 counterpart.
- **No `PERF-D02` guardrail closes.** A committed baseline lets `check-timing-regression` detect a regression in this path; it does not mean any of `PERF-D02-G01`..`G25`'s stated targets (all `T1+T2`, all `specified`) are met.
- **No new fault-containment coverage.** `fixture_fault` already proves task-only containment; this phase adds no new adversarial evidence about *that* — only a latency number for the path both fixtures share.
- **Host noise, observed but not fixed.** A `check-timing-regression --runs=3` immediately after this session's own 5-run baseline recording showed `D04/context_switch_yield_roundtrip_2switches` p50 regress on one attempt and pass cleanly on a re-run with no code change in between — the same shared-host Tier 0 variance `LE-18` already names, reconfirmed here rather than newly discovered.

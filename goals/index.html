Protection Domains + remote-code exclusion

One lightweight sandbox primitive combines private active memory, kernel-owned capabilities, CPU/resource budgets, provenance, lifecycle generation, containment class, and fault teardown. Every external byte remains non-executable C4 data unless all 14 code-admission gates pass; inspection is destroyed and admitted code starts as a fresh empty-authority C3 domain.

14 PD invariants · 14 remote-code gates · all 25 C0–C4 paths · no remote W→X, process-write, in-place patch, JIT exception, driver load, deploy activation, or trust-root enrollment path.

The assurance spine is now a mandatory join through every Feature and Story. Every Feature declares its implementation/subject containment classes, authority posture, hostile inputs, boundary tests, and required evidence; every Story selects performance domains, security controls, and classes. The Security Charter is connected transitively and exhaustively to all 20 controls and 20 boundary tests. Current mappings expand to 1,500 Story/performance contracts. All 25 functionally Verified Stories are honestly marked baseline-debt; EPIC-P1's 10 Stories are specified. No Story is yet assurance verified — converting that state is EPIC-P1's explicit charge.

This is a release block, not a claim that Phase 0 has failed. The current functional suite predates the assurance spine and does not contain raw latency tails, CPU-cycle, allocation, memory-footprint, signing, active-address-space isolation, hostile-load, or campaign-level security evidence. Those results must be produced by dated Reports; the dashboard will not backfill them from functional passes.

Whole-system flight plan

The destination is represented as four inseparable planes. A future application does not become a vague compatibility promise: it names its Goal, selects the performance cells it must earn, declares its execution and containment model, and identifies the security controls that remain true at the measured speed. The machine-readable joins are in application-platforms.tsv and landing-zones.tsv; the narrative architecture is docs/whole-system-context.md.

Why Goals

Falsifiable outcomes: real-time control, quality-adjusted AI velocity, application compatibility, connectivity, developer experience, hardware and fleet operation.

How fast Performance

625 core guardrails plus per-application selections for latency tails, CPU/GPU cycles, allocations, queues, memory, IPC, token delivery, load isolation and footprint.

What runs Applications

19 explicit targets across native tasks, AI, UX frameworks, managed and JavaScript runtimes, games, browser, remote UX, host bridge, compatibility and fleet profiles.

Under what authority Security

Protection Domains, C0–C4 placement, signed admission, provenance, no ambient IPC/files/network, revocable grants, bounded brokers and fail-closed teardown.

A Story is never functionally Verified on implementation alone. Assurance verified is stricter again: the Report must close its mapped performance and security release gates with raw evidence.

Just-in-time decomposition

EPIC-P0 (functionally complete) and EPIC-P1 (next up) are decomposed to Feature/Story level. Decomposing every future Epic today would produce dozens of Story files describing undesigned work, which this project's own principles argue against. Decompose an Epic when work on it is about to start, not before — EPIC-P1 was decomposed the day EPIC-P0 closed, which is exactly the model working as designed.

Goals, performance, applications, and security are the spine

625 performance guardrail tests cover 25 OS domains against 25 measurable latency, CPU-cycle, memory, allocation, queue, throughput, isolation, fault-containment, observability, footprint, and comparative-evidence checks. 20 security controls cover signed execution, private process memory, revocable sharing, sandbox-first authority, origin/entitlement, network/port isolation, active content, downloads, privacy/tracking, ransomware/worms, drivers/DMA, secrets, updates, resource exhaustion, and Fable-class adaptive AI campaigns. Five containment classes and 20 boundary tests make component placement, hostile input, promotion, teardown, negative surface, and single-defect containment explicit. The root Security Charter adds the canonical Protection Domain and only permitted remote-data-to-code path.

They are joined to every current and future Feature and Story by feature-contracts.tsv and story-contracts.tsv. Adding an unmapped artifact, invalid class/test reference, stale contract, malformed control, incomplete charter/catalogue, uncovered control/boundary, or missing C0–C4 pair fails xtask check-assurance-spine in CI. The current-state review keeps design contracts separate from implemented runtime evidence. Linux and “10× RTOS” comparisons remain claim gates requiring same-hardware, safety-equivalent raw evidence.

Five containment classes

ClassRuntime roleDefault posture
C0 · Root of TrustBoot verification, measurement, recovery and one-way handoffNo reusable runtime command surface
C1 · Trusted Kernel CoreScheduler, MMU, fixed IPC/capability checks, faults, interrupts and budgetsNo complex hostile-format parser
C2 · Isolated System ServiceDrivers and device/network/storage/loader brokersAssumed compromisable; narrow restartable grants
C3 · Sandboxed ApplicationSigned installed programs, inference runtime and toolsFresh private process; empty authority until policy grants a manifest subset
C4 · Hostile Transient DomainDownloads, unknown executables, parsers, scripts, documents and model outputQuarantined, disposable, zero authority, never promoted in place

Containment class is independent of capabilities, scheduling priority, and provenance. A class never grants authority; a signed driver remains isolated C2; a human is an authenticated principal rather than a class.

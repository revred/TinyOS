About that zero, because a bare 0 with no denominator and no path is a bad statistic even when it is accurate. A Story reaches assurance verified only when dated raw evidence closes every applicable release gate — G01–G23 in each selected domain, plus its SEC-* and BND-* obligations. Selecting one domain brings all of its guardrails in, so a dispatch Story inherits sustained throughput, cold start, isolation under 90% competing load, and a 72-hour soak. The measurement protocol additionally wants ≥1,000,000 operations for p99.9 and 30 independent runs. **The first verified Story is therefore a measurement campaign, not a boot** — getting the Pi 5 running is necessary and nowhere near sufficient.

Governing security charter

Protection Domains + remote-code exclusion

One lightweight sandbox primitive combines private active memory, kernel-owned capabilities, CPU/resource budgets, provenance, lifecycle generation, containment class, and fault teardown. Every external byte remains non-executable C4 data unless all 14 code-admission gates pass; inspection is destroyed and admitted code starts as a fresh empty-authority C3 domain.

14 PD invariants · 14 remote-code gates · all 25 C0–C4 paths · no remote W→X, process-write, in-place patch, JIT exception, driver load, deploy activation, or trust-root enrollment path.

The assurance spine is now a mandatory join through every Feature and Story. Every Feature declares its implementation/subject containment classes, authority posture, hostile inputs, boundary tests, and required evidence; every Story selects performance domains, security controls, and classes. The Security Charter is connected transitively and exhaustively to all 20 controls and 20 boundary tests. Current mappings expand to 2,600 Story/performance contracts across 23 Features. All 38 functionally Verified Stories are honestly marked baseline-debt (evidence gathered, no guardrail closed); the other 18 contract rows — EPIC-P1's remaining Stories and all 10 of EPIC-P9's — are specified. No Story is yet assurance verified — converting that state is EPIC-P1's explicit charge.

This is a release block, not a claim that Phase 0 has failed. The current functional suite predates the assurance spine and does not contain raw latency tails, CPU-cycle, allocation, memory-footprint, signing, active-address-space isolation, hostile-load, or campaign-level security evidence. Those results must be produced by dated Reports; the dashboard will not backfill them from functional passes.

Whole-system flight plan

The destination is represented as four inseparable planes. A future application does not become a vague compatibility promise: it names its Goal, selects the performance cells it must earn, declares its execution and containment model, and identifies the security controls that remain true at the measured speed. The machine-readable joins are in application-platforms.tsv and landing-zones.tsv; the narrative architecture is docs/whole-system-context.md.

EPIC-P1 — Determinism Proof IN PROGRESS — FEAT-P1-01/-02/-03/-04 COMPLETE

Decomposed 2026-07-27 now that every EPIC-P0 Story is functionally Verified: 7 Features, 20 Stories, with valid assurance-contract rows (56/56 Stories mapped by CI, EPIC-P9's 10 included). Work started the same day and has continued since: FEAT-P1-01 (measurement harness) and FEAT-P1-02 (real fault handling) are both functionally complete — all 5 of their Stories Verified at Tier 0 + Host, including the fault-latency baseline (LE-17, closed 2026-07-27, REPORT-2026-07-27-07). FEAT-P1-03 (active per-task address spaces) completed 2026-07-28 — all three Stories Verified, every exit criterion met including the D04 switch-cost measurement deferred twice. This is the Feature where TinyOS stopped being a set of proven mechanisms and became a system that runs something: the boot-time all-RWX identity map is retired at run time for a W^X kernel tree shared across every address space (REPORT-2026-07-28-01), and a new top-level os system image discovers hardware, loads a real PE64 through the real loader, resolves its imports against the capability allowlist, and schedules it as a task under its own CR3 (REPORT-2026-07-28-02). Both directions of the capability contract now hold against real images: a granted call resolves and returns correctly from inside the loaded image's own code, and a refused one faults at a named trap address. FEAT-P1-04 (preemption and overrun enforcement) completed 2026-07-28, and it is where this kernel started taking the CPU away from software that will not give it up. Dispatch became genuinely preemptive — a task whose body contains no switch, no hlt and no scheduler call is removed from the CPU by a real local-APIC tick and resumes exactly where it was, with its SSE state intact (REPORT-2026-07-28-03) — and the same tick now enforces WCET budgets, applying the policy each task declared at creation: restart, degrade to a declared floor, or trip to a fail-closed safe state (REPORT-2026-07-28-04). Ordering: measurement first (FEAT-P1-01, the timing-regression CI gate), then faults before address spaces (FEAT-P1-02 → FEAT-P1-03, per Handover 32/33/35's standing CR3 reasoning — now realized), preemption/deadline enforcement (FEAT-P1-04 — now realized), then the two proof Features — hostile load (FEAT-P1-05) and the G-PA-1 decision-to-actuation bound (FEAT-P1-06). This Epic is where baseline-debt first converts to verified — not yet done: every Verified Story here still carries assurance state baseline-debt, pending hardware-tier evidence (LE-09).

A seventh Feature was added 2026-07-28, and it changes what "next" means. A Raspberry Pi 5 became available, so FEAT-P1-07 — six Stories, six Test documents written before any implementation — is now the next work. It is the only Feature in this repository that can close LE-09, and LE-09 is the single blocker behind all 38 baseline-debt Stories: one blocker, not fifty-six. FEAT-P1-05 and FEAT-P1-06 would each produce more Tier 0 evidence, which is the one thing this project already has a surplus of — Tier 0 tail variance of 39–61% is a statement about QEMU, so no evidence about this system's jitter exists yet. Alongside it, ADR 0004 records ARM64 as the real-time tier: an x86 SMI is entered above the kernel and cannot be masked, observed or attributed, so an x86_64 worst-case bound is a claim about firmware rather than about TinyOS. x86_64 keeps throughput, rich-workload and host-bridge claims and stays the Tier 0 gate; no existing number is retracted. One consequence for this Epic: FEAT-P1-06 states a bound, so under ADR 0004 that bound is quotable from ARM64 hardware and a Tier 0 or x86_64 run of it is mechanism evidence.

Hardware direction (user, 2026-07-27): the Raspberry Pi 5 is the only viable hardware in the short term. It is ARM64 and TinyOS has an x86_64 HAL only, so Tier 0 (QEMU) proves every mechanism while a minimal ARM64 bring-up slice + deploy path is scoped as loose end LE-09 — until Pi 5 measurement exists, every timing claim carries named, dated hardware-tier debt. See the Epic's hardware ladder.

ARM64 sequencing decided (user, 2026-07-27): Option B with a carve-out — Handover 03. The ARM64 CNTVCT_EL0/CNTFRQ_EL0 cycle source and timebase are written now (no board needed, and the only thing that tests the harness's arch-neutrality claim — with its own Story contract row and Test document first, per the spine); UART-borne pass/fail folds into STORY-P1-01-02; AArch64 boot, the PL011 driver and the SD-card run path wait for FEAT-P1-02, after which a fault on that board reports itself instead of hanging silently. A Story is never functionally Verified on implementation alone. Assurance verified is stricter again: the Report must close its mapped performance and security release gates with raw evidence.

Just-in-time decomposition

EPIC-P0 (functionally complete) and EPIC-P1 (next up) are decomposed to Feature/Story level. Decomposing every future Epic today would produce dozens of Story files describing undesigned work, which this project's own principles argue against. Decompose an Epic when work on it is about to start, not before — EPIC-P1 was decomposed the day EPIC-P0 closed, which is exactly the model working as designed.

Goals, performance, applications, and security are the spine

625 performance guardrail tests cover 25 OS domains against 25 measurable latency, CPU-cycle, memory, allocation, queue, throughput, isolation, fault-containment, observability, footprint, and comparative-evidence checks. 20 security controls cover signed execution, private process memory, revocable sharing, sandbox-first authority, origin/entitlement, network/port isolation, active content, downloads, privacy/tracking, ransomware/worms, drivers/DMA, secrets, updates, resource exhaustion, and Fable-class adaptive AI campaigns. Five containment classes and 20 boundary tests make component placement, hostile input, promotion, teardown, negative surface, and single-defect containment explicit. The root Security Charter adds the canonical Protection Domain and only permitted remote-data-to-code path.

They are joined to every current and future Feature and Story by feature-contracts.tsv and story-contracts.tsv. Adding an unmapped artifact, invalid class/test reference, stale contract, malformed control, incomplete charter/catalogue, uncovered control/boundary, or missing C0–C4 pair fails xtask check-assurance-spine in CI. The current-state review keeps design contracts separate from implemented runtime evidence. Linux and “10× RTOS” comparisons remain claim gates requiring same-hardware, safety-equivalent raw evidence.

It also delivers the first *real* task: `blue-sharc.exe`, loaded through the real PE64/TXE pipeline into its own W^X space and scheduled through the production dispatcher, whose own CRT called an unallowlisted Win32 API (`GetSystemTimeAsFileTime`) through an unpatched IAT, faulted for real, and was contained — the first fault this project has caught from a real workload's own defect rather than from a fixture built to fault on cue. Spoor finally has production call sites. `STORY-P1-03-03` (Verified 2026-07-28, `REPORT-2026-07-28-02`) closes the Feature: reading `STORY-P1-03-02`'s own passing capture revealed that its containment was *arithmetically accidental* — nothing patched the loaded image's IAT, so a refused capability faulted at an image-derived RVA that merely happened to be non-executable — so import resolution now writes every IAT slot exactly once (granted calls get real, callable `extern "win64"` trampolines; everything else gets a deliberately-unmapped trap address that names the cause in `CR2`). A new top-level `os` binary crate, depending on both `kernel` and `exec` as neither could alone, makes the *real* boot path discover hardware, retire the all-RWX bring-up map, load a real PE64, resolve its imports, and schedule it under its own `CR3` — with the embedded workload's own code calling `GetCurrentProcess` through its patched IAT and getting the correct answer back. `G-DX-8`'s image gate moved to that image. And the `D04` switch cost, deferred twice, is measured: ~276 cycles same-space against ~7,452 cross-space, reported and deliberately ungated because at Tier 0 the figure is dominated by TCG's own TLB-flush emulation — the sharpest argument yet for `LE-09`. `FEAT-P1-03` now meets every exit criterion. `STORY-P1-04-01` (Verified 2026-07-28, `REPORT-2026-07-28-03`) opens `FEAT-P1-04` and makes dispatch genuinely preemptive: the local-APIC timer, armed since `STORY-P0-04-02` and consumed by nothing since, now drives `kernel::preempt::on_timer_tick` through a registered `TickHook`, which suspends a running task into the dispatcher's own suspended context — so `dispatch::run_once` regains control exactly where a cooperative yield would have left it, and needed no change at all. A task whose body contains no `switch`, no `hlt` and no scheduler call is demonstrably taken off the CPU and demonstrably resumes where it left off (~1.3M iterations in, then ~420k more). `LE-14` closed, and closed in a different place than it was scoped: the fixture's adversarial `XMM0` check failed with the save/restore around the *context switch*, because an interrupt handler is itself compiled code on the interrupted task's stack and a **non**-preempting tick can clobber SSE registers just as thoroughly — so `FXSAVE`/`FXRSTOR` moved into the timer ISR stub, around the whole handler call, and the omission was then deliberately falsified to prove the check can fail. `LE-01` closed too: the classic three-task inversion scenario runs for real, asserting the dispatch order taken (`low → high → low → high`) *and* that the medium task, `Ready` throughout and able to run afterwards, made no progress whatever while the boosted holder finished — closing the host-only caveat `STORY-P0-02-03`'s own module doc has carried since `EPIC-P0`. `STORY-P1-04-02` (Verified 2026-07-28, `REPORT-2026-07-28-04`) closes `LE-02` and **exits `FEAT-P1-04`**: `wcet::record_tick` is driven by the real timer through the same tick hook, and an overrun applies the `OverrunPolicy` the task declared at creation — restart, degrade to a declared floor, or trip to a fail-closed safe state. The policy is a parameter of `Scheduler::create_task` with no default (78 call sites), a degrade floor above the task's own priority is rejected rather than clamped (an overrun must never be a route to a criticality level nobody granted), and `kernel::fault::Disposition` is deliberately not extended — an overrun has no frame, no vector and no hardware event, so it gets a parallel decision table that likewise reads exactly one input, the declaration the task made in advance. All three Tier 0 fixtures passed on their first run and **two of them were not evidence**: a falsification that removed every enforcement mutation left `wcet-restart` green (the fixture was proving its own context rewind, not the kernel's budget-window reset) and `wcet-trip` reporting `ok=true` (it never checked the task was actually `Finished`, and its pass condition is a failure exit code, so exit 1 carried no information). Both fixed, and `wcet-trip`'s CI step now greps the serial capture rather than trusting the exit code — a stronger pass condition than `broken-boot` or `idt-apic-unrouted` have. Opened `LE-22` (degrade silently undone by `PriorityInheritingLock`'s restore-on-unlock). `STORY-P1-04-03` (Verified 2026-07-28, `REPORT-2026-07-28-05`) closes `LE-20` and makes `FEAT-P1-04` exit **on the shipping image** rather than on its fixtures: `os` installed no tick hook, so for two Features this project had a Verified preemptive scheduler and a Verified WCET watchdog and the binary it ships ran neither. It now installs the hook before the timer is armed, dispatches in a bounded loop with `IF` clear (read back from `RFLAGS` on every round, not asserted in a comment), charges every tick to whoever was on the CPU, and reinstalls the supervisor `CR3` after each round — the trap Handover 06 named, which only the shipping image could expose because the `FEAT-P1-04` fixtures dispatch through `run_once` and touch no `CR3` at all. The workload's `TripToSafeState` declaration was replaced with `Degrade(PRIORITY_MIN)`: letting a contained, capability-mediated application halt the system for burning CPU is a *more* severe consequence than the same system gives it for a genuine fault, and hands it the denial of service `PD-07`/`PD-08` and `BND-15` exist to deny. Enforcement is proven against a real PE64 whose `.text` is `EB FE`, generated by the same `probe_pe` module, admitted by the same capability gate, and differing from the shipping workload only in that section — so the runaway run exercises the shipping hook rather than a fixture's. Three falsifications: without the hook the image **times out**, held indefinitely by a workload it had already admitted; without the mask `if_clear=false`; without the reinstatement `cr3_after_round` is the *image's* `PML4`. A fourth finding never reached the code — the first draft of clause 1 asserted a serviced-tick count, and two runs of identical binaries reported different splits, so it became a read-back of the hook pointer instead. Tests are written when each Story starts, per the TDD workflow.

**`EPIC-P9` — Memory Confidentiality and Integrity Against a Dump.** Specified 2026-07-28 in [`EPIC-P9.md`](epics/EPIC-P9.md): 8 Features, 10 Stories, decomposed from [`session/hand-2026-07-28/07-memory-confidentiality-proposal.md`](../session/hand-2026-07-28/07-memory-confidentiality-proposal.md) as revised against [`08`](../session/hand-2026-07-28/08-memory-confidentiality-review.md)'s review. A **capability Epic that runs alongside the phase sequence rather than inside it** — confidentiality is not in `EPIC-P1`'s determinism thesis, and its prerequisites (entropy, crypto primitives, a hardware root of trust) are infrastructure other phases will also want. The design in one sentence: the secrecy lives in a per-machine, per-boot root that never existed in the source tree, every process key derives from it using public process metadata as salt so nothing is stored or carried across a power cycle, and the thing stopping an attacker booting their own modified TinyOS is the TPM refusing to unseal for a boot that measures differently. **The precondition is stated first and is not a caveat**: none of `FEAT-P9-02` through `FEAT-P9-08` can reach `baseline-debt` on this project's current evidence base, because every acceptance test for the central construction needs a TPM and — for `FEAT-P9-07` — a memory-encryption engine, and a software TPM under QEMU would verify the emulator exactly as `STORY-P1-03-03`'s `D04` figure measured TCG's TLB model. `LE-09` is therefore a hard gate on this Epic, and it cannot exit at Tier 0. **`FEAT-P9-01` is the exception and is scoped precisely so that it is**: the dump-scan audit (`STORY-P9-01-01`, which turns “no plaintext survives teardown” from a property holding by accident of implementation into a measured invariant with a scanner proven able to fail) and the staging-arena wipe (`STORY-P9-01-02`, which closes the largest plaintext puddle in the image — a fully decoded PE with headers intact, already dead by the time the task runs, for the cost of one memset). Neither needs cryptography, entropy, a TPM or hardware; both can land inside the current phase. The Epic also carries an objection neither source document raised: the graceful-degradation tier is a **downgrade attack** on the forged-kernel defence, because making the TPM unreachable is strictly easier than forging measurements — which is why `STORY-P9-04-02` exists separately from the TPM driver Story, and why the Epic's exit criteria require that resolved rather than deferred. This Epic is also the first thing to put implementation behind `SEC-01` (hardware-rooted verified boot) and `SEC-15` (secret and credential isolation), both declared in the Security Charter from the beginning with nothing behind them.

## Mandatory assurance spine

The V&V hierarchy above is governed by the root [`Security Charter`](../SECURITY_CHARTER.md) and joined to performance, security, and containment by [`assurance/feature-contracts.tsv`](assurance/feature-contracts.tsv) and [`assurance/story-contracts.tsv`](assurance/story-contracts.tsv). Every Feature has exactly one boundary contract; every Story has exactly one assurance row selecting:

- one or more domains from the complete 25 × 25 [`performance/catalogue.tsv`](performance/catalogue.tsv), expanding to all 25 guardrails per selected domain;
- one or more release controls from [`security/controls.tsv`](security/controls.tsv);
- one or more of the five canonical classes from [`security/containment-classes.tsv`](security/containment-classes.tsv), while the parent Feature selects mandatory [`BND-*` tests](security/containment-tests.tsv);
- an assurance state distinct from the Story's functional status.

The current **57** Story rows expand to **2,625** Story/performance contracts. The 19 application/platform targets expand to 6,575 destination/performance obligations by selecting the same canonical domains and guardrails. **39** functionally Verified Stories are `baseline-debt`, not assurance `verified`; the remaining 18 — `EPIC-P1`'s unstarted Stories and all 10 of `EPIC-P9`'s — are `specified`. The distinction prevents functional reports or future application context from being misrepresented as latency, cycle, allocation, footprint, signing, active process-isolation, hostile-load, or AI-campaign evidence.

**No Story is assurance `verified`, and that number will not move soon** — a Story flips only when *every* applicable release gate closes, which for most domains includes a 72-hour soak and a million-operation tail measurement on hardware this project does not yet have (`LE-09`). Below the Story level, [`assurance/guardrail-evidence.tsv`](assurance/guardrail-evidence.tsv) now records which individual `PERF-Dnn-Gnn` gates carry dated evidence: **10 of the 391 in play**, all of them `G11`, on the compiler-enforced fact that no shipped crate can allocate. It is a record of evidence and never a score — a gate absent from it is *unevidenced*, never *passed*, and no Story's state is derived from it.

## How to keep this in sync

1. Adding a new Feature, Story, or Test: add a row here (or extend an existing Feature's rows), add the Feature to `assurance/feature-contracts.tsv`, and add/update the Story in `assurance/story-contracts.tsv` in the same PR. An unmapped Feature or Story fails CI.
2. A Test's Status changes (e.g. first pass, or a regression): update the Status column and add the Report row in the "Session cross-reference" table if a handover discusses it, in the same PR that adds the Report file under `goals/reports/`.
3. Decomposing a backlog Epic into Features/Stories: move it out of the "not yet decomposed" section into its own fully-populated block, matching the `EPIC-P0` pattern above.
4. A Story becomes assurance `verified` only when its dated Reports close every applicable mapped release gate with raw evidence. Functional status and assurance status are never conflated.

## What this session did

1. **Implemented `kernel::spoor_journal::SpoorJournal<N>`** (new module, `os/src/kernel/src/spoor_journal.rs`): a fixed-capacity, no-heap ring buffer of `Spoor` values. `append` never blocks, never allocates, never panics — a full journal silently overwrites its oldest entry rather than rejecting the new one (matching `Sharc.Blue`'s own "stamp immediately, never buffer/batch" doctrine, and the judgment call that losing the newest audit event is worse than losing the oldest for a fixed-size trace). `iter()` reads entries back oldest-first, correctly handling both the not-yet-wrapped case (oldest is always index 0) and the wrapped case (oldest is at the slot the next `append` would overwrite).
2. **Matched `Sharc.Blue`'s on-disk record shape exactly, without needing a filesystem to prove it**: each journal slot stores the entry's raw `Spoor::to_bits()` value directly (no intermediate representation), and a new `JOURNAL_MAGIC` constant (`b"SPOORJ01"`) is defined identical to `Sharc.Blue`'s own journal-file magic — so a future storage-backed journal (once TinyOS has a filesystem) can serialize this buffer's contents directly, byte for byte, rather than needing a translation step.
3. **6 new host tests**, covering the ring buffer's full state space: empty, not-yet-full (oldest-first ordering), exactly-full-then-one-more (oldest entry overwritten, not newest), many-more-appends-than-capacity (repeated wraps, no panic, exactly the most recent `N` survive), the degenerate `N = 1` boundary, and the record-format/magic check.

## What this session deliberately did not do

- **Did not implement a storage-backed journal.** This kernel still has no filesystem — `SpoorJournal<N>` is in-memory only. `JOURNAL_MAGIC` exists so a future storage-backed serializer has a documented, `Sharc.Blue`-compatible target to write to, but no such serializer exists yet.
- **Did not construct a real concurrency/race test.** This kernel's current execution model is single-CPU with no interrupts (no timer/IDT — a repeatedly-named gap across recent handovers), so `append`'s atomicity with respect to a concurrent read is guaranteed by Rust's own borrow checker (no concurrent `&mut self`/`&self` access is expressible through the safe API at all) rather than tested against a real race, since no such execution context exists yet to construct one.
- **Did not wire any real subsystem to call `append`.** `kernel::lock`'s boost/restore events and `kernel::wcet`'s overrun detection remain the natural first candidates, tracked explicitly as `FEAT-P0-06`'s own still-open exit-criteria follow-up, not silently treated as already done.
- **Did not implement any query/replay/summarize capability.** `Sharc.Blue`'s own `spoor.query`/`spoor.watch`/`spoor.replay`/`spoor.summarize` atoms remain out of scope until `EPIC-P2` (Shell & UX) exists to host such commands.

## Key decisions worth restating

- **Storing raw `to_bits()` values, not `Spoor` structs, was deliberate.** It makes the on-wire/on-disk compatibility claim (`STORY-P0-06-02`'s acceptance criterion 3) trivially true by construction — `entries: [u64; N]` *is* the serialization format, not something a future writer has to derive from a higher-level representation.
- **"Oldest entry overwritten, not newest" was a judgment call worth recording explicitly**, not an arbitrary ring-buffer default: for a fixed-size audit trail, the newest event is almost always the most operationally relevant (what just happened, right before now), so losing it to make room for something that already happened would be the wrong trade-off. `Sharc.Blue`'s own doctrine doesn't dictate this specific policy (that project uses an unbounded append-only file), but it's the natural fixed-capacity analogue.
- **`FEAT-P0-06` reaching "Verified" with one exit-criteria item still open is consistent with this project's established convention** (`STORY-P0-05-02`/`-03`, `FEAT-P0-02`'s two prior structural gaps) — a Feature/Story is Verified when its own acceptance criteria are met, not when every conceivable adjacent goal is also achieved; the still-open item (real subsystem adoption) is named explicitly in the Feature doc's exit criteria rather than either blocking Verified status or being silently dropped.

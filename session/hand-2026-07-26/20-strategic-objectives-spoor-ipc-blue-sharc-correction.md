# Handover 20 — New Strategic Direction: Spoor, Local IPC, Deploy Tooling; `blue-sharc.exe` Framing Corrected

Follows: [`19-story-p0-03-02-capacity-configuration-implementation.md`](19-story-p0-03-02-capacity-configuration-implementation.md). Mid-session, the user gave three new strategic objectives and one important correction, superseding the prior "keep working through `EPIC-P0`'s remaining unblocked Stories" plan with new direction.

## What the user directed

1. **A standing framing correction**: TinyOS is not a "hobby OS" — it is a serious project targeting data centers/local AI, UAVs, medical devices, edge devices, and consumer electronics. Saved to persistent memory (`feedback_project_framing.md`) so this holds across future sessions, not just this one.
2. **Three strategic objectives**:
   - In-process communication: shared memory between processes, socket communication, a TCP/IP stack.
   - The sibling `Sharc.Blue` project's `blue.atoms`/`blue-sharc.exe` tooling should speed up TinyOS's own development/deployment onto devices like a Raspberry Pi 5.
   - The concept of "spoors" should be universal, borrowed from `C:\Code\Sharc.Workspace\Sharc.Blue`.

## What this session did

1. **Researched `C:\Code\Sharc.Workspace\Sharc.Blue` directly** (read-only, via a dedicated research agent) rather than guessing at any of the three objectives:
   - **Spoor** is real and precisely specified: a 64-bit, fixed-size, hierarchically bit-packed audit/action record (`CAT|WHO|ACT|OUT|TARGET|COST` — 4/4/4/4/16/32 bits), implemented in parallel Rust (`spoor.rs`) and C# (`Spoor.cs`), with an explicit doctrine ("stamp immediately at execution point," never buffered, never a `String` field, bit layout frozen).
   - **"blue.atoms" doesn't literally exist** — the real C# façade is `blue.atom` (singular, `Sharc.Blue.Atom`), a thin CLI wrapper over the atom catalog. **`blue-sharc.exe` is real and already built** (confirmed on disk, 8MB, `Sharc.Bluekind/target/gate-fast/blue-sharc.exe`) — but its actual function is an **MCP sidecar/context engine for LLM tool-calling over stdio/IPC**, not an Ollama-like inference runtime. This directly contradicted `FEAT-P0-05.md`'s existing description (dating to Handover 11), which needed correcting — see below.
   - **No Raspberry Pi 5 / ARM64 deployment tooling exists in `Sharc.Blue`** to import wholesale — that assumption, if held, doesn't hold; any RPi5 deploy tooling would need to be built fresh for TinyOS, though the *pattern* (a small, fast, single-binary CLI front end) is reusable.
   - **`Sharc.Blue` has a real, documented IPC doctrine**: loopback TCP was explicitly retired as an IPC transport ("S74 W7 forbade loopback TCP attack-surface") in favor of named pipes (Windows) / Unix domain sockets (Linux/macOS), with one narrow, allowlisted exception (a localhost-TCP bridge to a C# worker subprocess).
2. **Asked three clarifying questions** (via `AskUserQuestion`) where the research left genuine, user-level decisions open, all answered with the recommended option: correct the `blue-sharc.exe` framing now; scope spoor as a new Feature inside `EPIC-P0` (not a standalone Epic or bundled with IPC); adopt `Sharc.Blue`'s no-loopback-TCP doctrine for local IPC while treating a real TCP/IP stack as a separate, later Feature for actual network deployment.
3. **Corrected `FEAT-P0-05.md` and `STORY-P0-05-04.md`**: removed the "Ollama-like local-inference runtime" framing for `blue-sharc.exe`, replaced with an accurate description (MCP sidecar/context engine), and removed the erroneous `G-AI-1` (local inference hosting) goal claim from `STORY-P0-05-04.md` — `blue-sharc.exe` running under TinyOS proves process/executable compatibility (`G-PC-1`–`G-PC-4`) only, not anything about inference hosting, which remains Phase 6's own, separate, later claim. Fixed the matching `traceability-matrix.md` row.
4. **Added and implemented `FEAT-P0-06` (Spoor)**, inside `EPIC-P0` per the answered scoping question:
   - New `kernel::spoor` module: the packed `Spoor` type over `Category`/`Actor`/`Action`/`Outcome` enums, `stamp`/`decode` constructors, typed field accessors — all `const fn`, no heap, no allocation.
   - **What's borrowed vs. TinyOS's own**, decided and documented explicitly in the module's own doc comment: the 64-bit layout (field widths/positions) and `Outcome`'s vocabulary (ok/empty/chose/capped/failed/skipped/superseded/partial) are adopted verbatim from `Sharc.Blue`, since both are genuinely domain-neutral. `Category`'s and `Action`'s specific variants are TinyOS's own (scheduling/lock/wcet/dispatch/exec/memory/boot; create/boost/restore/block/select/overrun/reset-budget) — reusing `Sharc.Blue`'s literal render/mutate/classify category set would make no sense for a kernel, the same way two projects sharing a network header format still define their own port assignments.
   - 7 new host tests, including an exhaustive 12,544-combination round-trip property test and four field-specific adversarial rejection tests (one per nibble field, each verified independently).
   - `STORY-P0-06-02` (append-only journal writer) specified but not implemented — the natural next Story.
5. **Specified (not implemented) `FEAT-P0-07` (Local IPC)**: message channels and shared-memory grants between two tasks, explicitly scoped to **never** create a network-addressable socket (loopback included) — the doctrine researched from `Sharc.Blue` adopted deliberately, per the answered clarifying question. Two Stories specified (`STORY-P0-07-01` message channel, `STORY-P0-07-02` shared-memory grant), neither implemented this session.
6. **Recorded a real TCP/IP stack's placement** in `goals/epics/backlog.md`: `EPIC-P3` (Connectivity), layered above `G-HW-2`'s network-class-driver goal, explicitly separate from `FEAT-P0-07`'s local-IPC scope — plus a note that Raspberry Pi 5's existing Tier 1 placement (`README.md`'s Target Hardware & Test Matrix, "Phase 3 onward") is worth reconciling against the new deploy-tooling objective's urgency when `EPIC-P1_5` (Deploy tooling) is actually decomposed.

## Key decisions worth restating

- **"Borrow the format, not the vocabulary."** The single most important design decision this session made for `FEAT-P0-06`: `Sharc.Blue`'s spoor bit layout and outcome vocabulary are genuinely generic and worth adopting verbatim; its category taxonomy (render/mutate/classify/etc.) is specific to what `Sharc.Blue` actually does and would be nonsensical for a kernel. Every future spoor-adjacent Story should preserve this distinction rather than reflexively copying more of `Sharc.Blue`'s specifics than the format itself warrants.
- **Corrections were made to existing docs, not left standing.** `FEAT-P0-05.md`/`STORY-P0-05-04.md` had carried an inaccurate technical claim about `blue-sharc.exe` since Handover 11 (11 sessions ago) — once the research surfaced the discrepancy, both docs were corrected in place with an explicit "Correction (2026-07-26)" note explaining what was wrong and why, rather than quietly fixed with no trace or left inconsistent with the newly-verified facts.
- **Genuine ambiguity was surfaced as questions, not resolved by guessing.** Three real decisions (blue-sharc.exe framing, spoor's structural placement, TCP/loopback doctrine) had defensible alternatives; each was asked via `AskUserQuestion` with a recommended default rather than silently picked, consistent with this session's general practice of asking when a choice is genuinely the user's to make.

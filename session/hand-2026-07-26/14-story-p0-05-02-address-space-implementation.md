# Handover 14 — `STORY-P0-05-02` Implemented and Verified: Process Address-Space Creation and Section Mapping

Follows: [`13-story-p0-02-02-context-switch-implementation.md`](13-story-p0-02-02-context-switch-implementation.md), which implemented `STORY-P0-02-02` (context switch) and named it as the single blocker standing between `FEAT-P0-05` and its remaining three Stories. This handover picks up that mandate directly and implements `STORY-P0-05-02`.

## What this session did

1. **Implemented x86_64 page-table construction** in a new module, `os/src/hal-x86_64/src/paging.rs`: a 4-level (PML4/PDPT/PD/PT), 4KiB-granularity `PageTable` type, `map_4k` (walks/creates missing intermediate levels via a caller-supplied `FrameAllocator` trait, Dependency Inversion — this module has no dependency on `kernel::mem::Pool` or any other specific allocator), and `translate` (reads a mapping back without creating anything). Pure `u64`-array manipulation, no target-specific instructions, so it's host-testable directly (`cargo test -p hal-x86_64 --lib`) — 7 new tests.
2. **Implemented `exec::address_space`** (new module, `os/src/exec/src/address_space.rs`): `validate_sections` (pure — checks pairwise section overlap and collision with the kernel's own identity-mapped region `[0, 0x4000_0000)`, no page table touched) and `AddressSpace<'a, FRAMES>` (validates, then maps every section via `hal_x86_64::paging`, backed by a `Pool<PageTable, FRAMES>`-based `FrameAllocator` the caller owns and passes in by reference — an `AddressSpace` must never move once its page-table cross-links are populated, so it borrows rather than owns its backing storage, mirroring `context.rs`'s/`context_switch_fixture.rs`'s own `static`-based approach to the same constraint). `Drop` resets the PML4 and replaces the frame pool with a fresh one — the assignment drops the old `Pool` in place first, reclaiming every occupied slot via `Pool`'s own existing `Drop` discipline, so `AddressSpace` needs no per-handle bookkeeping of its own for symmetric teardown. 7 new host tests.
3. **Added `kernel::mem::Pool::get_mut`** (`os/src/kernel/src/mem.rs`) — returns a stable `&mut T` into an occupied pool slot without freeing it, needed by the `Pool`-backed `FrameAllocator` to hand out page-table frame addresses. 2 new tests.
4. **Relocated `boot.rs`/`qemu_exit.rs` from `kernel` into `hal-x86_64`** — a structural prerequisite, not scope creep: `exec` needs `kernel::mem::Pool`, which rules out `kernel`'s own binary depending back on `exec` for a Tier 0 fixture (a cyclic crate dependency). `exec` got its own `exec-fixture` `[[bin]]` (`os/src/exec/src/fixture_main.rs`), and the shared PVH boot-entry glue moved to `hal-x86_64` so both binaries (and any future one) can reuse it — `ENTRY(_start)`/`KEEP(...)` in `targets/x86_64-tinyos.ld` pull the object code out of whichever rlib it's compiled into, regardless of source crate. `boot`/`qemu_exit` are gated `#[cfg(not(target_os = "windows"))]` (ELF-specific `global_asm!`, assembles fine on the real target and on ELF-native hosts like this project's Linux CI runner, not on a Windows dev machine's COFF-flavored assembler) — the same reason this code was never buildable via a bare host `cargo build`/`clippy` on Windows even before this move.
5. **Added the Tier 0 QEMU fixture**: `xtask qemu-x86_64 --fixture=address-space` now builds and boots `exec`'s `exec-fixture` binary instead of `kernel`'s — `xtask`'s `qemu_x86_64` function was generalized to take a `(package, binary)` pair rather than hardcoding `kernel`. The fixture exercises the real `AddressSpace::create` end to end: maps two sections with distinct permissions and reads their PTE bits back, rejects an overlapping section set and a kernel-region-colliding one without mapping anything, and runs 32 create/drop cycles against a 16-frame pool without exhausting it.
6. **Fixed a real bug discovered mid-session**: the QEMU fixture initially triple-faulted (register trace showed `RSP=0`, `#PF` on push) — the 64KiB boot stack `STORY-P0-01-01` sized for the walking skeleton is too small for this Story's workload (4096-byte `PageTable` values passed by value through several call layers in an unoptimized dev-profile build). Bumped to 1MiB in `hal_x86_64::boot`, with a comment explaining why, since this affects every binary that reuses this boot glue.
7. **Verified**: all four QEMU boot paths (`qemu-x86_64` plain, `--fixture=broken-boot`, `--fixture=context-switch`, `--fixture=address-space`) pass. `cargo test --workspace --lib`: 66/66 (up from 61). `cargo fmt --check` clean. `cargo clippy --workspace --all-targets -- -D warnings` clean for every host-buildable target; `kernel`'s and `exec`'s `[[bin]]` targets can't be host-clippy'd on this Windows dev machine at all (pre-existing limitation, not a regression — verified as a substitute via `cargo clippy --target targets/x86_64-tinyos.json` on both bins, clean). `cargo run -p xtask -- check-crate-sizes --ceiling=20000`: all crates comfortably under, `kernel` actually shrank (774 → 630 lines, `boot.rs`/`qemu_exit.rs` moved out) while `hal-x86_64` grew correspondingly. `cargo run -p xtask -- governance-fixture-test` unaffected. Filed `REPORT-2026-07-26-09`.
8. **Updated all V&V docs**: `STORY-P0-05-02.md` to `Status: Verified` with its previously-"draft" acceptance criteria finalized against what was actually implemented; `TEST-P0-05-02-A.md` updated with an explicit revision note (see below) and a passing Report link; `FEAT-P0-05.md` to "2/4 Stories Verified"; `EPIC-P0.md`'s `FEAT-P0-05` row; `goals/traceability-matrix.md`'s `STORY-P0-05-02` row and session cross-reference table; `goals/index.html`'s stat tiles (9/18 → 10/18 Stories, 8/12 → 9/12 Tests) and the `FEAT-P0-05` table row; `session/hand-2026-07-26/index.html`'s entry list.

## What this session deliberately did not do

- **Did not load the constructed page-table tree into `CR3`, and did not induce/catch a real `#PF`.** The original `TEST-P0-05-02-A` specification asked for "a page in a read-only section faults... if code under test attempts to write to it" — this needs an IDT/exception-handling subsystem this kernel doesn't have yet, which is a real prerequisite, not a corner to cut. Permission correctness is instead verified deterministically by reading the constructed PTEs back. Recorded explicitly in both `STORY-P0-05-02.md` (acceptance criterion 1) and `TEST-P0-05-02-A.md` (revision note) so it isn't mistaken for an oversight later.
- **Did not implement demand-zero/`.bss`-style section backing.** `AddressSpace::create` maps file-backed pages only (`section.file_size >= section.virtual_size` implicitly required by using `max(virtual_size, file_size)` as the mapped extent while requiring the whole extent be within `image_bytes`); a section needing zero-fill beyond its file data is out of scope.
- **Did not implement a general-purpose physical frame allocator.** Page content is backed directly by the caller's `image_bytes` slice (no copy) — simple, but means `image_bytes` must itself start on a page boundary (validated, `AddressSpaceError::Misaligned` if not) and stay alive and unmoved for the `AddressSpace`'s whole lifetime.
- **Did not implement `STORY-P0-05-03`/`-04`** (Win32 API shim, end-to-end `blue-sharc.exe`) or `STORY-P0-02-03`/`-04` (priority inheritance, WCET enforcement). `STORY-P0-05-03` is now unblocked and the natural next pick for `FEAT-P0-05`.
- **Did not source or vendor a real `blue-sharc.exe` fixture.** Unrelated to this Story but still open from Handover 11/12 — unchanged.

## Key decisions worth restating

- **`exec` depends on `kernel` (for `mem::Pool`) and `hal-x86_64` (for `paging`), one-directionally — `kernel` never depends on `exec`.** This is the load-bearing constraint behind two decisions this session made: `exec` needed its own `[[bin]]` (`exec-fixture`) for its Tier 0 fixture rather than another `kernel` Cargo feature, and the shared boot-entry glue moved to `hal-x86_64` (which both `kernel` and `exec` already depended on, or now do) rather than staying `kernel`-private or moving into `kernel`'s own library.
- **An `AddressSpace` borrows its backing storage rather than owning it, because it must never move once populated.** The intermediate PDPT/PD/PT frames are referenced from `pml4` by raw address; if the struct holding `pml4` moved (e.g. returned by value with no guaranteed NRVO), those addresses would go stale. Callers place `pml4`/`frame_pool` in a `static` or an unmoved stack local and pass `&mut` references in — the same discipline this codebase already uses for `Context`/stack storage, for the identical underlying reason.
- **Symmetric teardown comes from `Pool`'s existing `Drop`, not new bookkeeping.** `AddressSpace::drop` does `*frame_pool = Pool::new()`, which first drops the old `Pool` in place (freeing every occupied slot) before writing the fresh one — no handle-tracking needed in `AddressSpace` itself.
- **The 64KiB→1MiB boot-stack bump was found empirically, not guessed.** QEMU's `-d int` trace made the failure mode (`RSP=0`, `#PF` on push — a stack overflow, not a toolchain bug) unambiguous once captured; worth remembering as a debugging technique for any future Story that trips a similarly opaque triple-fault.

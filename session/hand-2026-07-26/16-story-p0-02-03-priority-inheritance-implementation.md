# Handover 16 — `STORY-P0-02-03` Implemented and Verified: Priority Inheritance on Lock Contention

Follows: [`15-story-p0-05-03-win32-shim-implementation.md`](15-story-p0-05-03-win32-shim-implementation.md). `STORY-P0-05-04` (the natural next `FEAT-P0-05` Story) is blocked on sourcing a real `blue-sharc.exe` build — not something this session can do. ## What this session did

1. **Added `Scheduler::priority_of`/`set_priority`** (`os/src/kernel/src/sched.rs`) — thin accessors over the existing `Pool<Tcb, N>::get_mut`, reading and mutating a live task's current priority. `set_priority` is what a lock's priority-inheritance boost (and its later restore) actually calls.
2. **Implemented `kernel::lock::PriorityInheritingLock`** (new module, `os/src/kernel/src/lock.rs`): `try_lock(scheduler, task, task_priority)` grants the lock if free; if held by a different task, boosts that holder's priority to `task_priority` when it's higher (recording the holder's pre-boost priority the *first* time contention boosts it, so repeated escalating contention from multiple waiters still restores to the original value, never an intermediate one), and reports contention via `Err(LockError::AlreadyLocked)`. `unlock(scheduler, task)` restores the holder's original priority (a no-op if the lock was never contended while held) and frees the lock; rejects a non-holder's unlock attempt and a holder's own reentrant lock attempt.
3. **7 new host tests**, TDD-first: the classic three-task priority-inversion scenario (low holds, high contends, an uninvolved medium task's priority is what must be outranked after the boost); deterministic restore on unlock, including after repeated escalating boosts; a lower-priority contender never disturbing the holder; rejection of a non-holder's unlock and a holder's reentrant lock.

## What this session deliberately did not do

- **Did not verify that priority inheritance actually prevents starvation under live, running scheduling.** This kernel has no ready-queue/priority-based dispatch loop yet — `kernel::context::switch` is a raw two-context primitive invoked explicitly by whoever calls it (per `STORY-P0-02-02`), not an autonomous scheduler that picks the next task to run by priority. There is no live "medium preempts low" scenario to run on any tier yet. This Story proves the bookkeeping half of priority inheritance exhaustively (contention boosts the holder; release restores it deterministically) but the *behavioral* half needs a real dispatcher — flagged explicitly in `STORY-P0-02-03.md`'s new scope-resolution note and `kernel::lock`'s own doc comment, not silently assumed solved by the bookkeeping alone.
- **Did not add a Tier 0 QEMU fixture.** Unlike `STORY-P0-02-02`/`-05-02`/`-05-03`, this Story's logic is pure (`kernel::sched`/`kernel::lock`, no `unsafe`, no register/memory-layout dependency) — entirely host-testable, mirroring `STORY-P0-02-01`'s own precedent of no separate Tier 0 requirement.
- **Did not implement any blocking/parking of a contending waiter.** `try_lock` reports contention via `Err`, it doesn't block the caller until the lock frees — actually parking a task pending a wakeup is a dispatcher responsibility this kernel doesn't have yet, the same missing piece as the point above.
- **Did not implement a priority-ceiling protocol as an alternative.** The Story's description named it as an option ("priority inheritance... or a documented priority-ceiling equivalent"); this session implemented inheritance only, the more direct match for the acceptance criteria as drafted.
- **Did not handle multi-lock interaction.** `PriorityInheritingLock`'s bookkeeping is correct in isolation per-lock; a task holding several such locks simultaneously, each independently contended (and the deadlock-avoidance ordering real priority-inheritance protocols also need for that case), is out of this Story's scope.
- **Did not implement `STORY-P0-02-04`** (WCET budget enforcement) — the last remaining Story for `FEAT-P0-02`, now unblocked, and likely to run into the exact same missing-dispatcher constraint this Story did (enforcing a WCET budget by preempting an over-budget task also needs a real scheduler loop, not just bookkeeping).
- **Did not implement `STORY-P0-05-04`** (end-to-end `blue-sharc.exe`) — still blocked on sourcing a real binary, unchanged from Handover 11/12/15.

## Key decisions worth restating

- **The missing ready-queue/priority-based dispatcher is now a concrete, twice-surfaced prerequisite.** `STORY-P0-05-02`'s handover already named the missing IDT/exception-handling subsystem as a named gap; this session surfaces a second, independent one — no autonomous scheduler loop exists to actually run tasks by priority order, only the raw `context::switch` primitive plus (now) priority/lock bookkeeping. Both `STORY-P0-02-03` (this Story) and `STORY-P0-02-04` (WCET enforcement, next) can only prove their bookkeeping halves without it. Building that dispatcher is likely worth scoping as its own Story before either `-04` or a deeper pass at `-03`'s behavioral guarantee is attempted.
- **The boost-restore design keeps exactly one "original priority" per lock, set only on the *first* contention that boosts it.** This is what makes `repeated_boosts_still_restore_the_original_priority_on_unlock` correct: a second, higher-priority waiter's contention re-boosts the holder further but doesn't overwrite the recorded original, so a single `unlock` always lands back at the true pre-contention value regardless of how many times it was boosted in between.
- **This lock is deliberately not reentrant.** A holder's own second `try_lock` call is rejected the same way a different task's contention is, rather than silently granted (which would need recursive-lock-count bookkeeping this Story didn't need to add) or left to deadlock.

## What this session deliberately did not do

- **Did not implement `STORY-P0-02-02`/`-03`/`-04` or `STORY-P0-04-02`/`-03`.** All five are natural next Stories now that QEMU is confirmed working end to end (including a real ACPI-derived topology, which `STORY-P0-04-02`'s APIC bring-up will need), but each is its own unit of TDD work and none were started here — scope discipline, not a blocker.
- **Did not attempt to make the RSDT-only branch of ACPI discovery host-testable end-to-end.** RSDT entries are inherently 32-bit physical addresses (why ACPI 2.0 introduced the 64-bit XSDT); a 64-bit host's real stack addresses don't fit in `u32`, so a host-side "real pointer" end-to-end test for that branch would either crash (as one draft test did, diagnosed and removed) or require faking data at a low fixed address a host process can't control. The branch's parsing logic is still covered by a pure host unit test (`parses_rsdt_entries_as_widened_addresses`); its `unsafe` boundary is Tier 0-only, documented as such in the test module rather than silently under-tested.
- **Did not add a serial console driver.** Diagnosing the `hvm_start_info.rsdp_paddr` issue (below) was done via single-shot `isa-debug-exit` writes carrying diagnostic codes across separate rebuild-and-boot cycles, since the exit device terminates the VM on every write and can't be used as a sequential print console. A real serial driver would make future kernel debugging much faster and is worth prioritizing, but wasn't in scope for this Story.

## Key decisions worth restating

- **QEMU's PVH direct-kernel-boot loader does not populate `hvm_start_info.rsdp_paddr`**, despite the Xen PVH spec documenting that field as the RSDP's physical address. Discovered empirically (not assumed) by bisecting with diagnostic `isa-debug-exit` codes: confirmed `kernel_main` was reached with a non-zero `start_info_paddr`, confirmed the `hvm_start_info` magic matched, then found `rsdp_paddr` itself read as zero. `hal_x86_64::acpi::discover_topology` now falls back to the classic BIOS-era EBDA/ROM signature scan (`find_rsdp_via_bios_scan`, ACPI spec 5.2.5.1) whenever the PVH-provided address is zero, since QEMU places its generated ACPI tables at those legacy addresses regardless of boot protocol. This is exactly the kind of thing `STORY-P0-04-01`'s acceptance criterion 3 ("verified against QEMU's real tables, not a hand-crafted fixture only") exists to catch — a fixture-only implementation would have shipped with a codepath that silently never worked under the kernel's actual boot protocol.
- **`boot.rs` now passes a real argument to `kernel_main`** (`extern "C" fn() -> !` → `extern "C" fn(u64) -> !`), the first boot-path signature change since `FEAT-P0-01`. `EBX` (the PVH-provided `hvm_start_info` pointer) is moved into `EDI` immediately before `call kernel_main`, verified safe because no instruction between `_start` and that point touches `EBX` (the page-table/GDT setup only ever uses `EAX`/`ECX`/`EDX`) — documented inline in `boot.rs` so a future contributor modifying that setup code knows not to clobber it silently.
- **The two Stories were split across a subagent and direct work by risk profile, not by arbitrary assignment**: `STORY-P0-02-01` is pure host-testable logic with a well-established pattern to follow (`mem.rs`'s `Pool<T, N>`) — low risk to delegate. `STORY-P0-04-01` required real-hardware-adjacent debugging with tight iteration loops (rebuild → boot → interpret exit code → adjust) — kept in the main session rather than delegated, since diagnosing the `rsdp_paddr` issue needed direct judgment calls at each step, not a single up-front task description.

## What this session deliberately did not do

- **Did not build a dispatcher/timer loop in `main.rs`.** That's a materially larger undertaking (a preemptive timer/IDT this kernel has never had — `STORY-P0-05-02`'s own named gap) than "wire a spoor consumer" as posed; wiring `kernel::wcet` the same scoped way `kernel::lock` was wired in `STORY-P0-06-03` was the interpretation consistent with existing precedent and the menu option offered.
- **Did not add a `SpoorJournal<N>` capacity constant or a D11-G09/D11-G10 footprint measurement.** Same reasoning as `STORY-P0-06-03`: no dispatcher/timer is wired into `main.rs` yet, so there is still no real, concrete production `N` to measure against the performance catalogue's guardrails. This remains the next natural step once a real caller exists, not before.
- **Did not touch `kernel::sched`, `kernel::dispatch`, or `kernel::lock`'s own production logic.** `kernel::wcet::record_tick`/`reset_budget_window` have no existing caller in `kernel::dispatch` (unlike `kernel::lock`, which `dispatch.rs`'s own test already exercised via a real dispatch round) — so unlike `STORY-P0-06-03`, no other module's test needed updating to thread the new journal parameter through.
- **Did not add a production call site anywhere.** Same bar `STORY-P0-06-03` and `kernel::lock`'s own `STORY-P0-02-03` were held to: host tests exercise the real code path, not a mock, but nothing at boot calls it yet.

## Key decisions worth restating

- **Interpreted "wire a real spoor consumer" as the scoped, host-tested unit `STORY-P0-06-03` already established, not as "build the missing dispatcher/timer infrastructure."** The latter is a distinct, much larger piece of work (`FEAT-P0-02`'s own still-open structural gap) that the "Immediate next steps" list in Handover 23 named separately and didn't ask for; conflating the two would have silently expanded scope well beyond what was requested.
- **The journal remains a parameter, never a field either `record_tick` or `reset_budget_window` owns.** Same Dependency Inversion discipline as `kernel::lock`'s `STORY-P0-06-03` and `kernel::wcet`'s own pre-existing `OverrunHandler` pattern — no capacity `N` is picked here, so wiring in a real, sized journal later remains additive.
- **Only budget-*boundary-crossing* events are stamped, not every tick.** Mirrors `kernel::lock`'s "only priority-mutating events" discipline exactly: a within-budget tick attributes consumption (state does change) but isn't a notable audit event on its own, the same way a non-boosting `try_lock` isn't. Stamping every tick would make the journal a call-count log at exactly the frequency `FEAT-P0-06`'s own description warns against treating spoor as.
- **`reset_budget_window`'s COST records what was cleared, not the post-reset value (always 0).** A restore's `COST` (in `kernel::lock`) names the value returned to, which is informative; for a reset, the informative number is what got wiped, not the trivial always-zero result — so `reset_budget_window` captures `ticks_consumed` before clearing it, then stamps only if that prior value was nonzero.
- **Added two test functions this time, unlike `STORY-P0-06-03`'s "no new test functions" discipline.** `STORY-P0-06-03` could extend existing scenarios because `STORY-P0-02-03`'s own test suite already covered every relevant boost/restore/no-op case. `kernel::wcet`'s pre-existing suite had no test asserting `reset_budget_window`'s no-op or fail-closed paths at all (only `record_tick`'s fail-closed case existed) — those two gaps needed genuinely new tests, not just new assertions on existing ones, to reach the same coverage bar.

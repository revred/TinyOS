## What this session did

1. **Corrected the "blocked on sourcing a real binary" premise.** `Sharc.Workspace/Sharc.Blue/Sharc.Bluekind/target/gate-fast/blue-sharc.exe` — the exact path `STORY-P0-05-04.md` names — already exists (8,254,976 bytes). Nobody had gone back to use it; that was unclaimed work, not a real blocker.
2. **Found, before writing code, that the Story's own acceptance criteria as drafted were infeasible this session.** Pulled the real binary's import table: 220 named/ordinal imports across 14 DLLs (`KERNEL32.dll` 109 functions — threads, named pipes, memory-mapped files, timers; `WS2_32.dll` sockets; `advapi32`/`secur32`/`crypt32` security descriptors/TLS/certificate stores; `ntdll` raw syscalls; `VCRUNTIME140.dll` C++ exception unwinding; the `api-ms-win-crt-*` family's full CRT init sequence, called before `main` even runs). Executing this binary's real entry point needs a per-task `CR3` switch, an IDT/interrupt/exception-handling subsystem, and threads — none of which exist. Surfaced this to the user rather than attempting it and either failing silently or burning the session on an intractable rabbit hole.
3. **Found a second, independent blocker while investigating the first**: `AddressSpace::create`'s original zero-copy mapping required every section's on-disk `file_offset` to be page-aligned. `blue-sharc.exe`'s real sections use the standard 512-byte `FileAlignment` (none of its 6 real `file_offset` values are 4096-aligned) — a fact true of essentially any real-world PE, not specific to this binary. x86-64 page tables can only ever map whole aligned physical pages, so this is a hardware constraint, not a design gap to route around cheaply.
4. **Redefined `STORY-P0-05-04`'s acceptance criteria with the user before implementing**, through several rounds of scoping discussion:
   - AC1 (process entry + heap allocation) redefined to: the real image's header/sections/import table parse correctly, its real sections map correctly (including the real `.bss` case), its real import table is correctly *rejected* by this Phase 0 shim's 9-call allowlist (220 real imports vastly exceeds it — the security gate working as designed, not a failure), and `HeapAlloc` specifically resolves and succeeds through the capability-mediated path when granted. No jump into the image's own machine code.
   - The file-alignment gap is fixed generically in `AddressSpace::create` (a copy-based mapper, tolerating any real alignment) rather than by preprocessing the fixture file — preprocessing would have violated the Story's own "never patched to make it work" principle.
   - **New direction from the user**: TinyOS should support a native, page-aligned executable container ("TXE") as a real, first-class capability, not just an implementation detail dodging one Tier 0 fixture's alignment problem. Scoped as a new Feature (`FEAT-P0-08`) with its own Story (`STORY-P0-08-01`), rather than silently building it as unlabeled fixture-prep code.
5. **Implemented `AddressSpace::create`'s copy-based generalization** (`os/src/exec/src/address_space.rs`): takes a new `staging: &mut [u8]` parameter; every mapped page is zero-filled, then whatever falls within `[0, file_size)` of the section's own file-backed range is copied in — one mechanism uniformly handling both the file-alignment gap and a section whose `virtual_size` exceeds `file_size` (`.bss`). New `AddressSpaceError::SectionDataOutOfBounds`/`StagingExhausted` variants. Both existing QEMU fixtures (`exec-fixture`, `win32-shim-fixture`) and `win32_shim.rs`'s host tests updated to pass a staging buffer.
6. **Implemented `win32_shim::heap_alloc`** (`os/src/exec/src/win32_shim.rs`): mirrors `write_file`/`read_file`'s own "report success, no real backing yet" precedent — checks the capability policy, returns the requested size as a stand-in handle when granted.

## What this session deliberately did not do

- **Did not execute `blue-sharc.exe`'s real entry point.** Its own C runtime calls dozens of Win32/CRT functions (TLS setup, exception tables, environment init) before `main` runs, spanning 220 imports across 14 DLLs — several more Features' worth of work (CR3 switching, an IDT, threads, socket/crypto/security shims), not attempted here.
- **Did not build TXE security scanning, code-signing, or sandboxing.** Recorded as a vision in `goals/epics/backlog.md` under `EPIC-P5` (needs the real `aci` capability engine, likely a real IDT for fault-isolated sandbox teardown), not implemented.
- **Did not build a `.ton` shared-library format.** Named only, per the same backlog note — TinyOS has no dynamic-library loader at all today.
- **Did not add a production call site.** `kernel`'s own binary still doesn't link `exec` — the same "no dispatcher wired into `main.rs`" gap `STORY-P0-06-03`/`-04` already named for spoor.

## Key decisions worth restating

- **Surfacing infeasibility before implementing, twice in a row, rather than quietly declaring success or silently narrowing scope.** First for "execute the real entry point" (220 real imports, no CR3/IDT/threads), then for "map the real sections zero-copy" (512-byte FileAlignment vs. 4096-byte page granularity) — both are facts about the real binary and the real hardware, not judgment calls to route around without saying so.
- **A TXE repacks section *layout*, never the image's own logical contents.** Every RVA (including the import directory's) is untouched — the packer only patches the section table's own file-offset/size fields, so `exec::pe::parse` needed zero changes to consume its output.
- **`AddressSpace::create`'s copy-based generalization stays even though the TXE fixture no longer strictly needs it.** It's independently correct engineering (proven by its own new tests) that makes `AddressSpace` tolerate any real-world PE, not just this one, pre-packed or not.
- **TXE was elevated from "implementation detail" to a named Feature at the user's explicit direction**, since a reusable, native packaging format is valuable for however TinyOS ends up distributing programs in production — not built simply to dodge one fixture's alignment problem.

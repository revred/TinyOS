  15. 15STORY-P0-05-03 implemented and Verified: capability-scoped Win32 API compatibility shim

Implemented exec::win32_shim: a closed Api allowlist (resolve, the single designated dispatch point) checked against every import STORY-P0-05-01's parser found (check_imports, load-time rejection, never a runtime stub); a standalone CapabilityPolicy trait standing in for the not-yet-existing aci crate (Phase 5), with the migration path documented in the module's own doc comment; and two representative capability-scoped, bounds-checked call implementations (write_file/read_file) that validate every buffer argument against the calling process's own AddressSpace — page by page, via AddressSpace::translate — before any access, since this kernel still has no IDT/exception-handling subsystem to catch a real #PF.   16. 16STORY-P0-02-03 implemented and Verified: priority inheritance on lock contention

    Continued autonomously into FEAT-P0-02's next unblocked Story (STORY-P0-05-04 remains blocked on sourcing a real blue-sharc.exe). Implemented kernel::lock::PriorityInheritingLock: a lock that boosts its current holder's priority to a contending waiter's (via new Scheduler::priority_of/set_priority accessors) when contended by a higher-priority task, and restores the holder's original priority deterministically on release — no path leaves a task permanently boosted, including after repeated escalating contention from multiple waiters. Surfaced and documented a real scope constraint: this kernel has no ready-queue/priority-based dispatch loop yet (context::switch is a raw two-context primitive, not an autonomous scheduler), so this Story proves the bookkeeping half of priority inheritance exhaustively but not the behavioral half (a real medium-priority task actually failing to preempt a boosted holder) — flagged as a concrete prerequisite for a future Story rather than silently assumed solved. 7 new host tests (the classic three-task inversion scenario, non-boosting contention, repeated boosts, non-holder unlock rejection, reentrant-lock rejection) — entirely host-testable, no QEMU dependency, mirroring STORY-P0-02-01's own precedent. 83/83 host tests passing workspace-wide (up from 76), all five QEMU fixtures unaffected, fmt/clippy clean — new TEST-P0-02-03-A, REPORT-2026-07-26-11. EPIC-P0 now at 12/18 Stories Verified. Unblocks STORY-P0-02-04 (WCET budget enforcement), which will likely face the same missing-dispatcher constraint.

  17. 17STORY-P0-02-04 implemented and Verified: WCET budget enforcement — completes FEAT-P0-02

    Continued autonomously into the last remaining FEAT-P0-02 Story. Implemented kernel::wcet::record_tick: attributes ticks to a task and checks cumulative consumption against its declared WCET budget synchronously on every call — an overrun trips on the exact tick that crosses the budget, not retroactively, whether from several small ticks accumulating past it or one oversized tick — calling a new standalone OverrunHandler trait exactly once per detected overrun (the same Dependency-Inversion pattern win32_shim::CapabilityPolicy established for aci, here standing in for this kernel's not-yet-built watchdog/failsafe system). Hit the identical structural gap STORY-P0-02-03 already surfaced — no ready-queue dispatcher to drive detection on a real timer tick, and (newly surfaced) no real watchdog subsystem exists anywhere yet to hand a detected overrun off to — both documented as open prerequisites rather than silently assumed solved. 6 new host tests (in-budget, at-exactly-budget non-overrun, multi-tick accumulation, single-oversized-tick, unknown-task rejection, budget-window-reset recovery) — host-only, mirroring STORY-P0-02-01/`-03`'s precedent. 89/89 host tests passing workspace-wide (up from 83), all five QEMU fixtures unaffected, fmt/clippy clean — new TEST-P0-02-04-A, REPORT-2026-07-26-12. FEAT-P0-02 now fully Verified (4/4 Stories, structural gaps noted); EPIC-P0 at 13/18 Stories Verified.

  18. 18STORY-P0-02-05 (new) implemented and Verified: priority-ordered cooperative dispatch loop — closes STORY-P0-02-03's behavioral gap

    Continued autonomously. `STORY-P0-02-03` and `STORY-P0-02-04` had each independently named the identical missing prerequisite — no mechanism actually ran tasks in priority order, only bookkeeping about who should — strong enough a signal to add and implement a new Story for it immediately rather than deferring further. Implemented Scheduler::highest_priority_ready (new TaskState: Ready/Running/Blocked/Finished, `Pool::iter_occupied`/`PoolHandle::index` added to support enumeration) and kernel::dispatch::run_once, which actually switches into the selected task via the existing `context::switch` primitive. The flagship test constructs the classic three-task scenario with real context switches into real task functions (not simulated): without contention a real dispatch round picks the higher-static-priority medium task over low; after high contends for low's lock (boosting it via `STORY-P0-02-03`'s own `PriorityInheritingLock`), the next round switches into the now-boosted low instead; after release, a further round reverts to medium — closing `STORY-P0-02-03`'s own previously-unverifiable behavioral claim. Explicitly scoped as cooperative, not preemptive (still no timer/IDT), and does not touch `STORY-P0-02-04`'s separate timer/watchdog gap, which remains open. 7 new host tests (5 `sched`, 2 `dispatch`) — host-only, since `context_switch_asm` is `sysv64`-pinned and runs identically on the host toolchain. 96/96 host tests passing workspace-wide (up from 89), all five QEMU fixtures unaffected, `fmt`/`clippy` clean — new `TEST-P0-02-05-A`, `REPORT-2026-07-26-13`. `FEAT-P0-02` now 5/5 Stories Verified (one Story added mid-Feature); `EPIC-P0` at 14/19 Stories Verified.

  19. 19STORY-P0-03-02 implemented and Verified: compile-time pool-size configuration — completes FEAT-P0-03

Implemented kernel::capacities: a single, reviewable module consolidating the two pool/array capacities that actually had a real, concrete call site today — MAX_CPUS (previously a local const in main.rs) and EXEC_FRAME_POOL_CAPACITY (previously a FRAMES constant duplicated across exec's two Tier 0 fixture files) — plus a documented STATIC_MEMORY_BUDGET_BYTES and a const _: () = assert!(...) check proving a capacity that would overflow it fails the build (a compile-time error[E0080]), not a runtime allocation-failure path. FEAT-P0-03 now 3/3 Stories Verified; EPIC-P0 at 15/19 Stories Verified.

  20. 20New strategic direction: spoor, local IPC, deploy tooling

    The user gave three new strategic objectives (IPC/shared-memory/sockets/TCP-IP; using the sibling Sharc.Blue project's blue.atom/blue-sharc.exe tooling to speed up development/deployment onto devices like a Raspberry Pi 5; making "spoor" a universal concept borrowed from Sharc.Blue) and corrected a standing misframing: TinyOS is not a "hobby OS" but a serious project targeting data centers/local AI, UAVs, medical devices, edge devices, and consumer electronics, saved to memory. Researched Sharc.Blue directly (read-only) rather than guessing: confirmed spoor is a real, precisely-specified 64-bit bit-packed audit record (CAT/WHO/ACT/OUT/TARGET/COST), confirmed blue-sharc.exe is real and already built but is an MCP sidecar/context engine for LLM tool-calling, not an Ollama-like inference runtime as FEAT-P0-05.md/STORY-P0-05-04.md had incorrectly claimed since Handover 11, and confirmed Sharc.Blue has no Raspberry Pi/ARM64 deployment tooling to import wholesale but does have a real doctrine of rejecting loopback TCP for local IPC in favor of named pipes/Unix domain sockets. Corrected the blue-sharc.exe framing. Added and implemented FEAT-P0-06 (spoor): new kernel::spoor module, STORY-P0-06-01 Verified with a 12,544-combination round-trip property test; STORY-P0-06-02 (journal writer) specified only. Added (specified only) FEAT-P0-07 (local IPC: message channels + shared-memory grants), explicitly scoped to never create a network-addressable socket; a real TCP/IP stack recorded as a separate, later EPIC-P3 concern. 104/104 host tests passing workspace-wide (up from 97), all five QEMU fixtures unaffected, fmt/clippy clean — new TEST-P0-06-01-A, REPORT-2026-07-26-15. EPIC-P0 now spans 7 Features (23 Stories total, 16 Verified).

  21. 21STORY-P0-06-02 implemented and Verified: append-only spoor journal — completes FEAT-P0-06

    Continued directly from Handover 20's own next-step recommendation. Implemented kernel::spoor_journal::SpoorJournal<N>: a fixed-capacity, no-heap ring buffer of Spoor values — append never blocks, never panics, and overwrites the oldest entry once full rather than rejecting a new stamp; iter() reads back entries oldest-first correctly across both the not-yet-wrapped and wrapped cases. Each entry is stored as exactly its raw Spoor::to_bits() value (no intermediate representation), alongside a JOURNAL_MAGIC constant (b"SPOORJ01") identical to Sharc.Blue's own on-disk spoor journal magic, so a future storage-backed journal could serialize this buffer directly once TinyOS has a filesystem. 6 new host tests covering the full ring-buffer state space: not-yet-full, exactly-full, wrapped-once, wrapped-many-times, and the degenerate N=1 capacity boundary. 110/110 host tests passing workspace-wide (up from 104), all five QEMU fixtures unaffected, fmt/clippy clean — new TEST-P0-06-02-A, REPORT-2026-07-26-16. FEAT-P0-06 now fully Verified (2/2 Stories); one follow-up remains open per that Feature's own exit criteria — wiring a real subsystem (kernel::lock or kernel::wcet are natural candidates) to actually emit spoors, not yet done. EPIC-P0 now at 17/23 Stories Verified.

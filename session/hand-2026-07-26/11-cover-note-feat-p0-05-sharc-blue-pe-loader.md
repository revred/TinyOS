## The directive (this session, 2026-07-26)

Two new standing constraints, plus one new critical use case:

1. **Total OS image size ceiling.** The built TinyOS image — everything except drivers — fits within **8MB**. Recorded as `G-DX-8` in `SeedMVP.md` §3.6, with CI-enforcement language added to `agent/CODING_STANDARDS.md` (new "Total OS image size ceiling" section, mirroring the existing crate-size-ceiling section's structure and no-exceptions policy).
2. **"Unhackable," low-attack-surface-by-design as an explicit, checkable property** — not just a general aspiration already implicit in the README's security non-negotiables, but a property the new use case below is required to satisfy concretely (a small, explicitly-enumerated compatibility surface; no privileged bypass; a small auditable loader). Recorded as new Goal category `G-PC` (Process & Executable Compatibility), `SeedMVP.md` §3.7.
3. **Load and run `Sharc.Blue`'s `blue-sharc.exe`** (`Sharc.Bluekind/target/gate-fast/blue-sharc.exe` in the sibling project) as a native, "similarly executable like in Windows OS" process on TinyOS — explicitly framed as aligned with the Ollama use case (`blue-sharc.exe` is the sibling project's own Ollama-like local-inference runtime, already the architectural reference for TinyOS's Phase 6 mmap-based model-loading design per `docs/inference-architecture.md`). This is the concrete validation case behind `G-PC-1` through `G-PC-4`.

## Key decisions worth restating

- **This is explicitly not a general Windows compatibility layer.** `G-PC-2` and every Story built on it scope the API surface to exactly what `blue-sharc.exe` imports — an allowlist, closed by construction, where an unlisted import is a load-time rejection. This is the direct design response to "unhackable... security surface should be built to be easily defendable": a `kernel32`/`ntdll` reimplementation would be a permanently-growing, unauditable attack surface in direct tension with `G-DX-8`'s 8MB ceiling; a closed allowlist sized to one real, known binary is bounded and auditable by construction.
- **`STORY-P0-05-01` can start immediately, independent of the rest.** Unlike `-02` through `-04`, it has no dependency on `FEAT-P0-02`'s scheduler progress — it's pure parsing logic over an already-obtained byte slice, fully host-testable. A session without QEMU (like Handover 09's environment) could still make progress on this Feature by picking up `STORY-P0-05-01` alone.
- **The Story ordering intentionally puts the real end-to-end validation (`STORY-P0-05-04`) last, not first.** It would be possible to attempt "does `blue-sharc.exe` boot" as an early, coarse-grained smoke test — but that's exactly the failure mode `STORY-P0-04-01`'s Handover 10 encountered and had to debug blind (the `isa-debug-exit` port can't be used as a sequential console, so an undifferentiated end-to-end failure gives almost no diagnostic signal). Building `-01` through `-03` with their own dedicated Tests first means `-04`'s eventual failure (if any) is isolated to genuine composition problems, not "which of four subsystems is actually broken."

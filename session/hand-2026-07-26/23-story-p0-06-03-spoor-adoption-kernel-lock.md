## What this session deliberately did not do

- **Did not add a `SpoorJournal<N>` capacity constant or a D11-G09/D11-G10 footprint measurement.** No dispatcher is wired into `main.rs` yet (the same gap `kernel::lock`/`kernel::wcet` themselves have always had — see `kernel::lock`'s own module doc comment), so there is still no real, concrete production `N` to measure against the performance catalogue's image-footprint/working-memory guardrails. Adding one now would repeat exactly the speculative-capacity mistake `kernel::capacities.rs` warns against by name. This is the next natural step once a real caller exists, not before.
- **Did not wire `kernel::wcet`.** `FEAT-P0-06`'s exit criteria required *at least one* real subsystem, not both of the two named candidates. `kernel::wcet::record_tick`'s `Action::Overrun`/`Action::ResetBudget` vocabulary remains defined and unused — a natural second candidate if wanted, not required by anything currently open.
- **Did not add a production call site anywhere.** This Story proves the bookkeeping is genuinely wired (host tests exercise the real code path, not a mock), the same bar `kernel::lock`'s own `STORY-P0-02-03` was held to when it reached Verified with no dispatcher yet either — not that a running kernel currently emits spoors at boot.
- **Did not touch `kernel::wcet`, `kernel::sched`, `kernel::dispatch`'s own production logic** beyond threading a journal parameter through the one test that already exercised `PriorityInheritingLock` via a real dispatch round.

## Key decisions worth restating

- **Surfacing the "don't add a capacity with nothing consuming it" conflict before writing code, instead of implementing the originally-proposed footprint entry, was the right call** — the user's own project convention (`kernel::capacities.rs`'s doc comment) directly contradicted the first proposed next step, and asking rather than proceeding avoided introducing exactly the kind of speculative, ahead-of-need code this codebase's standards argue against elsewhere.
- **The journal is a parameter, never a field `PriorityInheritingLock` owns.** Mirrors `kernel::wcet::OverrunHandler`'s already-established Dependency Inversion pattern: `PriorityInheritingLock` (and, by the same reasoning, any future `kernel::wcet` adoption) picks no capacity, no concrete journal type — the caller supplies one sized for its own real use, so wiring in a production journal later is additive, not a signature rewrite.
- **Only priority-*mutating* events are stamped, not every call.** A journal recording every `try_lock`/`unlock` attempt (including no-ops) would be a call-count log, not an audit trail of what changed — the distinction this Story's acceptance criterion 3 makes explicit and tests directly (both no-op scenarios assert the journal stays empty).
- **No new test functions, only extended assertions on existing ones.** The spoor-emission property is inseparable from the exact scenarios `STORY-P0-02-03` already built (the three-task inversion case, the escalating-boost case, the no-op cases) — duplicating them as separate spoor-only tests would test the same code paths twice for no added coverage.

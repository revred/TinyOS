# Handover 12 — `STORY-P0-05-01` Implemented and Verified: Pure PE64 Image Parser (`os/src/exec/`)

Follows: [`11-cover-note-feat-p0-05-sharc-blue-pe-loader.md`](11-cover-note-feat-p0-05-sharc-blue-pe-loader.md), which specified `FEAT-P0-05` (decomposition, all four Test docs written test-first) but deliberately wrote no implementation code. This handover picks up that session's mandate: `STORY-P0-05-01`, the one Story in the Feature with no dependency on `FEAT-P0-02`'s still-not-started context-switch Story, is now implemented, tested, and Verified.

## What this session did

1. **Added a new workspace crate, `os/src/exec/`**, per `docs/mvp-delivery-strategy.md`'s crate map — added `"src/exec"` to `os/Cargo.toml`'s `members`, `Cargo.toml`, `src/lib.rs` (`#![cfg_attr(not(test), no_std)]`, `#![deny(missing_docs)]`, matching `hal-x86_64`'s split), and `src/pe.rs`.
2. **Implemented `pe::parse::<const SECTIONS: usize, const IMPORTS: usize>(bytes: &[u8]) -> Result<LoadDescriptor<SECTIONS, IMPORTS>, PeError>`** — a pure, `unsafe`-free PE32+ (64-bit only) image parser:
   - Validates the DOS header (`"MZ"`), `e_lfanew`, `"PE\0\0"` signature, COFF header (`Machine == IMAGE_FILE_MACHINE_AMD64`), and optional header (`Magic == IMAGE_NT_OPTIONAL_HDR64_MAGIC`) — every offset/length is `checked_add`/slice-bounds-checked against the actual byte slice before being trusted, mirroring `hal_x86_64::acpi`'s fail-closed discipline.
   - Parses the section table into `SectionDescriptor { virtual_address, virtual_size, file_offset, file_size, permissions }`, rejecting any section whose file offset + size exceeds the file's actual length, and rejecting (at parse time, not deferred) any section that requests both write and execute permission (`PeError::WriteExecuteSection`, `G-PC-1`'s W^X requirement).
   - Parses the import directory (Data Directory entry 1) into a flat list of `ImportEntry { dll_name, symbol_name }` pairs — named imports only; ordinal-only imports are recognized but not recorded (documented rationale on `IMAGE_ORDINAL_FLAG64`, since `blue-sharc.exe`'s expected import table is name-based per its `rust-lld`/`cargo-xwin` build target, `ADR 0002`).
   - `LoadDescriptor<const SECTIONS: usize, const IMPORTS: usize>` and the new `FixedBytes<const N: usize>` (a fixed-capacity byte buffer, the `no_std` stand-in for a bounded `String`) both follow the same caller-chosen-capacity pattern already established by `hal::topology::Topology<N>` and `kernel::mem::Pool<T, N>` — a file declaring more sections/imports/name-length than the caller's bound fails closed (`TooManySections`/`TooManyImports`/`NameTooLong`) rather than growing unbounded storage.
3. **Wrote 14 host unit tests** in `pe.rs`'s `#[cfg(test)] mod tests`, against a hand-crafted well-formed PE32+ fixture (one `.text` R+X section holding one import descriptor for `MYDLL.DLL`'s `MySymbol`) and deliberately corrupted variants of it — see `REPORT-2026-07-26-07` for the full list. Notably `no_truncation_length_panics` asserts every possible truncation length of the fixture (0 through its full length) either fails closed with a typed `PeError` or (only at the true full length) parses successfully — a lightweight stand-in for `cargo-fuzz` over the truncation dimension, since no fuzz-target infrastructure exists anywhere in this repo yet.
4. **Verified**: `cargo test -p exec --lib` (14/14 passing), `cargo build -p exec` (confirms the real `#![no_std]` path compiles, not just the `cfg(test)` host path), `cargo fmt -p exec -- --check` and `cargo clippy -p exec --all-targets -- -D warnings` (both clean), `cargo build --workspace`/`cargo test --workspace --lib` (every other crate's lib tests still pass unchanged), `cargo run -p xtask -- check-crate-sizes --ceiling=20000` (`exec` at 417 lines). Filed `REPORT-2026-07-26-07`.
5. **Updated all V&V docs**: `STORY-P0-05-01.md` and `TEST-P0-05-01-A.md` to `Status: Verified` with acceptance-criteria-by-criteria "Met" notes and a mapping from spec bullet to test function; `FEAT-P0-05.md` and `EPIC-P0.md` to "In progress — `STORY-P0-05-01` Verified locally"; `goals/traceability-matrix.md`'s `FEAT-P0-05`/`STORY-P0-05-01` row and session cross-reference table; `goals/index.html`'s stat tiles (7/18 → 8/18 Stories, 6/10 → 7/11 Tests) and `FEAT-P0-05` table row.

## What this session deliberately did not do

- **Did not source or vendor a real `blue-sharc.exe` fixture.** `STORY-P0-05-01`'s acceptance criterion 4 asks for "hand-crafted and real (`blue-sharc.exe`) fixture bytes" — only the hand-crafted half is done. Handover 11 flagged this as an open decision for `STORY-P0-05-04`, and this session had no new information to resolve it (vendored copy vs. built from the sibling project as part of CI), so it remains open — the parser itself is written to a real PE32+ specification (not fitted to the one fixture), so this is not expected to be a rewrite when a real binary is finally sourced, but it hasn't been checked against one.
- **Did not implement `STORY-P0-05-02` through `-04`.** These remain blocked on `FEAT-P0-02`'s `STORY-P0-02-02` (context switch), which is itself not yet started — exactly as Handover 11 called out. `STORY-P0-05-01`'s output (`LoadDescriptor`) is what `-02` (address-space/section mapping) will consume once unblocked.
- **Did not set up `cargo-fuzz`.** `agent/CODING_STANDARDS.md` calls for adversarial testing of parsers accepting external input; this repo has no fuzz-target precedent anywhere to mirror, and standing one up is an infrastructure decision independent of this Story's own acceptance criteria. `no_truncation_length_panics` is a deliberate, narrower interim substitute (documented as such in `REPORT-2026-07-26-07`) — it exhaustively covers truncation of one fixture, not arbitrary byte-level mutation.
- **Did not build the capability-scoped Win32 API shim's design.** Out of scope for this Story per its own acceptance criterion 3 ("resolution is `STORY-P0-05-03`'s job, not this Story's") — `STORY-P0-05-01` only produces the raw (DLL, symbol) import list `-03` will eventually check against an allowlist.

## Key decisions worth restating

- **`STORY-P0-05-01` needed no new capability-check surface**, unlike `STORY-P0-05-03` (whose `aci`-crate-ordering question Handover 11 explicitly left open) — parsing the import table is purely mechanical extraction, with allowlist resolution entirely deferred, so this Story didn't have to touch that open question at all.
- **Ordinal-only imports are silently not recorded, by design, not oversight.** A `LoadDescriptor` only ever contains named `(dll, symbol)` pairs — if `STORY-P0-05-04`'s eventual real `blue-sharc.exe` build turns out to import anything by ordinal (unexpected given its build toolchain, but not verified since no real binary has been parsed yet), that import would be invisible to `STORY-P0-05-03`'s allowlist check and need this module extended, not just the allowlist. Flagged in both the Story doc and `REPORT-2026-07-26-07` so it isn't rediscovered as a surprise later.
- **`rva_to_file_offset` uses `max(virtual_size, file_size)`** as a section's mapped-range extent rather than just `virtual_size`, matching real-world PE loaders' tolerance for headers where the two disagree (common with alignment padding) — a deliberate small permissiveness inside an otherwise strict fail-closed parser, chosen because rejecting on that mismatch would reject plenty of legitimately-built binaries, `blue-sharc.exe` included, for no security benefit (the actual bound enforced is still the file's real length, not the disputed header field).

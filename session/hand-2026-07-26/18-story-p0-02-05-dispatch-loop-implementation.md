# Handover 18 — `STORY-P0-02-05` (New) Implemented and Verified: Priority-Ordered Cooperative Dispatch Loop

Follows: [`17-story-p0-02-04-wcet-enforcement-implementation.md`](17-story-p0-02-04-wcet-enforcement-implementation.md). Both `STORY-P0-02-03` and `STORY-P0-02-04` independently named the identical missing prerequisite in the same session — no mechanism in this kernel actually selects and runs tasks in priority order, only bookkeeping about who *should* run next. That's a strong enough signal to add and implement a new Story for it immediately, per the user's standing request to keep chaining without stopping to ask. This Story is not part of `FEAT-P0-02`'s original 4-Story decomposition; it's added here as `STORY-P0-02-05`.

## What this session did

1. **Added `Pool::iter_occupied` and `PoolHandle::index`** (`os/src/kernel/src/mem.rs`) — the enumeration primitive a ready-queue scan needs (`iter_occupied`) and a read-only accessor for a handle's underlying slot index (`index`, used to key an external parallel array by task without exposing a way to forge a handle).
2. **Added `TaskState` (`Ready`/`Running`/`Blocked`/`Finished`), `Tcb::state`, `Scheduler::state_of`/`set_state`, `TaskId::index`, `Scheduler::iter_tasks`, and `Scheduler::highest_priority_ready`** (`os/src/kernel/src/sched.rs`) — every newly created task starts `Ready`; `highest_priority_ready` selects the highest-priority `Ready` task via `iter_tasks`, ties broken by `Iterator::max_by_key`'s documented last-wins behavior (most recently created of the tied set). 5 new host tests.
3. **Implemented `kernel::dispatch::run_once`** (new module, `os/src/kernel/src/dispatch.rs`): selects the highest-priority Ready task and switches into its slot in a caller-supplied `[Context; N]` array via the existing `context::switch` primitive (`STORY-P0-02-02`), resuming the caller the moment that task yields back; a still-`Running` task after the switch returns is reset to `Ready` (default cooperative round-robin). Blocking a task on contention remains the caller's job, done via `Scheduler::set_state` between rounds — this module has no automatic parking, matching `kernel::lock`'s own established scope.
4. **2 new tests, the flagship one closing `STORY-P0-02-03`'s own named behavioral gap**: `dispatcher_runs_the_boosted_holder_ahead_of_an_uninvolved_ready_task_after_contention` constructs the classic three-task scenario with *real* `context::switch` calls into real task functions (not simulated): round 1 (no contention) selects the higher-static-priority medium task over low; after a third task contends for low's `PriorityInheritingLock` (boosting low above medium), round 2 selects the now-boosted low instead; after low releases the lock, round 3 reverts to medium. A shared run-log the task functions write to before yielding (`[1, 0, 1]`) confirms the selected task's own code actually ran each round, not just that the right `TaskId` was returned.
5. **Verified**: `cargo test --workspace --lib`: 96/96 (up from 89; `kernel` alone: 35, up from 28). `cargo fmt --check` clean. `cargo clippy --workspace --lib --all-targets -- -D warnings` clean (fixed one `clippy::filter_map_bool_then` lint in `Pool::iter_occupied`'s first draft along the way). `cargo run -p xtask -- check-crate-sizes --ceiling=20000`: `kernel` grew to 1057 lines (from 887), everything else unchanged, all comfortably under. All five pre-existing QEMU fixtures re-verified unaffected (this Story added none of its own — `context_switch_asm`'s `sysv64` pinning makes its host tests meaningful without one, per `STORY-P0-02-02`'s own established precedent). Filed `REPORT-2026-07-26-13`.
6. **Updated all V&V docs**: new `STORY-P0-02-05.md` (Verified) and `TEST-P0-02-05-A.md`; added an "Update" note to `STORY-P0-02-03.md` recording that its own behavioral gap is now closed; added an "Update" note to `STORY-P0-02-04.md` clarifying its gap is *not* closed by this Story (a dispatch loop isn't a timer); `FEAT-P0-02.md` to "5/5 Stories Verified" with a consolidated single-remaining-gap note; `EPIC-P0.md`'s `FEAT-P0-02` row (4/4 → 5/5); `goals/traceability-matrix.md`'s new `STORY-P0-02-05` row and session cross-reference table; `goals/index.html`'s stat tiles (13/18 → 14/19 Stories — the denominator grows since this Story is additive to the original decomposition — 12/13 → 13/14 Tests, progress bar 72% → 74%) and the `FEAT-P0-02` table row; `session/hand-2026-07-26/index.html`'s entry list.

## What this session deliberately did not do

- **Did not implement preemptive dispatch.** This dispatcher is cooperative — a task must call `context::switch` back itself; nothing forces a task that never yields to give up control. True preemption needs a timer interrupt / IDT this kernel doesn't have yet (`STORY-P0-05-02`'s named gap, restated here as this Story's own explicit limit).
- **Did not touch `STORY-P0-02-04`'s WCET gap.** A dispatch loop existing doesn't supply a periodic timer source or a real watchdog/failsafe implementation — both remain fully open, independent of this Story, and this is called out explicitly in `STORY-P0-02-04.md`'s own new "Update" note so the two Stories' differing outcomes from the same addition aren't conflated.
- **Did not integrate lock contention with automatic state transitions.** `PriorityInheritingLock::try_lock` still doesn't mark a contending task `Blocked` itself — this Story's own test does that explicitly, matching `kernel::lock`'s pre-existing scope note that blocking is the caller's responsibility, not something this Story silently changed.
- **Did not implement any fairness policy beyond "highest priority wins."** Ties among equal-priority Ready tasks break toward the most recently created, per `Iterator::max_by_key`'s own documented behavior — not a rotating round-robin fairness scheme. Acceptable for what this Story needed to prove; a real fairness policy is future work if ever needed.
- **Did not implement `STORY-P0-05-04`** (end-to-end `blue-sharc.exe`) — still blocked on sourcing a real binary, unchanged from Handover 11/12/15/16/17.

## Key decisions worth restating

- **This Story exists because two independent Stories converged on the same missing piece in one session.** That's a stronger signal than either Story alone would have been — worth remembering as a pattern: when a "scope resolution" note in one Story repeats verbatim in the next, it's often cheaper to build the missing piece immediately than to defer it a third time.
- **`run_once` takes raw pointers (`*mut Context`, `*mut [Context; N]`) rather than `&mut` references**, mirroring `context::switch`'s own signature and safety-contract style — the caller (this Story's own test, and any future real dispatcher loop) is responsible for the same aliasing discipline `switch` itself already requires, documented in `run_once`'s own `# Safety` section rather than re-deriving a different contract shape.
- **The flagship test's reliance on `Pool::alloc`'s first-free-slot allocation order (`low.index() == 0`, `medium.index() == 1`) is asserted explicitly in the test itself**, not left as a silent assumption — if `Pool`'s allocation strategy ever changes, this test fails loudly at the `assert_eq!` rather than silently switching into the wrong task's context.
- **`high` (the contending, never-actually-run task in the flagship test) is marked `Blocked` immediately upon creation**, before any `run_once` call — this is what keeps `highest_priority_ready` from ever trying to switch into `high`'s deliberately-uninitialized `Context` slot (which would be undefined behavior), documented inline in the test rather than left as an implicit "this happens to work" fact.

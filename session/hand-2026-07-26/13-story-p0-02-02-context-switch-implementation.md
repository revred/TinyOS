# Handover 13 — `STORY-P0-02-02` Implemented and Verified: x86_64 Context Switch

Follows: [`12-story-p0-05-01-pe64-parser-implementation.md`](12-story-p0-05-01-pe64-parser-implementation.md), which implemented `STORY-P0-05-01` and flagged `FEAT-P0-02`'s `STORY-P0-02-02` (context switch) as the single remaining blocker standing between `FEAT-P0-05` and its next three Stories. This handover picks up that mandate directly.

## What this session did

1. **Implemented the x86_64 context switch** in a new module, `os/src/kernel/src/context.rs` — the standard callee-saved-register/stack-pointer save-and-restore every production x86_64 kernel uses (Linux's `switch_to`/`__switch_to_asm` included); not a novel scheme, kept intentionally compact (per this session's own explicit steer: don't reinvent what's already solved, get inspired by the proven approach, keep the implementation small):
   - `context_switch_asm`, a `global_asm!`-defined free function (not inline `asm!` inside a normal Rust function body, which would be unsound here — the compiler doesn't know `rsp` changes mid-function): pushes `rbp`/`rbx`/`r12`-`r15`/`rflags` onto the current stack, saves the resulting `rsp` into `*prev`, loads `rsp` from `*next`, pops the same six values back off, and `ret`s — resuming either a previously-suspended task exactly where it left off, or (for a never-run task) landing at its entry point.
   - Declared `extern "sysv64"` explicitly, not `extern "C"` — `"C"` follows the host OS's own default convention (Windows x64 on this dev machine, System V on the kernel's real `x86_64-unknown-none` target), which would silently break the asm's fixed `rdi`/`rsi` argument-register assumptions the moment `cargo test` ran on Windows. Pinning the ABI is what makes this module's own host unit test possible at all.
   - `Context::new(stack, entry)` pre-populates a fresh stack with the same six-value frame `context_switch_asm` expects, computing the System V AMD64 alignment rule (`rsp % 16 == 8` at a callee's entry, immediately after `ret` pops the return address) by hand — fails closed with `ContextError::StackTooSmall` rather than writing past a too-small stack.
   - `entry` is typed `extern "C" fn() -> !`, the exact type `sched::TaskEntry` (`STORY-P0-02-01`) already is — this Story's stated dependency on "a `TaskId`/TCB to switch to and from" is satisfied at the type level, though the fixture below doesn't route through `Scheduler::create_task` itself (see "deliberately did not do").
2. **Wrote two host unit tests** in `context.rs`'s `#[cfg(test)]` module: `switch_preserves_each_of_two_tasks_own_state_across_interleaving` (two tasks, four interleaved switches, each task's own stack-local counter checked after) and `new_rejects_stack_too_small_for_the_initial_frame`. Both run on the host `cargo test` toolchain — safe only because of the `sysv64` pinning above.
3. **Added the Tier 0 QEMU fixture** the Story's acceptance criteria require: `os/src/kernel/src/context_switch_fixture.rs` (the identical two-task, four-switch sequence as the host test, run instead inside the real `no_std` kernel binary), gated behind a new `fixture-context-switch` Cargo feature (mirroring `fixture-broken-boot`'s existing precedent) and wired into `kernel_main`. Generalized `xtask`'s `--fixture=` argument parsing (previously hardcoded to the single `broken-boot` value) to also accept `context-switch`, mapping each to its Cargo feature.
4. **Verified**: `cargo run -p xtask -- qemu-x86_64 --fixture=context-switch` reaches the QEMU `isa-debug-exit` success code; both pre-existing fixtures (no `--fixture`, and `--fixture=broken-boot`) re-checked unaffected by the new branch in `kernel_main`. `cargo test -p kernel --lib` (13/13, including the two new tests), `cargo test --workspace --lib` (61/61 across every crate, no regressions), `cargo fmt --check` and `cargo clippy --workspace --all-targets -- -D warnings` (both clean workspace-wide, with two narrowly-scoped, commented `#[allow]`s for a clippy false-positive on the `&raw mut`/`&raw const` idiom used to avoid the `static_mut_refs` lint), `cargo run -p xtask -- check-crate-sizes --ceiling=20000` (`kernel` at 774 lines, comfortably under the ceiling). Filed `REPORT-2026-07-26-08`.
5. **Updated all V&V docs**: `STORY-P0-02-02.md` to `Status: Verified` with acceptance-criteria-by-criteria "Met" notes; new `TEST-P0-02-02-A.md` (written to match what was actually implemented, since the Story's own acceptance criteria — unlike `FEAT-P0-05`'s Stories last session — were already specified as "draft" before this session, not test-first from scratch); `FEAT-P0-02.md` to "2/4 Stories Verified" with an updated Story table row; `EPIC-P0.md`'s `FEAT-P0-02` row; `goals/traceability-matrix.md`'s `STORY-P0-02-02` row and session cross-reference table; `goals/index.html`'s stat tiles (8/18 → 9/18 Stories, 7/11 → 8/12 Tests) and both the `FEAT-P0-02` and `FEAT-P0-05` table rows (the latter to note `STORY-P0-05-02` is now unblocked); `session/hand-2026-07-26/index.html`'s entry list.

## What this session deliberately did not do

- **Did not route the QEMU fixture's two tasks through `Scheduler::create_task`.** `sched.rs`'s own module doc comment scopes context switching out of `Scheduler` entirely for now, and `Scheduler` has no dispatch loop or "current task" concept yet — building one is naturally a future Story's job (whichever Story adds real preemptive dispatch), not this one's. This Story's acceptance criteria only require switching "between two tasks," which the fixture does using local `extern "C" fn` entries built directly into `Context`s; the type-level compatibility with `sched::TaskEntry` is deliberate and sufficient for now.
- **Did not implement `STORY-P0-02-03`/`-04`** (priority inheritance, WCET enforcement) or `STORY-P0-05-02`/`-03`/`-04`. `STORY-P0-05-02` (process address-space creation and section mapping) is now unblocked — its dependency on a working context switch is satisfied — and is the natural next pick for whoever has bandwidth for `FEAT-P0-05` next, but this session's scope was the context switch itself.
- **Did not make the initial `rflags` value for a freshly-initialized task configurable.** `Context::new` always seeds `0x202` (reserved bit 1 + interrupt-enable flag) — a reasonable default, but a future Story that needs a task to start with interrupts masked will need to turn this into a parameter rather than silently reusing the constant. Flagged in `REPORT-2026-07-26-08` so it isn't rediscovered as a surprise.
- **Did not source or vendor a real `blue-sharc.exe` fixture.** Unrelated to this Story but still open from Handover 11/12 — unchanged this session.

## Key decisions worth restating

- **The context switch is deliberately unoriginal.** This session was explicitly steered not to invent a new scheme but to build the same technique every production x86_64 kernel already uses, compactly, in Rust — `Context` is a single `u64` (the saved `rsp`) precisely because the callee-saved registers live on the task's own stack rather than in the `Context` struct, exactly as they would for an ordinary (if very long-lived) function call.
- **Pinning `context_switch_asm` to `"sysv64"` rather than `"C"` was the change that made host-testing this possible at all.** Without it, the same code would silently break under `cargo test` on this Windows dev machine (Windows x64 ABI expects arguments in `rcx`/`rdx`, not the `rdi`/`rsi` the raw asm actually uses) while still working under the real `x86_64-unknown-none` kernel target (whose default `"C"` ABI already is System V) — a latent, environment-dependent bug that would have been easy to miss without deliberately testing on the host in the first place.
- **`Context::new`'s `entry` parameter stays `extern "C" fn() -> !` (matching `sched::TaskEntry`), not `"sysv64"`.** Only `context_switch_asm`'s two-argument call needed the explicit pin — a zero-argument, never-returning entry point has no argument-marshaling convention to get wrong, and its stack-alignment requirement at entry is identical under both ABIs, which is why the host test can jump into `extern "C" fn`-typed task entries too without issue.

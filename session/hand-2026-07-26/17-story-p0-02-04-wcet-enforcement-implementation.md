# Handover 17 — `STORY-P0-02-04` Implemented and Verified: WCET Budget Enforcement (completes `FEAT-P0-02`)

Follows: [`16-story-p0-02-03-priority-inheritance-implementation.md`](16-story-p0-02-03-priority-inheritance-implementation.md), which named `STORY-P0-02-04` as the last remaining `FEAT-P0-02` Story and flagged it as likely to hit the same missing-dispatcher constraint priority inheritance did. Continuing autonomously per the user's standing request (keep chaining into the next unblocked Story without stopping to ask after each one), this session picked it up directly.

## What this session did

1. **Added `ticks_consumed: u32` to `Tcb`** (`os/src/kernel/src/sched.rs`), initialized to 0 at task creation, plus `Scheduler::wcet_state`/`add_ticks_consumed`/`reset_ticks_consumed` accessors — the bookkeeping `kernel::wcet` reads and mutates, the same pattern `STORY-P0-02-03`'s `priority_of`/`set_priority` accessors established.
2. **Implemented `kernel::wcet`** (new module, `os/src/kernel/src/wcet.rs`): `record_tick(scheduler, handler, task, ticks)` attributes `ticks` to `task` and checks the new running total against its declared budget *on every call* — an overrun trips on the exact tick that crosses the budget, not retroactively at some later check, satisfying acceptance criterion 1 as directly as this Story's scope allows. `OverrunHandler` is a new standalone trait (`fn on_overrun(&mut self, task: TaskId)`) standing in for `README.md` Non-Negotiable #5's not-yet-built watchdog/failsafe system — the identical Dependency Inversion pattern `exec::win32_shim::CapabilityPolicy` established for the not-yet-built `aci`, so wiring in a real watchdog later is additive. `reset_budget_window` starts a fresh window for a task (e.g. at the top of each new scheduling period).
3. **6 new host tests**, TDD-first: in-budget tick (no overrun, handler untouched); overrun detected on the exact tick that crosses budget, both via several small ticks accumulating and via one oversized tick; consumption exactly equal to budget is *not* an overrun (only strictly exceeding it); resetting a budget window after an overrun clears prior consumption; an unknown task fails closed without invoking the handler. Added a `#[cfg(test)] pub(crate) Scheduler::free_task_for_test` helper (mirroring `pe::FixedBytes::for_test`'s precedent from Handover 15) so `wcet`'s tests could construct a genuinely-unknown `TaskId` without exposing a real task-destruction API this Story doesn't otherwise need.
4. **Verified**: `cargo test --workspace --lib`: 89/89 (up from 83; `kernel` alone: 28, up from 22). `cargo fmt --check` clean. `cargo clippy --workspace --lib --all-targets -- -D warnings` clean for every host-buildable target (same pre-existing Windows/ELF `[[bin]]` limitation, unaffected — no new target-specific code). `cargo run -p xtask -- check-crate-sizes --ceiling=20000`: `kernel` grew to 887 lines (from 775), everything else unchanged, all comfortably under. All five pre-existing QEMU fixtures re-verified unaffected (this Story added none of its own). Filed `REPORT-2026-07-26-12`.
5. **Updated all V&V docs**: new `TEST-P0-02-04-A.md`, `STORY-P0-02-04.md` to `Status: Verified` (acceptance criteria finalized, AC2 explicitly marked "partially met" with the reason why), `FEAT-P0-02.md` to fully "Verified — 4/4 Stories Verified" (with a new note naming both Stories' shared structural gaps), `EPIC-P0.md`'s `FEAT-P0-02` row, `goals/traceability-matrix.md`'s `STORY-P0-02-04` row and session cross-reference table, `goals/index.html`'s stat tiles (12/18 → 13/18 Stories, 11/12 → 12/13 Tests, progress bar 67% → 72%) and the `FEAT-P0-02` table row (now fully Verified), `session/hand-2026-07-26/index.html`'s entry list.

## What this session deliberately did not do

- **Did not implement a live timer-tick source.** Nothing periodically calls `record_tick` on its own yet — the identical missing ready-queue/priority-based dispatch loop `STORY-P0-02-03`'s handover already named. `record_tick` is a function a future timer-interrupt handler or dispatcher tick would call; building that caller is out of this Story's scope.
- **Did not implement a real watchdog/failsafe system.** `README.md` Non-Negotiable #5 commits to one at the design level; no implementation exists anywhere in this codebase yet, independent of the dispatcher gap. `OverrunHandler` is this Story's own standalone stand-in — a genuine, currently-unmet piece of acceptance criterion 2, marked "partially met" in `STORY-P0-02-04.md` rather than silently claimed complete.
- **Did not implement admission control or schedulability analysis.** This Story is purely reactive detection after ticks are attributed to a task; it does not check at task-creation time whether a set of declared budgets is even jointly schedulable.
- **Did not add a Tier 0 QEMU fixture.** Same reasoning as `STORY-P0-02-03`: `kernel::wcet`/`kernel::sched` are pure logic, no `unsafe`, no register/memory-layout dependency — entirely host-testable, and the one property that would need a live target (a real timer, a real watchdog) can't be verified on any tier yet regardless.
- **Did not implement any Roadmap Phase 1 timing-regression-suite entry** — acceptance criterion 3 explicitly defers that in full; this Story's own tests are the minimum "detection is correct under synthetic overrun" bar that criterion also requires.

## Key decisions worth restating

- **This Story hit the exact same structural wall `STORY-P0-02-03` did, for an independent reason.** Priority inheritance was missing a dispatcher to behaviorally verify starvation prevention; WCET enforcement is missing both that same dispatcher (to drive detection on a real tick) *and*, newly, a real watchdog subsystem that doesn't exist independent of the dispatcher at all. Both gaps are now named twice across two Stories — strong signal that a dispatcher Story is worth prioritizing before any further scheduler-adjacent Story is picked up, restated in "Immediate next steps" below.
- **`OverrunHandler` mirrors `CapabilityPolicy`'s shape deliberately**, not by coincidence — both are this codebase's now-established answer to "the real subsystem this needs doesn't exist yet": a local trait, concrete-type-free at every call site, so the eventual real implementation (`aci`; a real watchdog) is a drop-in addition rather than a rewrite. Worth recognizing as a repeating pattern, not re-deriving it fresh each time a Story hits this shape of gap.
- **`FEAT-P0-02` is marked fully Verified (4/4 Stories) despite two Stories carrying explicitly-documented partial scope.** This follows the same convention `STORY-P0-05-02`/`-05-03` already established (Verified with a named, deliberate deferral, not "blocked" or "in progress") — a Story reaching Verified means its acceptance criteria are met *as finalized against what was actually implementable*, not that every originally-drafted aspiration was achieved. The Feature-level doc names both gaps explicitly rather than letting "4/4 Verified" read as more complete than it is.

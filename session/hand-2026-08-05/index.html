  1. 01AThe need for speed, and what must not be traded for it

    Written at the owner's request on the framing that the project now has a verifiable development cycle worth a 10× improvement, with TDD and no loss of quality. §2 — where the speed actually comes from: evidence replaced transcription; ground truth captured before design (twenty minutes of SSH sized STORY-P1-10-05 correctly and corrected a wrong risk statement already made out loud); a capture no longer has to be lucky; and gates that cost less than the failures they catch. The benchmark is real — STORY-P1-10-05 ran observation → ground truth → design → TDD → gates → Story → commit → image in about an hour, with the owner only inserting a card and applying power. §3 — what must not be traded, each with this session's receipt: prove the Red (14 tests failed against a neutered implementation); never substitute a constant for a discovery (LE-69 refused a conforming device, and a wrong temperature still reads like a temperature); state what you did not measure (LE-74's caution was right and far too gentle — the board measured two consecutive epochs 151 counter ticks apart); a gate that cannot see its subject is not a gate (LE-72); widen a vocabulary, never stretch one (and note ACT now has one verb of headroom). §5 — the mandate, and it is not what FEAT-P1-10's Story list implies: hal-arm64 references none of sched, dispatch, lock or wcet — the board has never run TinyOS's kernel. There are no call sites to wire because nothing calls them. The real next milestone is one task dispatched once on silicon, with the tick driving the dispatch round, observed through the stream built for exactly that. First, though: boot f06bfa8ac7ec and read the thermal rung, and write REPORT-2026-08-04-01, which is release-blocking.

Review of c7f2a6d: the --until matrix was re-run independently, including a capture built to attack the strongest claim — a rung present only inside a retained frame correctly does not sight, which matters because a watch that fired on the boot certificate would report a five-second-old reboot as a live event forever. My first run showed six failures and they were a stale binary; the tool was right and the harness was wrong, recorded as discipline. §4 — deployment over the wire, and the line that must not blur: Pi 5 firmware netboot is charter-neutral because the bootloader fetches the image before TinyOS exists and rule 9 never engages; TinyOS receiving and executing an image is a different thing entirely — it reverses a tested refusal, replaces the containment argument LE-67 rests on, and needs all fourteen RCG-* gates. The two sound identical in a sentence and differ by a charter. Then: take the OS for a spin — one task created, one dispatch round, one Dispatch spoor off silicon, because the board has never run TinyOS's kernel.

  4. 04AThe multiplier is real. Now run the kernel on it.

    TinyOS boots over Ethernet. The card swap — named in 01A §4 as the single largest remaining multiplier — is over: BOOT_ORDER=0xf12, tos64-netboot serves the image, the firmware fetches and jumps, and the running system emits spoors on the cable it arrived over (epoch 0x04C7D0FF, 96 frames in 30 s). Rule 9 is never engaged, because the firmware loads before TinyOS exists. All four 01A §4 frictions are closed: netboot, passwordless scoped root probe, Ti64Dink --until/--text/--any, and the spoor substrate's own overhead measured (stamp 138 cycles/op, announce 3101, drain 121955 — the drain being 674 cycles per record and worth a second look). Also today: REPORT-2026-08-04-01 filed and LE-09 closed; STORY-P1-10-04 and -05 board-proven; the thermal offset hypothesis held on silicon; and the measurement envelope parsed off the wire at last. §3 is the mandate and it has not changed: hal-arm64 references none of sched, dispatch, lock or wcet — the board has never run TinyOS's kernel. One task created, one dispatch round, one Dispatch spoor off silicon, and the board stops being parked and starts being an OS. §4 is the discipline, with four receipts from this session including two of my own errors: a stale binary that produced six confident false failures, and a firewall diagnosis stated confidently and wrong — ask for a privilege only after proving you need it.

  5. 05AOne power cycle from the kernel driving the machine

    The next session opens on a bench action, not a design question. FEAT-P1-11 is new and implemented — kernel::board_dispatch runs one cooperative dispatch round from the park loop with interrupts live, host-Green with 6 tests, image f8133b0958d3 built, gated, staged and served — and never yet booted. One power cycle answers it, and all three outcomes are informative: Ok means the kernel drives the machine; Skipped means the scheduler is empty and points at boot ordering; Failed means the switch went in and never returned, which would be the interesting one. §2 is a correction that reshaped the mandate: two handovers and two commit messages said "the board has never run TinyOS's kernel" and that was wrong — fixture_measure has created a task, switched context and run a dispatch round on this board since BOARD VERDICT 5, with the numbers in every envelope I had already quoted. The grep asked hal-arm64; the caller is kernel. A grep that returns nothing is evidence about the search, not the claim. The corrected gap is narrower: the kernel runs but does not run the machine. Also decided and written down so it is not re-derived: docs/tinydb-rt-scope.md — the owner's fast Rust database as the first application and RT falsifier, with the eight things it may never do, and the four-layer database picture settled across two agents and the owner. §5 carries five discipline receipts, three of them my own errors, including LE-77: a batch command that stops on first failure reports on a prefix while looking like it reported on everything.

  6. 06ANothing is verified, and the reason is not velocity

    Written in answer to the owner: "I don't see the stories moving to completion, especially EPIC-P1." The observation is correct and the cause is structural. All 31 in-flight EPIC-P1 Stories read In progress — ten under FEAT-P1-07, fifteen under -09, five under -10, one under -11 — and zero of 97 contract rows have ever reached assurance verified, not this month, not ever. There are two ceilings and the project has treated them as one. Functional Verified is reachable today and is simply not being claimed: FEAT-P1-07's ladder was recorded as "effectively done" on 2026-08-04 with -03's every criterion and -04's all five Green on silicon, REPORT-2026-08-04-01 is filed, and all ten Stories still read In progress — LE-65's class, whose remediation refuses a stale Specified but nothing refuses an In progress Story whose criteria are all met. Assurance verified is not slow, it is closed: it requires release gates in a declared deployment profile, ADR 0005 requires a qualified platform, and qualified-platforms.tsv holds 5 platforms, 0 qualified with 11 of 460 guardrail rows carrying evidence — so EPIC-P1 cannot discharge Determinism Proof through Stories at all until a Q2 campaign starts. The last three sessions optimised the loop, not the ledger: a 10× loop attached to a queue that never drains produces a longer queue, faster. §4 is a closing pass — advance every satisfied Story or name the one missing thing, close LE-65's other half so it cannot recur, and either start Q2 or restate what the Epic discharges without it. §6 names the measure: Stories at Verified under EPIC-P1 (zero) and guardrail rows (11/460). If the next handover reports new capabilities and those are unchanged, the loop got faster and the project did not.

  8. 08AThe closing pass, and the board that was never blocked

    07A §6 was the mandate and five of its six items are done. Against 06A §6's measure: Stories at Verified under EPIC-P1 1 → 22 and guardrail rows 11/460 → 22/460 — both numbers moved, which is what 06A §7 said would distinguish the loop getting faster from the project moving. The power cycle happened and the board was never the blocker. The owner powered it on request; two attempts were lost to host-tool defects. tos64-netboot crashed on the first packet it ever answered (LE-81) — it sampled its own address at startup while the board was off, so the bench NIC had no link, and an unhandled SocketException killed the server on the one MAC it exists to answer. Worse, ti64dink --until rung=DispatchRound — the exact command 07A §1 printed as the next session's first act — watched 300 seconds of DispatchRound records and exited 1 as a timeout (LE-80), because two hand-kept host tables had never learned the rung existed, one of them under a doc comment asserting it could not drift. A watch that reports a live event as an absence is worse than one that cannot parse. Both fixed and both verified in the failing direction first. Then, netbooted with no SD card in the board: Dispatch Kernel Select Ok rung=DispatchRound, one per beat, 0 refused, 0 lost — STORY-P1-11-01 criterion 7, the kernel driving the machine with interrupts live, where every prior verdict measured TinyOS from inside a fixture with IRQs masked. The closing pass read all 31 Stories: 21 advanced, 10 given the one missing thing, and not one of the ten is blocked on unbuilt work — three need a deliberate negative nobody has bothered to observe (a boot with pciex4_reset=0 removed, a boot with the cable out, one photograph), because a probe whose failure arm has never been exercised is a probe only shown to succeed.

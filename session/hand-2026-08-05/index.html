  4. 04AThe multiplier is real. Now run the kernel on it.

    TinyOS boots over Ethernet. The card swap — named in 01A §4 as the single largest remaining multiplier — is over: BOOT_ORDER=0xf12, tos64-netboot serves the image, the firmware fetches and jumps, and the running system emits spoors on the cable it arrived over (epoch 0x04C7D0FF, 96 frames in 30 s). Rule 9 is never engaged, because the firmware loads before TinyOS exists. All four 01A §4 frictions are closed: netboot, passwordless scoped root probe, Ti64Dink --until/--text/--any, and the spoor substrate's own overhead measured (stamp 138 cycles/op, announce 3101, drain 121955 — the drain being 674 cycles per record and worth a second look). Also today: REPORT-2026-08-04-01 filed and LE-09 closed; STORY-P1-10-04 and -05 board-proven; the thermal offset hypothesis held on silicon; and the measurement envelope parsed off the wire at last. §3 is the mandate and it has not changed: hal-arm64 references none of sched, dispatch, lock or wcet — the board has never run TinyOS's kernel. One task created, one dispatch round, one Dispatch spoor off silicon, and the board stops being parked and starts being an OS. §4 is the discipline, with four receipts from this session including two of my own errors: a stale binary that produced six confident false failures, and a firewall diagnosis stated confidently and wrong — ask for a privilege only after proving you need it.

  5. 05AOne power cycle from the kernel driving the machine

    The next session opens on a bench action, not a design question. FEAT-P1-11 is new and implemented — kernel::board_dispatch runs one cooperative dispatch round from the park loop with interrupts live, host-Green with 6 tests, image f8133b0958d3 built, gated, staged and served — and never yet booted. One power cycle answers it, and all three outcomes are informative: Ok means the kernel drives the machine; Skipped means the scheduler is empty and points at boot ordering; Failed means the switch went in and never returned, which would be the interesting one. §2 is a correction that reshaped the mandate: two handovers and two commit messages said "the board has never run TinyOS's kernel" and that was wrong — fixture_measure has created a task, switched context and run a dispatch round on this board since BOARD VERDICT 5, with the numbers in every envelope I had already quoted. The grep asked hal-arm64; the caller is kernel. A grep that returns nothing is evidence about the search, not the claim. The corrected gap is narrower: the kernel runs but does not run the machine. Also decided and written down so it is not re-derived: docs/tinydb-rt-scope.md — the owner's fast Rust database as the first application and RT falsifier, with the eight things it may never do, and the four-layer database picture settled across two agents and the owner. §5 carries five discipline receipts, three of them my own errors, including LE-77: a batch command that stops on first failure reports on a prefix while looking like it reported on everything.

  6. 06ANothing is verified, and the reason is not velocity

    Written in answer to the owner: "I don't see the stories moving to completion, especially EPIC-P1." The observation is correct and the cause is structural. All 31 in-flight EPIC-P1 Stories read In progress — ten under FEAT-P1-07, fifteen under -09, five under -10, one under -11 — and zero of 97 contract rows have ever reached assurance verified, not this month, not ever. There are two ceilings and the project has treated them as one. Functional Verified is reachable today and is simply not being claimed: FEAT-P1-07's ladder was recorded as "effectively done" on 2026-08-04 with -03's every criterion and -04's all five Green on silicon, REPORT-2026-08-04-01 is filed, and all ten Stories still read In progress — LE-65's class, whose remediation refuses a stale Specified but nothing refuses an In progress Story whose criteria are all met. Assurance verified is not slow, it is closed: it requires release gates in a declared deployment profile, ADR 0005 requires a qualified platform, and qualified-platforms.tsv holds 5 platforms, 0 qualified with 11 of 460 guardrail rows carrying evidence — so EPIC-P1 cannot discharge Determinism Proof through Stories at all until a Q2 campaign starts. The last three sessions optimised the loop, not the ledger: a 10× loop attached to a queue that never drains produces a longer queue, faster. §4 is a closing pass — advance every satisfied Story or name the one missing thing, close LE-65's other half so it cannot recur, and either start Q2 or restate what the Epic discharges without it. §6 names the measure: Stories at Verified under EPIC-P1 (zero) and guardrail rows (11/460).

  2. 01BThe runs were never created, and not(windows) is not bare metal

    Executes 01A, and the premise 01A opened with was itself the answer to half of it. origin/main was at e273931, not at dff7b1d — dff7b1d was committed on this bench and never pushed, so the missing run for it was the absence of a push, not the absence of a runner. The cheap decisive test 01A named was run and answered in the first direction: pushing e273931..dff7b1d created run 31161538569 within seconds, so run creation is not broken — the four pushes of 2026-08-06 evening fell inside the outage window and GitHub does not backfill runs it dropped. Filed and closed as LE-102, with the residual stated rather than softened: the gates now execute on the cumulative tree and never on the individual trees of b4a7010, cb9b27b, 4f5f2a4 or e273931, so a bisect across those four has no runner evidence behind any step. The account-level candidate is ruled out on structure rather than on a probe — the repository is public and every job is on ubuntu-latest, and standard runners on public repositories are unmetered. The instrument correction is sharper than 01A's: actions/runs?head_sha= does not return zero regardless — it works, but only with a full 40-character SHA. 10C abbreviated it, so its probe was answering correctly about a commit identifier the API accepts and can never match. Then host-tests went red on its first Linux run, and not for the predicted reason: rust-lld: duplicate symbol: _start in four crates, so not one host test in the workspace ran — the suite died at the linker. hal_x86_64::boot is gated not(target_os = "windows") and defines _start, and a Linux host satisfies that gate exactly as the bare-metal target does; it was harmless for the life of the project only because CI ran clippy, which does not link, and became reachable the moment LE-100 added cargo test --workspace. LE-100's own sentence landing on LE-100. The fix is deliberately narrower than the obvious one — gating the modules reddens the green Linux governance job, so the global_asm! blocks themselves move to target_os = "none" — and the guard skips comment lines because boot.rs's own explanation of the gate contains the needle, was verified by mutating the real file, and refuses the wrong #[cfg] as well as a missing one. The fixed suite then found the second instance, and it is worse: with the linker unblocked, exec died with SIGSEGV after five passing tests — unmap_page and link_shared_directory call invalidate_page under the same gate, and invlpg is ring 0, so a safe public function called by ordinary unit tests executed a privileged instruction in a userspace process. A segfault with no test name attached, after five ok lines, reads like a flaky harness rather than a defect. Its guard failed on its own needle list on first run — the four string literals it searches for are lines containing write_cr3( — so it stops at #[cfg(test)] and asserts that it stopped; third self-match in this repository. Run 31163298610: host-tests green, 1231 tests — the first time this project's host suite has passed on a runner. What is not fixed is stated rather than softened: the same spelling still stands across hal-x86_64 and kernel::context, and it cannot be converted without changing how the no_main fixture bins are built, because the Linux governance job compiles them for the host and they reference those items ungated — so the guarantee is empirical rather than structural, and the only red left on main is LE-23.

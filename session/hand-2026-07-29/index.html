  1. 01STORY-P0-07-03 Verified — grant fails closed instead of panicking

    LE-40's remedy line reserved a Story for "replacing the .expect with a fail-closed path… before any SMP work". Auditing the whole function for that defect class found a worse instance than the row named: grant computed every page address with unchecked +/* on caller-chosen values, so a page-aligned sharee_virt of 0xFFFF_FFFF_FFFF_F000 — which passes both the alignment and the kernel-region checks — overflowed on the second page. Unlike the .expect, that is reachable today, and the release build is worse than the debug build: with overflow-checks defaulted off the address wraps silently to 0x0 and is never re-checked against KERNEL_RESERVED_REGION_END, because the function is already past that check. Both profiles set panic = "abort", so the debug disposition is a whole-system abort on a transactional path. A second finding the row also did not name: the mapping loop's re-read .expected presence and re-checked permissions not at all — so under the same conditions it would have panicked on a vanished page and mapped a narrowed one anyway. The privilege-escalating half was the unguarded one. Presence and authority are now one verdict from one function that both loops call; the range is checked once up front (SharedMemoryError::RangeOverflow); the generation counter refuses to wrap or saturate (it is the whole basis of StaleGrant); and a test gates this module's non-test source against explicit panic constructs, failing on the pre-fix source and naming the line. Host tests 613 → 621. LE-52 registered for the generalisation — with the warning that the implicit half is where this session's reachable defect actually was. Written as uncommitted, since landed at 82e3d57; §7 records the two commits that arrived mid-session and why neither collided with this work.

  2. 03ATauri and the tab host — where a webview belongs, and where EPIC-P2 §6 already excludes one

    A decision record, not work done — no code, no contracts, no Story; one LE-53 row and the document. Prompted by a direct question (should TinyOS support Tauri for the multi-tab command prompt?) whose honest answer is three answers to three questions the wording bundles together: Tauri as an application lane is already yes (G-APP-2, APP-05, EPIC-H2) and needs no decision; Tauri as the implementation of the tab host is no; a Tauri host-side console is plausibly the cheapest route to the UX aspiration and is unregistered. The middle answer is the one worth recording because the first makes the wrong answer to it attractive. EPIC-P2 §6 already excludes every single-webview front end and never says so: §6.3's reserved region that no tab content may ever paint is not merely hard inside one webview but inexpressible, since the region and the tab content are the same DOM in the same renderer; §6.5's escape-injection rule gets worse, because HTML injection into a status bar is strictly more capable than a terminal escape and lands directly on §6.3. Two structural exclusions are also unrecorded: Tauri ships no renderer (it binds the platform webview), so a webview shell needs a browser engine first — inverting the critical path, since EPIC-P2 gates EPIC-H1/H3/H5 — and REPORT-2026-07-26-28 already rules webview runtimes optional profiles never added to the 8 MiB core image, while the shell is core. §6.4 does this exact reasoning against one artefact (Windows Terminal) and never generalises, which is the gap. Second half of LE-53: §6.4 calls the text-buffer/renderer separation "worth copying as a shape" when §6.6's drop-frames-rather-than-block obligation depends on it — free before the shell crate exists, expensive after, and it is also what keeps a webview front end possible later without taking the dependency now. Ordering caveat carried explicitly: this is not the next work — §1 of the Epic says 15 of 22 verbs are blocked on a filesystem that does not exist (LE-48), so the shell's blocker is storage, not the front-end framework.

  3. 07ACover note — brief for an independent review of the Tauri-based operator frontend

    Written to be handed to an external reviewer verbatim, assuming no knowledge of this repository. §2 is the section that earns the rest: the frontend architecture is entirely on paper — seven crates, none of them a shell, UI, display, window, font or terminal module, and no filesystem, no ACI capability engine, no display service and no rendering engine. A reviewer who assumes an implementation exists will calibrate wrongly. Records the owner decision that Tauri, tao and the IPC internals may be forked and modified, which changes the analysis sharply: §6.5 tabulates which objections survive a fork and the answer is almost none of them — Capability.local defaulting to true, the __TAURI_INVOKE_KEY__ bearer secret, the string-keyed in-process ACL and the unbounded IPC transport are all editable. What survives is the engine, and it is the one that carried the weight: forking Tauri does not produce a renderer, and the JIT and real-time questions live there. Two concrete findings the fork raises: prefer the seams to the patches (tauri-runtime is already a trait, so replacing tao wholesale is cheaper than modifying it, while RuntimeAuthority has no seam and is where a patch set genuinely belongs), and a governance collision — a vendored fork breaks rule 7 (all code under os/src/) and rule 4 (20,000-line ceiling), with tauri measured at 32,457 lines. Carries two corrections this session owed: LE-53's "inexpressible" is too strong, because Tauri supports multiple webviews per window so a host-owned reserved region is expressible; and the earlier "reference only, never built upon" recommendation is superseded.

  4. 06ATauri reviewed from source — and what it changes in the context model

    The other half of 03A: the application lane, where Tauri is first-class by founding intent and the repository's position was one paragraph of assertion. SECURITY_CHARTER.md sets the standard itself — runtime policy is "informed by the actual upstream execution models rather than framework names" — and the Tauri paragraph did not meet it, so the review is from source, pinned to tauri-apps/tauri dev at 872428f (tauri-runtime-wry 2.11.4, wry 0.55, tao 0.35). Credit where it is due: Tauri resolves the calling window/webview from its own Rust-side objects, never the payload — PD-02's shape reached independently by a userspace framework — and origin is recomputed from the webview's current URL at each call, so the Charter's "navigate to a remote origin and lose local IPC authority" is an implemented upstream mechanism, not a requirement TinyOS must add. Authority is resolved at build time (plugin manifests × capability files, baked in by tauri-codegen), which is the strongest alignment found: a signed manifest is a build-time-fixed authority set. Three findings cut the other way: __TAURI_INVOKE_KEY__ is a caller-supplied bearer secret and an XSS in the local page yields it; Capability.local defaults to true where PD-03 demands empty authority first — the likeliest silent authority leak in any port; and the governing one, core/wry/tao are ONE process, so every command handler runs with the app's full OS authority and the ACL decides only whether a string reaches a handler. Tauri's ACL is an in-process input filter, not an OS boundary — which is what the Charter already said, now evidenced rather than inferred, making agent.md rule 10 load-bearing here. The full PD-01…PD-14 map's shape is the conclusion: everything Tauri does well is interface shape; everything it does not do is isolation, accounting and time. tauri-runtime is a real trait seam (a port is impl Runtime for TinyOsRuntime, not a fork) but Tauri ships no renderer, so it is well-shaped rather than small. EPIC-H2 now has a document — Specified, not decomposed — carrying what the backlog row could not: the five lanes do not cost the same (.NET AOT is cheapest, Tauri is not, so H2-03 is recommended before H2-05), a missing EPIC-H3 dependency for the webview lanes, and six review-derived constraints written to become boundary tests. No Feature or Story documents were created, per the just-in-time rule, and no LE-54 — contiguity is jammed behind uncommitted LE-53, which 05B is also waiting on.

  5. 08CCover note — execute the Tauri fork PoC

    The start-here document for the session that runs the PoC. Follows the review's external audit, which produced ADR 0007 — the fork decision's proper record, previously carried only inside a document whose header says "no commitment" — plus reconciling edits to the review (remote capability contexts as the sharper authority-leak surface, the navigation TOCTOU wired to PD-13, a patch/seam/rewrite-risk classification of §7.1 against §7.3's own metric, release-tag baseline, named advisory process), EPIC-H2 §2.2/§2.5, and whole-system-context.md. The PoC's job is to try to break ADR 0007's four falsifiable claims cheaply, all on a host, none needing EPIC-H1/H3: the trait seam holds with zero patches to tao/wry (Stage A, starting from upstream's own MockRuntime); the "patch"-class fixes stay in the low hundreds of lines, measured cumulatively (Stage B, whose failing tests are EPIC-H2 §2.2's boundary tests prototyped early); authority resolution can defer to a mock ACI with upstream's tests still green (Stage C, producing the upstream PR draft as a side effect); and revocation-on-navigation is a clean patch (Stage D). Stage E, optional, is the 03A §5 host-side console against TinyOS-under-QEMU. Every stage has a kill criterion, and a killed stage is a success — it triggers the superseding ADR constraint 2 provides for; the failure mode is a PoC that ends without a verdict. §3 states up front what green stages must never claim: interface shape composes, isolation is not proven, and the renderer (EPIC-H3) remains the largest untouched dependency.

Owner ruling · no Python anywhere in the TinyTile stack · Python may call in through the C ABI · ADR 0014 narrows ADR 0012 clause 2

Handovers

  1. 01ANo Python in the TinyTile stack, anywhere; Python calls in through the C ABI

    Owner ruling recorded as ADR 0014, drawing one line through two sentences: Python may not be a component of TinyTile; Python may be a consumer of it. ADR 0012 clause 3 had already banned every compiler from the device — unchanged — but its clause 2 left the build host free to run “TileLang, TVM, nvcc, hipcc, or any other toolchain it likes”, and TileLang is a Python DSL on TVM, which put a Python runtime inside the path that produces and signs kernel artifacts. Now narrowed: TinyTile’s off-target compiler is Rust-native; a non-Python vendor assembler may still be a back-end step. “Easily consumes TileLang or CUDA” survives, re-read into two concrete paths — artifact ingestion as data (smaller, likely first) or a Rust front end that parses and lowers that source (substantial). Priced honestly: FEAT-P6B-03 stops being a contract around somebody else’s compiler and becomes a compiler. Changed: ADR 0012 (annotated + dated amendment), EPIC-P6B (four constraints → five, Feature re-shaped, exit criterion widened to the toolchain), tinytile-architecture.md. No code written and none owed — EPIC-P6B has no implementation yet, which is the cheapest possible moment for this constraint to arrive.

  2. 02AOwner-ordered: the boot splash (STORY-P1-07-07) — a dark screen is not a UI

    The owner watched the first physical boot succeed as a dark silent screen and rejected it. Delivered as FEAT-P1-07’s seventh Story: “TinyOS” in block letters on HDMI via the VideoCore mailbox framebuffer — property message host-pinned word-for-word, the firmware’s descriptor validated as hostile input (eight driven rejection arms), a pure centred renderer behind a Surface seam, every board wait budget-bounded, and the splash strictly after the TOS64-RESULT/1 verdict so it can never touch the evidence. 125 hal-arm64 tests (44-error compile Red first); cross-target clippy clean; image rebuilt (89,036 bytes, bbb85bd0…) — the staged card must be re-staged. Blind-flight caveat: the Pi 5 mailbox path is undocumented-stable; a dark screen still parks green and waits for the serial adapter. Also: the C# card-prep tool (owner preference) stayed untracked pending an ADR; it prepared the first card with letter-typed consent and a content manifest.

  3. 03AOwner direction: the Pi 5 is headless; the display is a remote desktop over peer-to-peer Ethernet

    No dedicated display, ever: any device connects to the Pi 5’s Ethernet port peer-to-peer (the recorded link-local deploy transport) and gets the UX as a remote desktop; the same authenticated link carries dev loop, deploy and the spoor stream. Converges with TinySpot and the Ti64 console’s seam architecture, and dissolves the on-target display problem. Chain: serial bootstrap (unchanged) → LE-26 Stories (PCIe → RP1 → NIC/DMA as a C2 service) → deploy-protocol/WCI session → UX stream as a console tab. Splash stays as-built, photo criterion opportunistic; first adaptive-splash boot remains unconfirmed (initial sighting withdrawn, recorded honestly).

  4. 04AOwner direction: TinyRemote — the cable is the signal, the window is the machine

    Names the product that replaces the ditched display: plug a peer-to-peer Ethernet cable between a TinyOS Pi 5 and a laptop and the TinyRemote host application renders the TinyOS desktop as if the machine were in that window — with a chooser for “something else” (Hardware Evidence, spoors, deploy, diagnostics). The cable is a discovery signal, never authority: sessions authenticate per the deploy-protocol/WCI model, remote bytes stay data, escape sequences stay inert. The Ti64 console is the embryo — its seams grow a transport. Chain unchanged: serial bring-up → LE-26 driver Stories → authenticated session → UX stream → chooser; first Ethernet Story can ship board-present detection as the earliest visible win.

  5. 05A04A executed: the card gains network smarts — FEAT-P1-09, the discovery signal over the firmware-kept link; TinyRemote renamed Ti64Dink

    The owner reordered (“the objective of this session is to fix it”) and the session delivered the device half of “the cable is the signal”: FEAT-P1-09 promoted through the full spine and host-implemented same-day — config.txt now generated with pciex4_reset=0 so the firmware keeps the PCIe ×4 link to RP1; the kernel gates on the always-mapped PCIe2 controller registers before one identity read through the 0x1F window (no abort machinery needed); clause-22 MDIO identifies the BCM54213PE before believing it and reads the cable state latched-twice; and after verdict + splash the board emits one TOS64-LINK/1 line and beacons TOS64-PRESENT/1 broadcasts (EtherType 0x88B5) once per second — a stock laptop packet capture becomes hardware evidence before the serial adapter works. Receive stays disabled and that absence is tested; LE-67 names the IOMMU-less transmit grant; LE-26 stays open. 171 + 266 host tests, cross-target clippy clean, spine green; card re-staged and hash-verified (e77aeb88…, 108,460 bytes). Nothing has run on silicon — every board criterion open, blocked on the serial adapter. Also recorded: TinyRemote is renamed Ti64Dink; its host-side promotion waits for FEAT-P2-10 under EPIC-P2.

  6. 06ANo signal: why the splash has never been seen, why Ethernet was dead, and what gates Ti64Dink

    Owner-ordered postmortem, opening with its own correction: the session misread an owner remark as a splash sighting and the owner promptly corrected — no signal on the monitor; the splash has never been seen on silicon. Q1: “no signal” narrows to unconfirmed plug conditions (port/input/timing never established for any attempt) vs. the Pi 5 firmware silently refusing the legacy mailbox framebuffer path — split cheaply by adding fb=granted|refused to the heartbeat. Q2: Ethernet died four layers deep — PHY held in active-low reset on RP1 GPIO 32 (LE-68, release implemented but unverified), the firmware-reset PCIe link (pciex4_reset=0 now generated, honor unproven), a driver chain that never existed by design (LE-26), and a serial instrument whose loopback was never run. Q3: Ti64Dink cannot ride Ethernet until the wire is proven, RX exists as a contract-gated C2 device service, link-local transport lands (EPIC-P3), and the deploy-protocol/WCI session layer exists — the cable is discovery, never authority, so a bare socket is forbidden, not just unfinished. What the wire can already carry: the TOS64-PRESENT/1 discovery beacon for FEAT-P2-10’s link-watch.

  7. 07AEvery instrument proven, TinyOS indicted: the work queue is now code, not cables

    The owner's common-cause argument (“two faulty cables is one-in-a-billion; the OS is the likely fault”) tested with one boot of stock Raspberry Pi OS on the same board, cables and monitor: Ethernet trained 1 Gbps with sub-millisecond bidirectional pings over IPv6 link-local, and HDMI0 showed a stable picture — every silence in this project's history was ours. Two charges stand: execution itself is unproven (the firmware's entry into kernel8.img has never been confirmed), and if it executes, both output paths fail silently. The laptop NIC replaces serial as the primary instrument (link training is visible with zero packets; serial is demoted after a fifth zero-byte capture on a healthy port). Staged and queued: the fb= heartbeat image (28682388…) on the proven display chain — splash or firmware-refusal, PHY release verified or convicted, in one boot. The Pi OS card stays as a ground-truth instrument (SSH into the working system; write drivers against what it measurably does). New C# host tools: tos64-serialwatch, tos64-imgwrite.
